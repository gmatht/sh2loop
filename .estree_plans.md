## Plan 4: lastExit-write liveness — drop dead `(( ))` ternaries / lastExit writes

- Status: **IMPLEMENTED** (direct, 2025-08-03 — 60c024f)
- Benchmark after: hot-loop `((i++))` body 17.6 -> 15.6 ms/300k (1.13x);
  bench-increment's loop is now `() => { i++; __n = __n + 1 }` — zero
  runtime surface per iteration. Call-site metric UNCHANGED (2865 —
  lastExit writes are property writes, not calls — expected).
- Issues: exposed a latent estree-gen bug (postfix `i++` rendered as
  prefix `++i`) — fixed in estree-gen.mjs; new corpus test
  arith-postfix-status.sh covers it. Errexit programs skip the pass (the
  guard consumes every statement's value). `$?` readers (getVar("?"),
  and/or, exit/return, subshell bodies) keep writes live. 529/529 estree.
- Priority: 1
- Target: `((i++))` / arithmetic-expression statements currently emit
  `((<expr> !== 0) ? ((sh2.lastExit = 0), true) : ((sh2.lastExit = 1), false))`
  even when the exit status is never read. Drop the ternary + lastExit writes
  (keep the side effect) when `$?` is provably unread before the next write.
- Rationale: 2,220 lastExit mentions / 482 tests. Loop bodies (`((i++))` inside
  `while`/`for` where `$?` and the loop status are unread) become bare `++i;` —
  removes 2 in-loop lastExit writes per iteration (count:increment's residual
  5 in-loop calls include them). Same family as the guard-liveness pass
  (08f6ec6); reuse its `MAY_ERREXIT` flag (keep writes when set -e may be on).
- Steps:
  1. In src/shir.rs, add a lastExit-liveness scan: for each statement that
     writes lastExit (the `(( ))` ternary, setLastExit calls, echo-status
     sequences), scan forward in the enclosing block for a lastExit READ
     (`sh2.getVar("?")`, `sh2.and`/`or`/`not`, test/if conditions, `return`/
     `break` statuses, a loop body's last statement when the loop status is
     consumed) before the next write. If none -> the write is dead.
  2. In the `(( ))` lowering, when dead, emit only the side effect
     (e.g. `++i` — the native arith path already handles lifted vars).
  3. Keep writes when MAY_ERREXIT is true (set -e could read the status).
  4. Corpus must stay 528/528; benchmark count:increment should drop from
     sh2[6 5 0] toward sh2[1 0 1].
- Benchmark before: count:increment js ~1215/s, sh2[6 5 0]

## Plan 3: unlifted `((i++))` (typeset-intVar path) — remove the 5-call regression

- Status: **IMPLEMENTED** (2025-08-03 — the INTDECL witness + let-source wiring)
- Target: `((i++))` with a NON-lifted variable (e.g. after `typeset -i i`) emits
  the verbose `sh2.setVar("i", String((Number(sh2.getVar("i"))||0)+1)), ...`
  chain (5 in-loop calls) — a 9x regression vs the old single `let` call
  (count:increment 1215/s vs 10959/s baseline). Either fall back to the
  `sh2.builtin("let", ["i++"])` form (1 call) or emit an efficient native
  form when the variable is store-backed.
- Root cause (two latent bugs, both in src/shir.rs):
  1. `collect_native_arith_sources` (the `typeset -i` Int(0) witness + the
     `let`/`(( ))` Arith assignment sources for the lift fixpoint) was
     defined but NEVER called — dead code since afab129. A var whose only
     writes were `((i++))`/`typeset -i` had NO assignment sources, so the
     fixpoint could never lift it.
  2. The walkers' intdecl skip was defeated by the exec arg shape: the
     names live inside the Array wrapper at args[1], so the per-name skip
     only matched bare Str args, while the `-i` FLAG's letters still
     marked the name store-bound via `mark_all_idents_args` (`-i` → "i")
     and the Array arg fell through `mark_write_builtin_vars` → excluded.
- Fix (Plan 3, direct):
  1. Wire `collect_native_arith_sources` into BOTH lift walkers' (numeric
     + string) `collect_assigns`/`collect_expr_assigns` for the
     `IrStmt::Exec` and `IrStmt::Expr(Call("exec"))` forms. The numeric
     side gains the Arith/Int sources (the lift); the string side gains
     them as disqualifiers (a `((x++))`-written var must not string-lift —
     the setVar the arith emits would desync from the native binding;
     this also FIXES a latent divergence: `x=abc; ((x++)); echo $x`
     printed "abc" vs bash's "1").
  2. Replace the per-name intdecl skip with a whole-call skip: a
     validated `-i` declaration writes nothing and references nothing.
  3. Guard: a native `((i++))` inside a subshell/background marks its
     written vars excluded (copy semantics — a module binding would be
     clobbered), mirroring the existing Assign-target exclusion.
- Result: `typeset -i i` + `((i++))` lifts `i` → per-iteration body is
  `i++; __count = __count + 1` (zero runtime surface; the lastExit ternary
  stays when the loop status is observable — the program's exit status).
- Benchmark after (10M-iter loop-only, same runner): **74.6s → 0.224s
  (333x)**; count benches sh2[1 0 1] / [2 0 1] — zero in-loop calls
  (bench.sh's js/s columns are node-startup-bound at CAL_MS=100, so the
  per-run js/s numbers wobble ~±30% — the loop-only delta is the truth).
- Metric: 2865 → 2843 call sites (getVar 404→388, setVar 191→185); the
  corpus in-loop sites are store-observed (unliftable by design).
- Issues: the documented SH2_ASSUME_INTDECL fidelity trade is now actually
  reachable: `typeset -i i` with an UNSET-state read (`echo $i` before any
  real write) prints "0" vs bash's "" — the same read-before-write trade
  the numeric lift already made for real sources (`echo $i` before `i=5`).
  Interpolated/bare `$refs` are native reads by design (getVar rewritten),
  so no string-context mark fires; SH2_ASSUME_INTDECL=0 restores maximal
  fidelity. Corpus 529/529, PERL pass count unchanged (441), cargo tests
  36/36 (new intdecl_and_arith_stmt_lift_to_native regression test).
- Benchmark before: count:increment js ~1215/s, sh2[6 5 0]
- Issues: (resolved — see above)

## Plan 9: sh2runtime capability manifest — the js/wasm "binary" registry
- Status: planned
- Priority: 3
- Target: the emitter hardcodes SYNC_BUILTINS + the runtime's builtins map
  with a "MUST match exactly" hazard — a drift between them leaves a
  runtime-capable command as a spawn (or worse, emits a sync call to a
  nonexistent builtin). Make the RUNTIME the source of truth:
  1. sh2runtime exports a capability manifest — `{ "js": [builtin names],
     "wasm": [wasm module names] }` — generated from the actual builtins
     map + the wasm registry (bc.wasm first).
  2. The emitter consumes it (embedded via include_str! at build time, or
     passed by the gate) — `exec("name")` dispatch: js-listed → sync
     sh2.builtin, wasm-listed → sync wasm call, else → spawn.
  3. Adding a native command = ship the js fn / .wasm + register it —
     the emitter's lowering follows automatically.
- Distinction (design decision): the manifest describes the RUNTIME's
  executable formats — js functions and wasm modules it can run natively,
  like binary formats for sh2runtime. It does NOT cover TRANSLATOR-side
  lowerings (echo/printf/cat/sort/grepText/arith/test-injection — inline
  JS emitted at compile time, no runtime call). The two layers compose:
  translator-inline first (compile-time, no dispatch), then the runtime
  manifest (sync dispatch), then spawn.
- Rationale: kills the drift hazard; makes bc (Plan 8) and future wasm
  binaries (tr/awk/sed as wasm — see Plan 10) a registry entry, not a
  special case.
## Plan 10: native text-filter subset — tr / sed-s / awk-print
- Status: planned
- Priority: 3
- Target: the corpus cmdsub families still spawn for `tr` / `sed` / `awk`
  (`$(echo "$s" | tr ...)` etc. — the strings-backtick/tr-cmdsub/awk
  examples). The benchmarks are already builtin-covered (echo/printf/cut/
  case) — this is corpus + the wasm registry's second batch.
  1. `tr` — translate/squeeze/delete over the stdin string — tractable
     (~50 lines), common in cmdsubs. Form: `$(echo X | tr SET1 SET2)` →
     native JS char-map; `-d`/`-s` too.
  2. `sed` subset — `sed -e 's/pat/repl/[gp]'` — the SAME substitution
     family as the already-native `${s/abc/XYZ}` — reuse its machinery;
     `-n ... p` (print-only) for the grep-like uses.
  3. `awk` subset — `awk '{print $N}'` (field printing) — covers most
     corpus uses; awk as a language stays on spawn.
- Implementation axis: each can be (a) a translator-inline lowering
  (like grepText), or (b) a wasm module registered in the Plan 9
  manifest (like bc) — prefer (a) for the simple forms, (b) for the
  general ones. The Plan 9 manifest makes (b) additive.
- Rationale: spawn-bound corpus examples are the remaining
  subprocess-parity gap; each lift removes real spawns from hot loops
  and cmdsubs.
