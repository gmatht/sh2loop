  4. Corpus must stay 528/528; benchmark count:increment should drop from

## Plan 3: unlifted `((i++))` (typeset-intVar path) — remove the 5-call regression

- Status: **IMPLEMENTED** (2025-08-03 — the INTDECL witness + let-source wiring)
- Target: `((i++))` with a NON-lifted variable (e.g. after `typeset -i i`) emits
  the verbose `sh2.setVar("i", String((Number(sh2.getVar("i"))||0)+1)), ...`
  chain (5 in-loop calls) — a 9x regression vs the old single `let` call
  (count:increment 1215/s vs 10959/s baseline). Either fall back to the
  `sh2.builtin("let", ["i++"])` form (1 call) or emit an efficient native
  form when the variable is store-backed.
- Root cause (two latent bugs, both in src/shir.rs):
  1. `collect_native_arith_sources` (the `typeset -i` Int(0) witness + the
     `let`/`(( ))` Arith assignment sources for the lift fixpoint) was
     defined but NEVER called — dead code since afab129. A var whose only
     writes were `((i++))`/`typeset -i` had NO assignment sources, so the
     fixpoint could never lift it.
  2. The walkers' intdecl skip was defeated by the exec arg shape: the
     names live inside the Array wrapper at args[1], so the per-name skip
     only matched bare Str args, while the `-i` FLAG's letters still
     marked the name store-bound via `mark_all_idents_args` (`-i` → "i")
     and the Array arg fell through `mark_write_builtin_vars` → excluded.
- Fix (Plan 3, direct):
  1. Wire `collect_native_arith_sources` into BOTH lift walkers' (numeric
     + string) `collect_assigns`/`collect_expr_assigns` for the
     `IrStmt::Exec` and `IrStmt::Expr(Call("exec"))` forms. The numeric
     side gains the Arith/Int sources (the lift); the string side gains
     them as disqualifiers (a `((x++))`-written var must not string-lift —
     the setVar the arith emits would desync from the native binding;
     this also FIXES a latent divergence: `x=abc; ((x++)); echo $x`
     printed "abc" vs bash's "1").
  2. Replace the per-name intdecl skip with a whole-call skip: a
     validated `-i` declaration writes nothing and references nothing.
  3. Guard: a native `((i++))` inside a subshell/background marks its
     written vars excluded (copy semantics — a module binding would be
     clobbered), mirroring the existing Assign-target exclusion.
- Result: `typeset -i i` + `((i++))` lifts `i` → per-iteration body is
  `i++; __count = __count + 1` (zero runtime surface; the lastExit ternary
  stays when the loop status is observable — the program's exit status).
- Benchmark after (10M-iter loop-only, same runner): **74.6s → 0.224s
  (333x)**; count benches sh2[1 0 1] / [2 0 1] — zero in-loop calls
  (bench.sh's js/s columns are node-startup-bound at CAL_MS=100, so the
  per-run js/s numbers wobble ~±30% — the loop-only delta is the truth).
- Metric: 2865 → 2843 call sites (getVar 404→388, setVar 191→185); the
  corpus in-loop sites are store-observed (unliftable by design).
- Issues: the documented SH2_ASSUME_INTDECL fidelity trade is now actually
  reachable: `typeset -i i` with an UNSET-state read (`echo $i` before any
  real write) prints "0" vs bash's "" — the same read-before-write trade
  the numeric lift already made for real sources (`echo $i` before `i=5`).
  Interpolated/bare `$refs` are native reads by design (getVar rewritten),
  so no string-context mark fires; SH2_ASSUME_INTDECL=0 restores maximal
  fidelity. Corpus 529/529, PERL pass count unchanged (441), cargo tests
  36/36 (new intdecl_and_arith_stmt_lift_to_native regression test).
- Benchmark before: count:increment js ~1215/s, sh2[6 5 0]
- Issues: (resolved — see above)

## Plan 9: sh2runtime capability manifest — the js/wasm "binary" registry
- Status: planned
- Priority: 3
- Target: the emitter hardcodes SYNC_BUILTINS + the runtime's builtins map
  with a "MUST match exactly" hazard — a drift between them leaves a
  runtime-capable command as a spawn (or worse, emits a sync call to a
  nonexistent builtin). Make the RUNTIME the source of truth:
  1. sh2runtime exports a capability manifest — `{ "js": [builtin names],
     "wasm": [wasm module names] }` — generated from the actual builtins
     map + the wasm registry (bc.wasm first).
  2. The emitter consumes it (embedded via include_str! at build time, or
     passed by the gate) — `exec("name")` dispatch: js-listed → sync
     sh2.builtin, wasm-listed → sync wasm call, else → spawn.
  3. Adding a native command = ship the js fn / .wasm + register it —
     the emitter's lowering follows automatically.
- Distinction (design decision): the manifest describes the RUNTIME's
  executable formats — js functions and wasm modules it can run natively,
  like binary formats for sh2runtime. It does NOT cover TRANSLATOR-side
  lowerings (echo/printf/cat/sort/grepText/arith/test-injection — inline
  JS emitted at compile time, no runtime call). The two layers compose:
  translator-inline first (compile-time, no dispatch), then the runtime
  manifest (sync dispatch), then spawn.
- Rationale: kills the drift hazard; makes bc (Plan 8) and future wasm
  binaries (tr/awk/sed as wasm — see Plan 10) a registry entry, not a
  special case.

## Plan 15: chain-context test lowering — native tests inside `&&`/`||` (the `_g` single-eval wrapper)

- Status: **IMPLEMENTED** (2025-08-05 — sh2perl a1a2b3c; estree.rs regression tests)
- Priority: 1
- Target: the `test` family (88 sites, the 4th-highest runtime construct). Tests
  inside `&&`/`||` chains stayed runtime calls (`sh2.test` — tokenize + parse +
  dispatch per evaluation) because the old rule required the native form to
  contain ZERO sh2 references (a store-var operand would lower to getVar calls
  — judged a net metric loss). Relaxed with three pieces:
  1. **`_g` single-eval wrapper**: `(sh2._g = t, sh2.lastExit = sh2._g ? 0 : 1,
     sh2._g)` — the guard/not scratch protocol — evaluates the native test
     ONCE (the old wrapper duplicated `t`, doubling its getVar reads and the
     metric count). A 1-getVar native is now metric-NEUTRAL vs the 1 runtime
     test it replaces.
  2. **Eligibility**: natives with ≤1 sh2.* call (a store-var/positional read —
     strictly faster, never a metric loss) and no awaits (file tests stay
     runtime in sync chain contexts). The count check uses a real AST walk
     (`expr_sh2_call_count`), not the old string contains-scan.
  3. **Op-skip instead of abort**: the numeric/string-op scans in
     `try_native_test` used `?`-abort on the FIRST operator match — a compound
     (`"$2"=="test" -o "$2"=="debug"`) never reached the `-a`/`-o` compound
     path. Failed operator positions now SKIP and keep scanning; the compound
     path lowers multi-leaf tests (`-o` splits first, `-a` inside — the
     runtime's binding order). The compound result is capped at ≤1 sh2 call
     ONLY when an op-skip occurred (`test_has_op_token`) — baseline-reachable
     pure-`-a`/`-o` compounds keep their pre-existing uncapped lowering.
- Result: 2654 → **2644** call sites (test 88 → 71, getVar 381 → 399 — the
  replaced tests' reads); in-loop sites drop 11 → 8 (the remaining in-loop
  tests are 2-getVar numeric guards, cmdsub operands, and async file tests —
  irreducible without whole-context async plumbing). Remaining tests are
  genuinely hard: cmdsub operands, array-index file paths, paren-grouped
  compounds, extglob patterns, `$'\x00'` escapes, `-nt`/`-ot`/`-ef`.
- Also lifted: `"$?"="0"` status equality (the `?` sigil is a lastExit read,

## Plan 16: general var-operand bc capture — `$(echo "$sum + $i" | bc)` native

- Status: **IMPLEMENTED** (2025-08-05 — shir.rs `bc_var_capture` +
  `bc_arith_to_js` + `bc_arith_divisors` + `bc_var_lit_ok`; estree.rs
  regression test extended)
- Priority: 1
- Target: the LAST async-forLoop straggler with a native path —
  `for i in 1 2 3 4 5; do sum=$(echo "$sum + $i" | bc); done` (the
  bc-native-capture corpus test) emitted `await sh2.capture(async () =>
  await sh2.pipeline([builtin echo, exec bc]))` PER ITERATION (4 in-loop
  sh2.* sites). Plan 8's native-capture hook only handled static programs
  and the `sqrt($var)` form. The general var-operand form (any
  `+ - * / % ( )` integer expression over interpolated vars) now lowers to
  `sum = String(Number(sum) + Number(i))` — and the whole loop becomes a
  native JS `for...of` (the body's last await is gone).
- Implementation:
  1. Reconstruct the bc program text from the interpolated echo arg,
     substituting each Expr slot with a `__bcvK` placeholder; the literal
     parts must pass `bc_var_lit_ok` (decimal digits, whitespace, the six
     operators ONLY — letters/`.`/`;`/`^`/comparisons/`#`/quotes bail to
     the spawn).
  2. Parse via the existing bash-arith parser `parse_arith` (the two
     grammars agree on `+ - * / %`, parens, unary minus, decimal
     literals, left associativity; `^` is bc POWER vs bash XOR — bailed;
     `010` parses DECIMAL in parse_arith, matching bc, and `0x`/`2#` base
     forms cannot pass the strict literal scan).
  3. Translate: slots → `Number(<slot expr>)` (bash vars are strings);
     `+ - *` → JS ops; `/` → `Math.trunc(a / b)` (bc's scale-0
     truncation toward zero); `%` → JS `%` (sign-of-dividend remainder,
     identical for integers). A zero divisor makes bc abort the WHOLE
     program with no stdout — each `/`/`%` site gets a
     `(divisor === 0) ? "" : ...` guard testing the divisor's VALUE (a
     nested `a / (b / c)` aborts on `b/c == 0`, not just `c == 0`); all
     operand exprs are pure reads, so the double evaluation is safe.
     Literal divisors skip the guard.
- Metric: 2611 → 2606 total, in-loop 11 → 7 (capture/pipeline/builtin/
  exec in-loop sites gone; forLoop 5 → 4, the bc-native loop is now a
  native for-of). No new sh2.* names (Math.trunc already whitelisted).
- Corpus: 531/531 estree; cargo tests 62/62 (bc_capture test extended:
  var-add form, Math.trunc + zero-divisor guard, `^` keeps the spawn);
  PERL pass count unchanged (441). Gate-OFF sanity: SH2_BC_NATIVE=0 keeps
  the spawn (the gate check runs before the whole lift).
- Documented assumption (shared with Plan 8's sqrt form, same option):
  every `$var` in the expression holds a bc INTEGER within 2^53. The
  double path is exact for such operands and String() prints the same
  digits as bc (bc's `.75`-style leading-zero omission cannot arise —
  results are always integers); a fractional operand would diverge, a
  non-numeric/unset operand ("NaN" vs bc's ""), a huge one (> 2^53).
  The corpus cannot observe these: `$sum` starts at integer 0 and every
  iteration adds an integer loop var (the invariant propagates).
- Issues: bc-native-capture.sh's stale "stays on the spawn by design"
  comment updated (the file is untracked in the submodule — inherited
  from the Plan 8 cycle, not committed there; the corpus reads the
  filesystem either way). Statement-level `echo EXPR | bc` pipelines (no
  capture) still spawn — the fold fires in capture context only, by
  design (their stdout is the pipeline's, and bc's stderr must still
  surface).

## Plan 17: sync-ok-loops verdicts wired — native/checkpointed loop emission (core request estree-20260805-045731)

- Status: **IMPLEMENTED** (2025-08-05 — this cycle; sh2perl commit pending)
- Priority: 1
- Target: wire the sibling worker's sync-ok-loops transform (analysis-only:
  per-loop `sync_ok` / `batch_ok` pointer-keyed verdicts, computed in
  `ast_to_ir`) into the loop renderer + runtime, so cheap/output-free loops
  run as ONE native chunk and long sync-executable loops yield every 1024
  iterations instead of blocking (or awaiting per iteration):
  1. `compute_async_region_loops`: a `sync_ok` loop is NOT an async-region
     loop (`if in_async && !sync_ok(st)`), so the existing sync gate emits
     it with the native for-of / native while path — zero runtime surface.
  2. For/While lowering: a `batch_ok` loop that still fails the native
     gate (async region / glob iterable / signals) emits
     `await sh2.forLoopBatch(iter, body, 1024)` /
     `await sh2.whileLoopBatch(cond, body, 1024)` instead of the blocking
     `forLoopSync`/`whileLoopSync` — sync chunks of 1024 with a
     `setImmediate` yield (bitmask-cheap counter, not a modulo), same
     flatten/glob/signal/_capExceeded semantics as the *Sync twins.
  3. Runtime: `forLoopBatch`/`whileLoopBatch` in sh2-namespace.mjs —
     EXACT mirrors of forLoopSync/whileLoopSync plus the iteration
     counter + yield; gate whitelist + A4 spec entries.
- Aggressiveness gating: the transform is registered in
  `transforms::all()` (the DEBASHC_TRANSFORMS machinery gates it like any
  worker transform); the renderer hooks consult the SAME gate
  (`transform_enabled("sync-ok-loops")`) so the bisect can disable the
  verdicts end-to-end without a rebuild. The verdicts are re-computed

  bound) OR (output-free AND finite) — a sync_ok capture producer
