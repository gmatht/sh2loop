# POSITIONAL_LOCAL lift accepts an `fnCall` call site but no `fnCall` lowering applies it

**Requester:** rust-frontend worker (gate log: loop-frontend-rust-frontend.log)
**Severity:** silent wrong output — a defined function's body never runs, with no
error on either side. Frontend-side workaround landed (see WORKAROUND); the
core inconsistency is still latent for every frontend that emits `fnCall`.

## NEED

`pos_lift_set` (sh2perl/src/shir.rs:6505) documents an `fnCall("name", [...])`
call site as a LIFT-ELIGIBLE "static call site":

```
6505:  ///   - every mention of the NAME is a static `exec("name", [...])` /
6506:  ///     `fnCall("name", ...)` call site whose args need no runtime flatten
6507:  ///     ([`direct_call_arg_ok`]); `fnValue`, `command`, `export -f`,
```

so such a function is lifted: its define lowers to a plain
`function f(__pos) { … }` that is deliberately NOT registered in
`sh2.functions` (shir.rs:40679).

But the only call-site arm that consumes `pos_lift_entry` is
`try_native_fn_call` (shir.rs:45203), which is the **`exec`** lowering — its own
doc says "the IR call is `exec`". A call site emitted as `fnCall` never consults
`pos_lift_entry`, so it renders as `sh2.fnCall("name", [...])` and dispatches
through the function map that the lift just emptied → command-not-found
(status 127), body never executed.

Either the analysis must stop accepting `fnCall` sites (then the define stays
registered and fnCall keeps working), or the `fnCall` lowering must honour the
lift exactly as the `exec` arm does. The current split is what makes it silent.

## WHY

Both gates are green on both sides of the mismatch, so the emit looks valid:

- the A1 emit passes ingress (`--target estree` exits 0),
- the estree output is well-formed JS,
- the only symptom is MISSING stdout (no stderr, no non-zero exit for the void
  call path — `sh2.fnCall` on a missing target sets `lastExit = 127`).

Diagnosed by rendering one file two ways:

```
SH2_ASSUME_POSITIONAL_LOCAL=1 otranspilerl-cli - --target estree < a1.json
  function hello(__pos) { … }            # define: NOT in sh2.functions
  sh2.fnCall("hello", ["3"]);            # call: map lookup -> 127, no output

SH2_ASSUME_POSITIONAL_LOCAL=0 otranspilerl-cli - --target estree < a1.json
  sh2.functions.set("hello", () => { … });
  sh2.fnCall("hello", ["3"]);            # works
```

## MINIMAL-CORE-CHANGE

One of (preferred first):

1. **Make the `fnCall` call-site lowering consult `pos_lift_entry`.** Factor the
   existing arm out of `try_native_fn_call` (shir.rs:45212-45224: `pos_call_arg_ok`
   check → `direct_binding_name` → `f([a1, …])`, awaited when the define is
   async) into a helper and call it from the `fnCall` arm before the
   `sh2.fnCall(…)` fallback. This keeps the analysis as documented and keeps
   `fnValue` unchanged.
2. **Or tighten the analysis**: in `pos_lift_set`, treat `fnCall` as a
   disqualified call site (like `fnValue` already is) instead of an eligible one.
   Smaller, but it gives up the lift for void calls and changes the comment at
   6505-6508.

## FAILING-CASE

`frontends/rust-frontend/testdata/t35_functions.rs` (gate `make test`, stage 3):

```rust
fn hello(n: i64) {
    println!("hello {}", n);
}

fn main() {
    println!("{}", twice(21));   // fnValue path — fine
    hello(3);                    // statement position -> fnCall before the workaround
}
```

native: `hello 3` is the 5th line. transpiled (fnCall emit): the line is absent.
`frontends/rust-frontend/testdata/t57_option.rs` hits it three times
(`show(...)` is void) — there the runner prints
`testdata/t57_option.rs: line 16: show: command not found`, i.e. the 127 path.

The same shape is reachable from any frontend that emits `fnCall` for a void
call to a positional-parameter function — c-sh-go emits
`fnCall(name, [args])` at frontends/c-sh-go/main.go:1103 and main.go:1082; its
functions carry named `params`, so it is masked there today, but a
positional-parameter `fnCall` emitter reproduces it exactly.

## WORKAROUND (landed in the frontend, no core change needed for the gate)

`frontends/rust-frontend/src/main.rs` statement-position user-fn calls now emit
`exec("name", [...])` — the form the core's bash frontend uses for a call to a
script-defined function, and the form all three native-call fast paths rewrite.
t35/t57 go green with the lift active (`hello(["3"])`). The core inconsistency
above still applies to `fnCall` emitters.

## OUTCOME: implemented

Took option 1: the `fnCall` arm in `expr_to_estree` (sh2perl/src/shir.rs)
now consults the same `try_native_fn_call` helper the `exec` site uses, so
POSITIONAL_LOCAL / param-lift / sync-direct call rewrites apply to a static
`fnCall("f", [args])` site; when no lift applies the helper reproduces the
old `sh2.fnCall(name, args)` emission byte-for-byte. Pinned by two
`shir_json_in` tests (`fn_call_site_honours_the_positional_lift`,
`fn_call_site_honours_the_param_lift`), both verified to FAIL against the
pre-fix arm and pass after it. `./fail-estree` 562/563 (the single failure,
`064_07`, is a pre-existing associative `${a[*]}` mismatch with zero
`fnCall` nodes); `cargo test --lib` failure set unchanged apart from the
two new tests.
