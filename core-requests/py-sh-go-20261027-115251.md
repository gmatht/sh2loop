# C backend: `sortedBigintJoin` inside `Return` emits a call with no helper definition

Frontend: `frontends/py-sh-go` (its own gate is now GREEN — `make test` →
101/101, 0 FAIL)
Filed: 2026-10-27T11:52+08:00 — by the py-sh-go frontend worker
Class: BUG in an existing backend lowering (C helper emission), not a new node

Supersedes `core-requests/py-sh-go-20261027-111627.md` (withdrawn — the
ESTree defect it describes was fixed on the frontend side; see that file's
`## RESOLUTION`).

## NEED

When a `sortedBigintJoin("arr")` call reaches the C backend **as the value of
an `IrStmt::Return`**, the backend renders the call but never emits the
`_sh_sorted_bigint_join` helper → the program does not link.

## WHY (cannot be fixed in the frontend)

py-sh-go now emits the canonical A1 for `return sorted(...)`:

```json
{"type":"Return","value":{"type":"Call","func":"sortedBigintJoin",
  "args":[{"type":"Str","style":"DoubleQuoted","value":"f"}]}}
```

plus `fnValue("factors", [...])` at value-consuming call sites (the contract's
value-returning call spelling, what c-sh-go emits). This is the same shape the
core frontend emits for a shell function's final `echo <value>`
(`{"type":"Return","value":…}` — verified: `f() { echo "$1"; }` →
`Return(getVar("1"))`), and it is required for the ESTree reference to return
the value instead of the status boolean.

The C backend's bigint-join support is keyed on the *previous* echo spelling:

- `analyze_array_return_fns` (`src/c_backend.rs` ~37878) only recognizes a
  lifted function whose **final statement** is
  `Expr(Call{exec|builtin, [Str("echo"), Array([Call{sortedBigintJoin, [Str(arr)]}])]})`.
- The helper body is emitted under `if !self.array_return_fns.is_empty()`
  (`src/c_backend.rs` ~12091).

With the canonical `Return(...)` shape, `array_return_fns` is empty → the
helper is skipped, while the call itself is still emitted by the ordinary
expression path → `undefined reference to '_sh_sorted_bigint_join'`.

Note the *int* helper has no such gate — it is emitted unconditionally, which
is why `sortedIntJoin` examples still build in C.

## MINIMAL-CORE-CHANGE

Either (preferred, smallest):

1. In `analyze_array_return_fns`, also accept the canonical form —
   `IrStmt::Return(Some(IrExpr::Call { func: "sortedBigintJoin", args }))` with
   `args[0] = Str(arr)` — so the existing array-return lowering applies to
   `Return` bodies as well; **or**

2. Gate the helper emission on *usage* rather than on the optimization being
   applicable: emit the `_sh_sorted_bigint_join` block whenever the program
   contains a `sortedBigintJoin` call anywhere (mirroring the int helper,
   which is unconditional). This is the conservative fix — the generic
   expression path already assumes the helper exists.

No contract change; `src/shir_json.rs`, `src/ir.rs`, the schema and the other
backends are unaffected.

## FAILING-CASE

`frontends/py-sh-go/testdata/t90_factor_bigint.py` (the only corpus example
with a bigint join). Both A1s are from the same source; `old`/`new` differ only
in the frontend's emit:

```
$ cd frontends/py-sh-go && ./py-sh-go --shir testdata/t90_factor_bigint.py --raw > t90.a1.json
$ OTRANSPILER_ROOT=<ws> otranspilerl-cli - --target c < t90.a1.json > t90.c
$ cc -O1 t90.c -o t90 -lgmp
t90.c:(.text+0x9e5): undefined reference to `_sh_sorted_bigint_join'
collect2: error: ld returned 1 exit status
```

Measured A/B on the same tree (old emit = echo-return + `capture`, new emit =
`Return` + `fnValue`):

| example | old (echo) | new (Return) |
|---|---|---|
| `t86_factor` (int join) | OK `[1, 2, 3, 4, 6, 12]` | OK `[1, 2, 3, 4, 6, 12]` |
| `t88_factor53` (int join) | OK | OK |
| `t89_factor_big` (bigint, no join) | OK `[1]` | OK `[1]` |
| `t90_factor_bigint` (bigint join) | OK `[1, 18446744073709551617]` | **link error** |

Expected after the fix: `t90` compiles and prints
`[1, 18446744073709551617]` / `[1, 1267650600228229401496703205389]`
(native-exact).
