# py-sh-go: A1 comprehension node (ArrayComp) incomplete — comp_for uncovered, working-tree impl does not compile and the gate rejects the node

## NEED
The A1 expr vocabulary must express Python **comprehension iterators** —
grammars-v4 Python3 rule `comp_for` (`[ASYNC] 'for' exprlist 'in'
or_test comp_iter?`), the iterator clause of list/set/dict displays and
generator expressions (`listcomp`/`setcomp`/`dictcomp`/`genexp`/
`testlist_comp`/`dictorsetmaker`, and the `argument` rule's sole-arg
`test comp_for?` generator form). A comprehension is an EXPRESSION that
evaluates to a NEW collection: iterate the `or_test` source, bind each
item to the loop target, evaluate the element expr per item (optionally
skipping items failing the `comp_if` filter). The node shape is the one
the pending comp_if/comp_iter requests already specify — and which the
estree worker has PARTIALLY implemented in the working tree:

```json
{ "type": "ArrayComp", "var": "x", "iter": <expr>, "elem": <expr>, "cond": <expr|null> }
```

`var`/`iter` ARE the comp_for clause; `cond` is the comp_if filter
(null = none). WHAT IS STILL NEEDED: a COMPLETE, COMMITTED, COMPILING
implementation. The working-tree partial (ir.rs variant, shir_json.rs
serialization, shir_json_in.rs ingress, shir.rs ESTree renderer) leaves
the crate with **33 E0004 non-exhaustive-match errors** — `IrExpr::
ArrayComp`/`IrExpr::Lambda` and `IrStmt::Select` arms are missing in
estree.rs and every non-ESTree backend — so `cargo build --bin debashc`
fails and the gate oracle (last-known-good binary) rejects the node
with `unknown expr type "ArrayComp"`.

## WHY
The coverage hook (rules-gap.sh) reports `comp_for` as a Python3
grammar rule no testdata example exercises (it is NOT ledgered in
frontends/coverage/refused-py-sh-go.txt; PARSER_GAPS.md line 190 lists
`comp_iter`/`comp_for`/`comp_if` as category 1 — "no A1 channel", i.e.
a contract gap, not a subset decision; py-sh-go has no FRONTEND.md).
No testdata example can be created: the hand-rolled parser in
frontends/py-sh-go/main.go has no comprehension arm — the `[`/`{`/`(`
literal parsers in `parsePrimary` accept only comma-separated elements,
so `for` in comp_iter position always fails loudly (verified
2026-08-13 22:50):

    $ printf 'x = [i * 2 for i in [1, 2, 3]]\nprint(x[1])\n' | ./py-sh-go --shir /dev/stdin --raw
    py-sh-go: parse: expected "]"
    exit=2

And even a hand-emitted ArrayComp document (the exact shape above) is
rejected by the current gate oracle:

    $ ./sh2perl/target/debug/debashc --shir-in-estree /tmp/ac-probe.json
    ShIR JSON ingress: Program.stmts[0].expr.type: unknown expr type "ArrayComp"

while the checked-out core cannot rebuild to accept it (33 E0004s, see
MINIMAL-CORE-CHANGE). So the construct is inexpressible end-to-end
(frontend emit -> ingress acceptance -> executed-stdout oracle) until
the ArrayComp implementation is completed and committed. This is the
same node requested by the still-open py-sh-go-comp-if-20260813-215131.md
and py-sh-go-comp-iter-20260813-223651.md (both pending — the working
tree has the uncommitted partial, but the requests are not in done/ and
core-pending-py-sh-go.txt still ledgeres comp_if/comp_iter); comp_for
itself has no pending escalation, which is why rules-gap.sh reports it
and this request exists. Completing the shared node closes all three
rules at once (any comprehension example exercises comp_for AND
comp_iter; a filtered one adds comp_if).

## MINIMAL-CORE-CHANGE
The variant, serialization, ingress and ESTree rendering already exist
in the working tree (uncommitted, modified: src/ir.rs, src/shir.rs,
src/shir_json.rs, src/shir_json_in.rs). What remains:

1. **Make the crate compile**: add the missing match arms. Current
   E0004 inventory (verified `cargo build --bin debashc`, 33 errors):
   `&ir::IrExpr::ArrayComp { .. }` and `&ir::IrExpr::Lambda { .. }` not
   covered + `&ir::IrStmt::Select { .. }` not covered (+ one `None`),
   in src/estree.rs, src/shir.rs, src/go_backend.rs, src/perl_backend.rs,
   src/sh_backend.rs, src/glsl_backend.rs, src/c_backend.rs,
   src/zig_backend.rs, src/rust_backend.rs, src/js_backend.rs.
   ArrayComp/Lambda are documented "ESTree-path only" in ir.rs — the
   non-ESTree backends may take `unreachable!()`/no-op arms, but
   estree.rs must dispatch to the EXISTING renderer at shir.rs:30295
   (an IIFE loop: `sh2.setVar(var, item)` per element, skip on falsy
   `cond`, push `elem`, return the array) so the executed-stdout oracle
   (native python3 vs estree-runner.mjs) can match.
2. **Commit** the completed implementation (estree worker's normal
   batch; move the pending comp_if/comp_iter requests to done/ and
   prune frontends/coverage/core-pending-py-sh-go.txt so the coverage
   worker retries comp_for/comp_iter/comp_if — the frontend-side
   parsePrimary arms + testdata example land after).
3. The gate oracle self-heals: the py-sh-go Makefile rebuilds debashc
   from the checked-out core when the binary is stale (falling back to
   the last-known-good binary only while the tree is broken).

The frontend side (list/set/dict literal arms: after the first element,
detect `for`/`if` -> parse comp_for/comp_if -> emit ArrayComp; genexp
sole-arg form likewise) is py-sh-go's own fix and lands after the
contract is complete.

## FAILING-CASE
Minimal Python programs (python3 runs both fine):

```python
x = [i * 2 for i in [1, 2, 3]]
print(x[1])
```

stdout: `4` (x = [2, 4, 6] — the comp_for mapping).

```python
x = [i for i in [1, 2, 3, 4] if i > 2]
print(x[0])
print(x[1])
```

stdout: `3`, `4` (x = [3, 4] — comp_for + the comp_if filter).

Current behavior (verified 2026-08-13 22:50): the frontend exits 2 with
`parse: expected "]"`; the hand-emitted ArrayComp A1 document is
rejected by the gate binary (`unknown expr type "ArrayComp"`); and
`cargo build --bin debashc` fails with the 33 E0004 errors listed
above — so no testdata example can cover `comp_for` until this
completes.

## OUTCOME: implemented — ArrayComp (var/iter/elem/cond) is complete and compiling: ir.rs variant, shir_json serialization, strict ingress, estree IIFE-loop renderer (setVar per item, cond skip, push, return array), all backends armed, schema.json updated. Verified with hand-emitted A1 docs: `[i*2 for i in [1,2,3]]` → 4; `[i for i in [1,2,3,4] if i>2]` → 3,4. The py-sh-go parsePrimary comprehension arms are the frontend's own fix.
