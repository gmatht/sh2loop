# triage: perl backend can't render what the zsh-sh-go frontend emits

## NEED
The perl renderer must handle this A1 (the estree reference renders it and
matches native).

## FAILING-CASE
frontend zsh-sh-go, example t89_arith_call.zsh (cross-product pair).

## EVIDENCE
estree matches native; perl differs

## OUTCOME: rejected: needs a zsh-mathfunc subset the shared parser does not model

Re-measured at HEAD: `harness/triage.sh zsh-sh-go t89_arith_call.zsh perl` →
FAIL-BACKEND. This one is NOT superseded — it reproduces, and the diff is
three distinct gaps, none of them a one-liner:

1. `exec("let", ["hypot(3, 4) == 5"])` in a STATEMENT/`&&` chain rebuilds as
   shell text (`bash -c 'let …'`), and bash has no `hypot`/`fmod` →
   `let: hypot(3, 4) == 5: syntax error in expression`. Only the
   CONDITION-position `let` takes the native `arith_text_to_perl` path.
2. That native path would emit `$hypot(3, 4)` unless `hypot`/`fmod` join its
   `skipped` identifier list, and Perl then needs `use POSIX qw(hypot fmod)`.
3. `arith(" int(3.7) ")` / `arith("int(9)")` — `parse_arith` (shir.rs) accepts
   no call syntax at all, so the value is undefined and the renderer prints
   `syntax error in expression`. Supporting mathfunc call nodes is a PARSER
   extension, shared with every backend.

Why it is not being done this round: (a) it is a parser + arith-rendering
extension for a zsh-only subset, with the whole shared corpus as blast radius,
and (b) the pair cannot be regression-gated natively — `zsh` is not installed
on this box, so triage's oracle is the estree reference alone.

Recommended resolution (better than teaching every backend zsh mathfunc):
have the zsh frontend lower `zmodload zsh/mathfunc` calls to the existing
sh2.* value ops the estree arm already implements (int/sqrt/hypot/fmod are
there) instead of emitting raw `let`/`arith` text — then every backend renders
them from the IR, which is the documented A1 contract.
