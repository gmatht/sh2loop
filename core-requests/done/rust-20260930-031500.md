# rust backend — t109 bool-function: estree target mis-lowers user predicates

- **Filed:** 2026-09-30
- **From:** `backends/rust` worker
- **Gate:** `fail-go --rust` — `t109_bool_func.go  js=MISMATCH  rust=PASS`
- **Impact:** holds the *rust* backend's gate red even though the rust column
  is fully green (`setup_backends.sh:1570` gates on `fail-go`'s exit code, and
  `fail-go:265` exits 1 whenever `js_fail > 0`).

## NEED

Fix the **estree** target so a user-defined `bool` function used in a
condition and printed as a value lowers faithfully. Currently the estree
rendering prints `not-n / false` where the oracle is `yes / not-n / true`.

## WHY

`testdata/t109_bool_func.go`:

```go
func isYes(s string) bool { return s == "y" }

func main() {
	if isYes("y")  { fmt.Println("yes") }
	if !isYes("n") { fmt.Println("not-n") }
	fmt.Println(isYes("y"))
}
```

Measured, on this machine, with the estree runner
(`node harness/estree-runner.mjs /dev/stdin --source <file>`):

| leg | output |
|---|---|
| oracle (`go run`) | `yes` / `not-n` / `true` |
| **estree (js)** | `not-n` / `false` — **wrong** |
| **rust** | `yes` / `not-n` / `true` — correct |

The failure is specific and diagnosable: the **first** `if isYes("y")`
never fires (its `fmt.Println("yes")` is missing), and the final
`fmt.Println(isYes("y"))` yields `false` instead of `true`.

The go-sh frontend emits valid A1 for this file
(`go-sh --shir t109_bool_func.go --raw` → rc 0, 5290 bytes), and
`otranspilerl-cli --target estree` consumes it cleanly (rc 0, 25822 bytes),
so the defect is in the **A1 → estree lowering**, not in parsing or ingest.

Because the predicate's verdict is carried by bash-style "exec the predicate,
then `test $?`" semantics, the likely fault is that the estree path drops or
mis-orders the `__SH_RC`-style status check when the call sits in a condition
(`!isYes("n")`) and in a value position (`fmt.Println(isYes("y"))`) — the two
places the rust renderer handles correctly.

## MINIMAL-CORE-CHANGE

None proposed — this is a bug in an existing lowering, not a missing node or
transform, so per `core-requests/README.md` this is a `.md` request for the
estree worker to diagnose and fix. No new shIR node, contract field, or
transform is required: the A1 contract already carries enough information for
the rust backend to render t109 correctly from the *same* A1 bytes.

## OUTCOME: implemented — landed as sh2perl `22083e1c4` (core, this round).
The `IrStmt::Function` arm bound `name`/`body`/`named_blocks` and dropped
`params`, so every A1-declared function emitted `() => …` and its body's
parameter reads fell through to the (empty) `sh2.vars` store. Fixed by
threading the declared plain-identifier params into the arrow and adding
`NAMED_PARAMS` so a read of one renders as the bare identifier. `is_named_param`
is checked AFTER the lift/slot arms (a lifted `local` of the same name shadows
the param) and before the store read. Verified: `./fail-go --rust t109` 1/1 js
pass 1/1 rust pass; `./fail-estree` 554/555 (unchanged — the path is a no-op
for bash-sourced functions, which emit no `params`); 3 new regression tests pass
in `shir::named_param_emission_tests`.
