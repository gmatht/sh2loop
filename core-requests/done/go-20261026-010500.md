# go: the gate's RENDER step has no exec-failure retry and no per-file line — a green corpus collapses to `CRASHED`

**Type:** gate harness (`setup_backends.sh`), not a shIR/core change. No shared-core
file is implicated and no go renderer change is requested; the go backend builds
and measures green on this exact corpus (evidence below).

## NEED

`setup_backends.sh`'s backend-gate corpus loop retries ONLY the core-emitter
exec-failure class (`harness/emit-shir-retry.sh`, wired at the `shir=$(...)`
assignment). The very next step — the renderer exec,

```sh
if g_out=$(printf '%s' "$shir" | "$g_bin" "$g_flag" - 2>/dev/null); then ok=1; else ok=0; g_out=""; fi
```

— has NO retry, and its failure is the only unclassified per-file path that
prints nothing. `fail` increments, `stub_files`/`eq_fail`/`sa_fail_total` stay
zero, and the verdict collapses to:

```
[go] backend gate: CRASHED (no classification) — 2/651 files failed and NONE produced a stub/equiv/static-analysis verdict; not a test score
```

The CRASHED branch also `exit 1`s BEFORE the `fails:` list is echoed, so the two
files are unrecoverable from the log — the run is not just discarded, it is
undiagnosable.

## WHY (measured, go backend, 2026-10-26)

Three consecutive official gate runs on one unchanged worktree:

```
22:5x  [go] backend gate: 644/651 corpus render OK, 0 fail, 7 skip ... equiv: 644 pass vs bash
00:2x  [go] backend gate: shir emit FAILED for .../tail-standalone.sh (rc=126, binary=... inode=3617845)   <- PRESENT inode
       [go] backend gate: CRASHED (no classification) — 1/651 files failed
00:2x  [go] backend gate: shir emit FAILED for .../bench-substr.sh (rc=127, binary=... inode=3682123)      <- PRESENT inode
       [go] backend gate: CRASHED (no classification) — 1/651 files failed
00:27  (no per-file line at all)
       [go] backend gate: CRASHED (no classification) — 2/651 files failed
```

The same corpus, rendered on demand through the same worktree bin:

```
$ for each of the 651 files: shir_render --target=go - < A1
scanned=651 render_fails=0
$ harness/go_gate_local.sh          # same corpus, same go arm, same verdict
644 PASS / 7 SKIP / 0 FAIL
```

So the failures are a MEASUREMENT artefact of two known shapes, both of which
already bit the emit step and were fixed there:

1. **exec window** — the worktree's `target/debug/shir_render` is relinked
   mid-run by another agent's `build-lock.sh --share-target` / `core-sweep`
   invocation, giving rc=126 (ETXTBSY) or rc=127 (path momentarily absent).
   `-x` is TRUE by the time anything inspects it, so nothing here can tell.
2. **A1 revision skew** — the emit comes from the SHARED main-tree
   `otranspilerl-cli` (rebuilt constantly by the estree worker) while the render
   uses the WORKTREE's older core copy. An A1 field/node added to main between
   the two builds is rejected by the worktree renderer for the files that touch
   it. This is the same "the renderer is a different revision than the emitter"
   hazard the metric script documents at length (GO_SHIR_RENDER comment).

Both are self-healing over minutes and neither is a go-lowering verdict, yet
each one reports as `gate FAILED` and burns a full worker attempt.

## MINIMAL-CORE-CHANGE

Two small edits in `setup_backends.sh`, mirroring what the emit step already has:

1. Wrap the render exec in the same retry policy (exec-failure class only):

```sh
# render-shir-retry.sh <renderer> <flag> <a1-file>   — stdout: the render
# rc 0 emitted; N the renderer RAN and rejected the A1 (returned at once);
# 126/127 retried like the emit step (a relinked path / ETXTBSY), and after
# every attempt a verified private copy of the renderer is used (a copy cannot
# be busy, and its name is keyed on (path, inode, mtime) so it can never serve
# a different binary).
```

   `harness/emit-shir-retry.sh` is already exactly this shape; the render step
   only needs `"$g_bin" "$g_flag" - < "$a1"` instead of `--target shir <file>`.
   Reusing the same helper (a `--mode=render` arm) keeps one policy, one
   selftest.

2. Print the fail list BEFORE the CRASHED `exit 1` (or make the CRASHED line
   carry `$fails`), so the next occurrence names its files:

```sh
if [ "$fail" -gt 0 ] && ...; then
  echo "  [$g_lang] backend gate: CRASHED (no classification) — $fail/... failing: $fails" >&2
  exit 1
fi
```

Either edit alone converts an undiagnosable corpus-wide CRASHED into one loud,
retried, named file.

## SECOND NEED: this branch cannot sync without a core owner

`backend/go` is 45 ahead / 42 behind `origin/main`, and merging main conflicts
ENTIRELY in single-owner shared core (`git merge --no-commit --no-ff origin/main`,
probed 2026-10-26, then aborted — a backend worker must not resolve these):

```
CONFLICT (content): src/render_ext_estree/handlers/mod.rs   (build.rs-generated)
CONFLICT (content): src/rust_backend.rs
CONFLICT (content): src/shir.rs
CONFLICT (content): src/transforms.rs
CONFLICT (add/add): src/transforms/slice_identity.rs
```

Until a core owner reconciles them, this worktree renders main's A1 with a core
copy 42 commits behind the emitter — hazard 2 above is structural, not
occasional. The branch's shared-core deltas that need reconciling are:
`src/shir.rs` (+49), `src/transforms.rs` (+4), `src/transforms/slice_identity.rs`
(new, 404 lines — also landed on main independently), `src/transforms/builtin.rs`,
`src/rust_backend.rs`, and the generated `src/render_ext{,_expr,_estree}/handlers/mod.rs`.

## FAILING-CASE

`setup_backends.sh --backend-gate go` on this worktree, corpus
`sh2perl/examples/*.sh` + `sh2perl/frontends/*/testdata/*.sh` (651 files).
Reproduce the exec window deterministically (the method
`harness/emit-shir-retry.sh`'s header already documents for the emit step):

```sh
# hold the renderer open for write, then run the loop-equivalent render
python3 -c 'import time;f=open("sh2perl/backends/go/target/debug/shir_render","r+b");time.sleep(8)' &
sleep 0.2
sh2perl/backends/go/target/debug/shir_render --target=go - < a1.json   # -> rc 126, counted FAIL, no message
```

Note: not blocking the go backend. It is the reason this worker's attempts have
been reporting `gate FAILED` on a tree that renders 651/651 and passes
644/7/0 locally.

## OUTCOME: implemented — both gate edits are already in the shared core: the render exec is retried through `harness/emit-shir-retry.sh --mode=render` (setup_backends.sh, commit 8abb49f2) and the CRASHED line now carries `failing: $fails`, so an exec window is retried and any residual failure is named; `harness/emit-shir-retry.selftest.sh` render arm: 20/20 pass. The backend/go↔main merge is NOT a core-owner action here: `backend/go` is a per-backend worktree whose core deltas must be reconciled by that backend worker when it syncs (merging a backend branch into the core tree would put backend-only core edits on main).
