# triage: c backend can't render what the cpp-sh-go frontend emits

## NEED
The c renderer must handle this A1 (the estree reference renders it and
matches native).

## FAILING-CASE
frontend cpp-sh-go, example t27_sized_type.cc (cross-product pair).

## EVIDENCE
estree matches native; c differs

## OUTCOME: rejected — phantom: the C renderer was never wrong; harness/triage.sh's link line was

This pair now reads **PASS**. Reproduced, not inferred.

`FAIL-BACKEND ... (estree matches native, c differs)` is triage's verdict when
the estree reference matches native but the backend's executed stdout differs.
The backend cell here returned EMPTY for a reason that has nothing to do with
rendering: `harness/triage.sh` compiled the emitted C with a bare
`cc main.c -o main`, but the C backend emits `#include <gmp.h>` and calls
`__gmpz_init` / `__gmpz_init_set_str` / `__gmpz_get_str` for any program whose
A1 mentions a BigInt. The link failed, `&& ./main` never ran, and empty stdout
was diffed against native.

Linking with `-lgmp` makes the emitted C byte-identical to the g++ native:

    t27_sized_type.cc   C: u=3000000000 ll=5000000000
                        native: u=3000000000 ll=5000000000
    t28_sizeof.cc       C: 1 4 8 8
                        8 8
                        native: 1 4 8 8
                        8 8

Both pairs flip to PASS after the harness fix. Fixed in `harness/` (core scope)
by commit `02c387c6`: the run field gains an optional 4th component
`mode:cmd[:ext[:extra]]` appended after `-o main`, set to `-lgmp` for the C
row. Nothing in `src/` was touched — there was no C defect to fix.

Keep this pattern in mind for future cross-product backend requests: check
whether the backend cell even BUILT before treating the pair as a renderer
gap. `harness/triage.sh` suppresses both the compile stderr and the link error
(`2>/dev/null`), so a build failure is indistinguishable from a wrong answer in
the recorded verdict.
