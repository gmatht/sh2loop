# zsh-sh-go: shell `for ((...))` never lowers to the A1 `ForInit` node — no frontend can cover it

Same shared-core situation as `core-requests/zsh-sh-go-20260813-003026.md`
(the A1 `Continue` node): the node is complete end-to-end in the contract,
but the shared core's SHELL lowering never emits it, so a byte-locked shell
frontend cannot cover it. This request files the A1-node `ForInit` gap for
the zsh-sh-go ledger (`frontends/coverage/coverage-gap.sh zsh-sh-go` →
`A1 node ForInit`, first line of the actionable list, gate green).

## NEED

The shared core's shell frontend must lower the C-style `for (( init;
cond; step ))` loop to the A1 `IrStmt::ForInit` node (statement position)
so `debashc --shir FILE --raw` can actually emit `"type": "ForInit"`.
Today the shell frontend path **never** constructs `IrStmt::ForInit`:
`stmt_for_command` at src/shir.rs:5573 lowers `Command::CStyleFor(cf)` to

```rust
IrStmt::Expr(call("cstyleFor", vec![st(&cf.arith_content),
    IrExpr::Arrow(body_stmts(&Command::Block(cf.body.clone())))]))
```

— the header survives as ONE opaque arithmetic string (`"i=0; i<3; i++"`)
evaluated by the runtime's evalArith. The only `IrStmt::ForInit`
constructions in the tree are `shir_json_in.rs:460` (the A1 deserializer)
and `shir_passes/strip.rs` (the lowering pass + its unit test) — so no
`--shir` output for any zsh/POSIX program contains a ForInit node, and
the A1-node coverage proxy reports `A1 node ForInit` for zsh-sh-go.

The node itself is complete end-to-end — no contract change needed:

- schema: `frontends/shir-contract/schema.json` stmts.ForInit
  (`{type, init: stmt[], cond: expr, step: stmt[], body: stmt[]}`;
  required: type, cond, body)
- serializer: `src/shir_json.rs:174` —
  `IrStmt::ForInit { init, cond, step, body } => json!({ "type": "ForInit", ... })`
- deserializer: `src/shir_json_in.rs:460` — `"ForInit" => IrStmt::ForInit`
- lowering: `src/shir_passes/strip.rs` (`strip_cfor`) — already wired into
  `--shir-in-estree` / `--shir-in-perl` / `--shir-in-sh` (core requests
  c-sh-go-20260812-205941 / cpp-sh-go-20260812-210616, order: strip BEFORE
  restructure per c-sh-go-20260812-211500), so the renderers never see an
  unstripped ForInit
- precedent shape: the C-family frontends already emit it —
  `frontends/cpp-sh-go/testdata_cpp/t05_arith_loop.cc` →
  `{"type":"ForInit","init":[Assign…],"cond":{"type":"Call","func":"test","args":[Str("$i -le 4")]},…}`

## WHY

zsh-sh-go gate is GREEN but `frontends/coverage/coverage-gap.sh
zsh-sh-go` reports `A1 node ForInit` uncovered. The frontend is
byte-locked to the core's `debashc --shir FILE --raw` emit (Makefile's
BYTE-EQUALITY ORACLE); the core's shell emit for the construct is a
`cstyleFor` Call (Expr/Call/Str/Arrow — no ForInit), so the gap detector
can never see a ForInit type in any zsh-sh-go testdata emit.

Probing the construct through the zsh-sh-go frontend (gate green today):

```
for ((i=0; i<3; i++)); do echo $i; done   -> Parse error: for: expected variable at 4
for ((i=0; i<3; i++)) { echo $i; }        -> Parse error: for: expected variable at 4
```

(`parseFor` in main.go requires an ident after `for`; the `((` header is
refused.) This is NOT a by-design subset refusal: FRONTEND.md excludes
nothing here — the construct HAS a bash-shaped A1 form in the core (the
core parses `for ((...))` fine, as `Command::CStyleFor` → `cstyleFor`
Call; the zsh frontend's parser mirrors the core's bash-shaped grammar),
and the core `for ((...))` executed-stdout path is fully supported
(`cstyleForSync` runtime twin, estree.rs test at 3839). What is
inexpressible is the **ForInit emission shape**, which only the shared
core's shell lowering can provide — the identical situation to the
pending/ledgered A1 `Continue` request
(`core-requests/zsh-sh-go-20260813-003026.md`). Escalating per the
core-requests channel (the estree worker is the single owner of
src/shir.rs).

## MINIMAL-CORE-CHANGE

Scope: `src/shir.rs` only — the `Command::CStyleFor` arm of
`stmt_for_command` (src/shir.rs:5573). Split the header string on `;`
(init; cond; step — the same split the backends already implement, e.g.
c_backend.rs:4563 "The cstyleFor condition: split on the comparison ops"
and perl_backend.rs:964's cstyle_for_expr header handling), and lower
through the EXISTING arith machinery:

- `init` (`"i=0"`) → the existing arith-assignment lowering (the
  `let i=0` / `((i=0))` path already produces
  `Assign{expr: Arith{...}}` — the `arithEvalStmt`/let mirror in the
  zsh frontend's lowering.go);
- `cond` (`"i<3"`) → the existing test/arith cond lowering (the
  `$i -le 4`-style test Call shape the C-family frontends emit, or the
  equivalent `Arith`-based cond the shell side already uses for
  `(( ... ))` conditions — pick the shape that keeps the estree output
  semantically identical);
- `step` (`"i++"`) → `Assign{expr: Arith{IncDec}}` via the same
  arith-assignment path;
- `body` → unchanged (`body_stmts(&Command::Block(cf.body.clone()))`);

emitting `IrStmt::ForInit { init, cond, step, body }`. Serializer,
deserializer, schema, and strip_cfor all already exist — nothing else in
the core needs to change.

Keep unchanged (same "keep unchanged" discipline as the Continue
request): the expression-context path `command_to_ir` (src/shir.rs:6285)
has no CStyleFor arm today — `for ((...))` is statement-only in shell, so
nothing to mirror there.

Corpus constraint (the estree worker mediates): this changes `--shir`
output for every shell file containing `for ((...))`. Executed-stdout
semantics are preserved (strip_cfor lowers to `init; while(cond){
body-with-step }` — the exact shape the frontends used to emit), but the
estree renderer would take the While path (stmt-level sync fast path)
instead of the `cstyleFor`→`cstyleForSync` fast path (src/shir.rs:28391),
so estree output SHAPE changes for cstyleFor-bearing scripts and the
estree corpus must be re-verified (`./fail-estree`); the backends'
`cstyleFor` arms (perl/go/sh/c) keep working via the already-wired
strip_cfor. Frontend byte-equality gates (zsh-sh-go, posix-sh-go, and
any other shell frontend with a `for ((...))` example) will show `DIFF`
until each frontend mirrors the new shape in the same window — the
established pattern from `core-requests/done/posix-sh-go-20260806-174619.md`;
the zsh-sh-go mirror is `main.go`'s `parseFor` (add the `((`-header arm
→ `Command::CStyleFor`) + `lowering.go`'s `stmtForCommand` (add the
ForInit arm). If the corpus mediation judges the cstyleFor Call shape
irreplaceable, the alternative is to mark this request REJECTED with a
mediation note — but then `A1 node ForInit` stays permanently uncovered
for the shell frontends (and the C-family frontends keep emitting the
ForInit node, which the A1 contract already carries for them).

## FAILING-CASE

Minimal zsh-sh-go (zsh) snippet — the coverage example this request
unblocks (currently uncreatable):

```zsh
for ((i=0; i<3; i++)); do
    echo $i
done
```

Today `debashc --shir failing.zsh --raw` emits — and the zsh-sh-go
frontend must byte-match — no ForInit anywhere; the loop lowers to:

```json
{"type":"Expr","expr":{"type":"Call","func":"cstyleFor",
  "args":[{"type":"Str","style":"DoubleQuoted","value":"i=0; i<3; i++"},
          {"type":"Arrow","body":[ … echo … ]}]}}
```

After the change the A1 must contain (the deserializer + strip_cfor
already consume this shape — see the cpp-sh-go emit of
testdata_cpp/t05_arith_loop.cc for the reference structure):

```json
{"type":"ForInit",
 "init":[{"type":"Assign","targets":[{"var":"i","indices":[],"sigil":null}],
          "expr":{"type":"Arith","ast":{"type":"…","value":"0"}}}],
 "cond":{"type":"Call","func":"test","args":[{"type":"Str","style":"DoubleQuoted","value":"$i < 3"}]},
 "step":[{"type":"Assign","targets":[{"var":"i","indices":[],"sigil":null}],
          "expr":{"type":"Arith","ast":{"type":"IncDec","var":"i","delta":1,"prefix":false}}}],
 "body":[ … echo $i … ]}
```

Repro of the gap itself (no core change needed to see it):
`bash frontends/coverage/coverage-gap.sh zsh-sh-go` →
`A1 node ForInit` (first line of the actionable list), with the gate
green — the examples cannot cover the node until this request lands.
