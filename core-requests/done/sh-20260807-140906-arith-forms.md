# sh: bash-shaped arithmetic forms (let / (( )) / c-style-for headers) are exec-string blobs — add a shared transform that parses them into structured IR

## NEED
A shared IR transform (`src/transforms/arith_forms.rs`, registered in
`transforms.rs`, env-gated like `seq_range_for`) that recognizes the
bash-shaped arithmetic forms the parser currently emits as exec-string
blobs, parses them with the existing arith grammar, and rewrites them
into structured IR every renderer can emit portably:

1. `exec("let", [<arith-expr>, ...])` → one `Assign` per expr
   (`let x+=1 y=2` → `x=$((x+1))`; `y=2`). POSIX has no `let`;
   `$(( ))` assignments ARE the portable form.
2. `exec("<init>; <cond>; <inc>", [body...])` (the c-style-for header
   blob) → `Assign(init…); While(cond, body, inc)`. Same grammar the
   estree runtime's `cstyleForSync` already parses — doing it once at
   IR level serves every backend (sh: POSIX while; estree: native for).
3. `(( expr ))` bare-compound conditions → `[ $((expr)) -ne 0 ]` form
   (the renderers' existing test machinery).
4. `$[old]` arith — already structured (Bin nodes); skip.

## WHY
The chimera gate's rc=2 cluster (let-plusassign, arithmetic-equality,
055_factorize, 058_advanced_bash_idioms, 047_for_arithematic,
parse-arithmetic-*, let arithmetic) is dominated by these forms. Today
`let x+=1` renders as `[ "$(($( _num "x" )+=1))" -ne 0 ]` — the `+=`
applies inside a COMMAND SUBSTITUTION, so x is never assigned and the
side effect is silently lost (a wrong-answer bug, not just a portability
gap). The c-style-for header being a string blob means the sh renderer
cannot emit a POSIX while loop at all. These are bash-isms whose portable
lowering is well-defined — the right place is the shared IR so all
backends inherit it (mirror of the seq_range_for precedent).

## MINIMAL-CORE-CHANGE
- `src/transforms/arith_forms.rs`: `fn transform(&mut Vec<IrStmt>) -> bool`.
  Match `IrStmt::Exec { func: "let" }` / `func: "exec"` with a single
  `;`-separated init/cond/inc string arg (c-style for) — reuse the
  existing `parse_arithmetic_assignment` / arith AST machinery in
  `src/parser/commands.rs` (it already parses `i=0; i<3; i++`-style
  text). Emit `Assign`/`While`/`Arith` nodes (all renderers have them).
  Do NOT touch the parser or IR enums — the transform runs on the
  current shapes (additive, no regression risk: nothing else consumes
  these blob execs except the estree runtime's cstyleForSync, which the
  transform's While output also serves).
- Register in `transforms.rs`; `cargo test --lib` green; `./fail-estree`
  stays at the trusted baseline (estree's While path already exists).
- The sh worker then renders the structured forms portably (its domain).

## FAILING-CASE
```sh
x=1
let x+=1
echo $x
for ((i=0; i<3; i++)); do echo $i; done
```
`--shir-in-sh` today emits the `_num`/`[ "$(($( _num "x" )+=1))" -ne 0 ]`
form (x never becomes 2) and cannot emit the loop as a POSIX while.
Expected after the transform: `x=$((x + 1)); printf '%s\n' "$x"` and a
`while [ i -lt 3 ]; do ... i=$((i + 1)); done` that prints 2 then 0 1 2
under dash/busybox/BSD sh alike.

## OUTCOME: implemented — src/transforms/arith_forms.rs registered in transforms.rs (DEBASHC_TRANSFORMS-gated like seq_range_for): exec("let", [...]) → one Assign per expr with Arith(Assign{op}) (let x+=1 → x=$((x+1)) — verified the failing case emits structured Assign+Arith nodes, no more exec-string blob); c-style-for header blobs → ForInit with structured Assign/Arith; bare ((expr)) conditions → the test machinery's form. Perl backend already renders ArithAst::Assign (ir.rs arith_ast_to_perl); sh renderer arm landed in backends/sh (6611). Estree corpus 546/546.
