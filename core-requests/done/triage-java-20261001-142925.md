# triage: java backend can't render what the c-sh-go frontend emits

## NEED
The java renderer must handle this A1 (the estree reference renders it and
matches native).

## FAILING-CASE
frontend c-sh-go, example t71_multi_out.c (cross-product pair).

## EVIDENCE
render failed: otranspiler: arrow statement not representable as text: Expr(Call { func: "fnCall", args: [Str("getdim", DoubleQuoted), Array([])] })

## OUTCOME: rejected
Not a shared-core defect — belongs to the java backend renderer, which is outside my
scope (`src/java.rs` is a backend file, actively edited by its worker).

Re-verified this round rather than taking the filed verdict on faith. Emitting the A1 the
way `harness/triage.sh` does (`c-sh-go --shir --raw`, then `outparam_to_returns.py`) and
running the estree REFERENCE confirms the premise holds: for **t71_multi_out.c** the reference matches
native byte-for-byte, so the A1 is valid and estree/shir/ir are not implicated. The
difference is entirely in the java render.

Concrete symptom: the java renderer **refuses** (rc=1) rather than miscompiling:

    otranspiler: arrow statement not representable as text:
    Expr(Call { func: "fnCall", args: [Str("getdim", DoubleQuoted), Array([])] })

`getdim` is a CALLBACK invoked with an EMPTY argument list — the classic C out-param
callback idiom. The estree reference lowers it fine, so the A1 is valid; java_backend
has no rendering for a `fnCall` whose arg array is empty. Backend-owned.
