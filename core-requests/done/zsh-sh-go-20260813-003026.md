# zsh-sh-go: shell `continue` never lowers to the A1 `Continue` node — no frontend can cover it

Same shared-core gap as `core-requests/posix-sh-go-20260813-002308.md`
(which explicitly names zsh-sh-go among the affected frontends); this
request files it for the zsh-sh-go ledger so the coverage hook skips it
while pending. The core change is identical — the estree worker can
implement both under the 002308 request; this file exists to pin the
zsh-side ledger entry.

## NEED

The shared core's shell frontend must lower the `continue` builtin to the
A1 `IrStmt::Continue` node (statement position) so `debashc --shir FILE
--raw` can actually emit `"type": "Continue"`. Today the shell frontend
path **never** constructs `IrStmt::Continue`: `stmt_for_command` at
src/shir.rs:5282 lowers `Command::Continue(_)` to
`IrStmt::Expr(call("continue", vec![]))`, and the expression path
`command_to_ir` at src/shir.rs:6049 does the same. The only
`IrStmt::Continue` constructions in the tree are `shir_passes/strip.rs`
(C-style ForInit→while pass, unreachable from zsh/POSIX input, which has
no C-style `for`) and the deserializer `shir_json_in.rs:414` — so no
`--shir` output for any zsh program contains a Continue node, and the
A1-node coverage proxy (`frontends/coverage/coverage-gap.sh zsh-sh-go`)
reports `A1 node Continue` for zsh-sh-go.

The node itself is complete end-to-end — no contract change needed:
- schema: `frontends/shir-contract/schema.json` stmts.Continue
  (`{"type":"Continue"}`, type required, no other fields)
- serializer: `src/shir_json.rs:158` —
  `IrStmt::Continue => json!({ "type": "Continue", "runs": stmt_provably_runs(s) })`
- deserializer: `src/shir_json_in.rs:414` — `"Continue" => IrStmt::Continue`
- estree renderer: `src/shir.rs:13232` — renders to `sh2.continue()`,
  byte-identical to the legacy `Expr(Call "continue")` arm at
  src/shir.rs:13235 — the estree output is unchanged either way

## WHY

zsh-sh-go gate is GREEN but `frontends/coverage/coverage-gap.sh
zsh-sh-go` reports `A1 node Continue` uncovered. The existing example
`frontends/zsh-sh-go/testdata/t82_continue.zsh` (gate green, commit
`5b1aa66`) emits only `Expr`/`Call`/`Str`/`Array`/`Arith` — byte-equal to
the core, gate green, and the gap detector **still** reports Continue,
because the example cannot contain a Continue node: the frontend is
byte-locked to `debashc --shir --raw`, which never emits one. Probing
every form:

```
continue            -> Expr(Call "continue")    # t82, byte-equal
continue 2          -> Expr(Call "continue")    # level DROPPED by the current lowering
```

This is NOT a by-design subset refusal: the zsh-sh-go frontend parses the
`continue` keyword fine (t82_continue.zsh passes the gate — the keyword
is expressed, just as a builtin call; FRONTEND.md excludes nothing
here). What is inexpressible is the **Continue emission shape**, which
only the shared core's lowering can provide. Same situation as the
pending `A1 node Declare` request
(`core-requests/posix-sh-go-20260813-001245.md`, ledgered in
`frontends/coverage/core-pending-zsh-sh-go.txt`): the node is complete
end-to-end, but the shell lowering never emits it. Escalating per the
core-requests channel (the estree worker is the single owner of
src/shir.rs).

## MINIMAL-CORE-CHANGE

Scope: `src/shir.rs` only — the `Command::Continue(_)` arm of
`stmt_for_command` (src/shir.rs:5282).

When the statement is a bare `continue` (no level argument), emit the
first-class node instead of the builtin call:

```rust
Command::Continue(None) => IrStmt::Continue,
Command::Continue(Some(_)) => IrStmt::Expr(call("continue", vec![])),
```

Concrete mapping:
- `continue` → `{"type":"Continue","runs":…}`
- `continue 2` → stays `Expr(Call "continue")` — the A1 Continue node has
  no level field, so a leveled continue would LOSE semantics; keep the
  legacy call shape for it (same "keep unchanged" discipline as the
  Declare request's flag forms)

Keep unchanged:
- the expression-context arm `command_to_ir` (src/shir.rs:6049) —
  `continue` inside `&&`/`||`/`!` chains is an operand, not a statement,
  and must stay `call("continue", …)`
- the estree side needs no change: the first-class arm (shir.rs:13232)
  and the legacy-call arm (shir.rs:13235) both render `sh2.continue()` —
  byte-identical estree output, so no corpus regression
- serializer/deserializer/schema already exist

Corpus constraint (the estree worker mediates): this changes `--shir`
output for every shell file containing a bare `continue` (t82-style).
Executed-stdout semantics are preserved (both shapes run the same
runtime `sh2.continue()`), and the estree corpus output is byte-identical
as noted. Frontend byte-equality gates (zsh-sh-go, posix-sh-go, and the
other shell frontends) will show `DIFF` until each frontend mirrors the
new shape in the same window — the established pattern from
`core-requests/done/posix-sh-go-20260806-174619.md`; the zsh-sh-go mirror
is `lowering.go`'s `stmtForCommand` continue arm (currently always the
builtin call, mirroring the core).

## FAILING-CASE

Minimal zsh-sh-go (zsh) snippet — the coverage example this request
unblocks (currently uncreatable):

```zsh
i=0
while (( i < 3 )); do
    ((i++))
    if (( i == 2 )); then
        continue
    fi
    echo $i
done
```

Today `debashc --shir failing.zsh --raw` emits — and the zsh-sh-go
frontend must byte-match — no Continue anywhere: the `continue` lowers to
`{"type":"Expr","expr":{"type":"Call","func":"continue","args":[],…}}`.
After the change the A1 must contain (the estree renderer already
consumes this shape):

```json
{"type":"Continue","runs":…}
```

Repro of the gap itself (no core change needed to see it):
`bash frontends/coverage/coverage-gap.sh zsh-sh-go` →
`A1 node Continue` (second line of the actionable list), with
`frontends/zsh-sh-go/testdata/t82_continue.zsh` present and the gate
green — the example cannot cover the node until this request lands.
