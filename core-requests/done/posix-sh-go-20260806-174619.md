# posix-sh-go: array-literal unquoted expansions still never field-split — gate red on t63_array_split.sh

## NEED
`arr=($x)` (unquoted expansion inside an array literal) must carry the
A1 `split` marker so the ESTree backend field-splits the element like
bash. Today the core emits `setArray("arr", [Str("$x")])` — the RAW
source text, unexpanded — and the ESTree lowering evaluates it as a
template literal WITHOUT splitting: `x="a b"; arr=($x)` yields one
element `"a b"` instead of two (`"a"`, `"b"`).

This is a RE-FILE of `core-requests/done/split-array-literal-20260806.md`
(mediated out without implementation by d63b57a — the core still emits
raw text). The posix-sh-go gate is now blocked on it: A1 byte-equality
is 67/67, but the executed-stdout gate fails 1/67.

## WHY
`frontends/posix-sh-go` gate (`make test`, run via the loop):
- Part 1 (A1 byte-equality vs `debashc --shir --raw`): **67/67 green** —
  the frontend emits byte-identical JSON to the core, including the raw
  `"$x"` setArray element. The frontend CANNOT deviate (byte-oracle).
- Part 2 (harness/frontend-stdout.sh: frontend A1 →
  `debashc --shir-in-estree` → node harness/estree-runner.mjs vs native
  bash): **66/67** — `t63_array_split.sh` fails:
  ```
  x="a b"
  arr=($x)
  echo "n=${#arr[@]}"
  echo "${arr[0]}|${arr[1]}"
  ```
  bash: `n=2` / `a|b`. Core A1→ESTree→runner pipeline: `n=1` / `a b|`.
  Verified the CORE's own pipeline produces the identical wrong output
  from the core's own A1 — a pure shared-core gap, not a frontend gap.

Root cause (probe-verified, unchanged since the original request):
`parser/assignments.rs: parse_array_elements` returns `Vec<String>` of
RAW token text (quotes stripped for quoted strings, everything else raw
`$x`), so the quoted/unquoted distinction is destroyed before
`ast_to_ir` — `Word::Array` lowering (shir.rs ~4004/4034/4059) maps each
element via `st(e)` → `IrExpr::Str(e)`. On the ESTree side,
`array_elt_to_estree` (shir.rs:17286) calls `test_str_to_estree` on the
Str, which lifts embedded `$var` references into a template literal
(evaluates, never splits).

## MINIMAL-CORE-CHANGE
(as specified in `core-requests/done/split-array-literal-20260806.md`,
with current line pointers; the A1 `split` Call already round-trips —
precedent: `0c44b56` carried the split marker for exec-args/for-items,
and `for_item_ir`'s `Word::Variable` → `split(getVar(..))` arm at
shir.rs:4991 is the exact pattern to reuse)

1. `parser/assignments.rs parse_array_elements` (~line 74): parse each
   element as a real `Word` (parse_word_list-style loop; Space/Tab/
   Newline separate; stop at ParenClose; Newline must be treated as
   whitespace, unlike parse_word_list).
2. `Word::Array(String, Vec<Word>, Option<()>)` + constructor + Display.
3. `ast_to_ir` `Word::Array` sites (shir.rs 4004/4034/4038/4059/4063):
   `elements.iter().map(arg_word_ir)` — `arg_word_ir` already lowers
   unquoted `Word::Variable` → `split(getVar(..))`; quoted
   interpolations stay single-field. Do NOT use `word_ir_quoted`
   (array elements field-split like exec args, not like assignment RHS).
   Then `arr=($x)` emits
   `setArray("arr", [Call{split(getVar("x"))}])`.
4. Perl-generator consumers of `Word::Array` elements must render
   LITERAL elements byte-identically to today (perl corpus gate).
5. Runtime `setArray`/`setArrayAppend` already splice array-valued
   elements (probe-verified) — no runner change needed.

Note the contract-side consequence: `arr=("$x")` and `arr=($x)` are
currently BYTE-IDENTICAL in A1 (both `Str("$x")`); after the change they
diverge (quoted → `Interpolate`/bare getVar element, unquoted → split),
which is the intended distinction.

```
→ n=1 / a,b|   (expected n=2 / a|b)
```

The emitted ESTree element is a NATIVE JS ARRAY expression
(`String(x).split(/\s+/).filter(w => w.length > 0)` — the `split` arm
of expr_to_estree inlines it), but `harness/sh2-namespace.mjs`
`setArray` (line 1713) does `expandWord(this, String(e))` on it:
`String(["a","b"])` === `"a,b"` → ONE element `"a,b"`. No splicing
exists anywhere in setArray/setArrayAppend.

ADD to MINIMAL-CORE-CHANGE, after step 3:

6. `harness/sh2-namespace.mjs` `setArray` (1713) and `setArrayAppend`
   (1766): splice JS-array elements before the expandWord path —

   element is already a final string). Mirror the same change in
   `harness/sh2-trace.mjs` setArray (1679) / setArrayAppend (1730).
   The `$@`/backtick/`$(` heuristics below stay untouched (they
   operate on string elements).
