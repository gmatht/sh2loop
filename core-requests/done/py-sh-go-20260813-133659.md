# py-sh-go: A1 contract has no Try node — Python try/except is inexpressible

## NEED
The A1 contract must provide a `Try` statement node so the py-sh-go
frontend can lower Python `try`/`except`/`else`/`finally` (grammars-v4
Python3 rule `try_stmt`) and the ESTree backend can render it as a JS
try/catch/finally. Proposed shape (serde_json BTreeMap-sorted keys,
mirroring the existing `If`/`While` node style):

```json
{
  "type": "Try",
  "body":     [<stmt>...],              // the guarded suite
  "excepts":  [{ "type": "TryExcept",
                 "match": <expr|null>,  // except clause test (None = bare except)
                 "as":    <string|null>,// optional binding name
                 "body":  [<stmt>...] }...],
  "else":     [<stmt>...],              // optional, [] when absent
  "finally":  [<stmt>...]               // optional, [] when absent
}
```

## WHY
The coverage hook (rules-gap.sh) reports `try_stmt` as a parser rule no
testdata example exercises. The reason no example exists: the frontend
cannot express it. `parseStmt` in frontends/py-sh-go/main.go has no
`try` case (only import/global/pass/print/def/if/while/for/return/with),
so a `try:` line falls into expression parsing and fails loudly:

    $ ./py-sh-go --shir /tmp/trytest.py --raw
    py-sh-go: parse: unexpected token ":"
    exit=2

This is NOT a documented by-design subset refusal (no FRONTEND.md for
py-sh-go; no exclusion list anywhere in the frontend). The frontend's
pattern is to lower every supported Python construct onto its ShIR
counterpart (if→If, while→While, for→For, def→Function, with→With) —
but exception handling has NO ShIR counterpart: the stmt vocabulary of
the A1 contract (src/shir_json.rs serialization, src/shir_json_in.rs
deserialization, frontends/shir-contract/schema.json "stmts" map) has no
Try node, because bash has no try/catch and the core never needed one.
`try/except` semantics cannot be reproduced by any combination of the
existing nodes (If/While/Exec/Pipeline/... cannot catch a runtime
exception), so the executed-stdout oracle (native python3 vs the
transpiled ESTree run) can never pass for a try example. The frontend
could express it if shIR had node X — its keyword dispatch in parseStmt
and the existing parseBody/parseSuite indent machinery would need only
a small addition.

## MINIMAL-CORE-CHANGE
1. src/ir.rs: add `Try { body: Vec<IrStmt>, excepts: Vec<TryExcept>,
   else_body: Vec<IrStmt>, finally_body: Vec<IrStmt> }` to `IrStmt`
   (with a `TryExcept { match_expr: Option<IrExpr>, as_name:
   Option<String>, body: Vec<IrStmt> }` struct), plus the mirroring
   statement enum in src/shir.rs.
2. src/shir_json.rs / src/shir_json_in.rs: serialize/deserialize the
   new stmts type `"Try"` with the fields above (empty arrays for absent
   else/finally, null match/as for bare except), so the A1-ingress
   oracle (`debashc --shir-in-estree`) accepts frontend emits.
3. src/estree.rs: render `Try` to a JS `try { ... } catch (e) { ... }
   finally { ... }` block; the except arm with `match` compiles to
   `catch (e) { if (e instanceof <match>) ... }` or a rethrow fallback,
   `as` binds the caught value to a runtime var (sh2.setVar), a bare
   except compiles to `catch (e) { ... }`, `else` to a post-try block
   (JS semantics: runs only when no exception propagated), `finally`
   to the JS finally clause. The thrown-value convention is the
   runtime's choice; a reasonable default is throwing `new Error(...)`
   with the string message, matching how the ESTree runtime already
   surfaces errors.
4. frontends/shir-contract/schema.json: add the `Try` entry to the
   "stmts" map (workspace-side, keeps check_schema.py green) — the
   estree worker's fix surface per core-requests/README.md is the
   shared core + harness/*; schema.json is updated by whoever lands the
   node.

The frontend side (parseStmt `try` case → emit the node) is py-sh-go's
own fix and lands after the contract has the node; the coverage worker
retries the gap automatically once this request completes
(core-pending-py-sh-go.txt pruning).

## FAILING-CASE
Minimal Python program (python3 runs it fine, prints "ok"):

```python
try:
    print("in try")
except:
    print("caught")
print("ok")
```

Current behavior: `./py-sh-go --shir` fails with
`py-sh-go: parse: unexpected token ":"` (exit 2), so no testdata
example can cover `try_stmt` and the A1 node is missing end-to-end
(frontend emit → ingress acceptance → ESTree run vs native python3
stdout).

## OUTCOME: implemented
Landed in sh2perl f25fc79 (workspace gitlink bump follows): `IrStmt::Try`
(+ `TryExcept`) in src/ir.rs, `"Try"` serialization (src/shir_json.rs) +
strict ingress (src/shir_json_in.rs, KNOWN_STMT + parse arm, byte-identical
round-trip test), ESTree rendering in src/shir.rs `stmt_to_estree` with
standard `TryStatement`/`CatchClause`/`ThrowStatement` nodes in
src/estree.rs (all Stmt passes recurse into them), and Try arms in every
IR walker/analysis/backend. Semantics notes for py-sh-go: (1) the except
ladder uses `e instanceof <match>` — a `match` expr must evaluate to a
constructor; (2) `as` binds via `sh2.setVar(name, e)` — the runtime store
stringifies, so the bound value reads back as a string; (3) the catch
first rethrows non-Error values (`!(e instanceof Error)`) so runtime
BREAK/CONTINUE/RETURN control signals pass through a Try untouched; (4)
`else` lowers to a post-try completion-flag block — Python's else runs
only when the try body completed WITHOUT raising (a handled exception
skips it) and else-body exceptions are NOT caught by this statement's
arms; (5) the estree renderer refuses `IrStmt::Output` (Perl-only) —
lower `print` to the exec/echo shape the shell frontend emits. Gates:
estree 521/521 (0 failed), perl 319 (unchanged), cargo test --lib 246
(244 + 2 new), check_ast 1 pre-existing failure unchanged.
