# c-sh-go: drop_dead_top_decls drops LIVE `let x = 0` — the declaration under test shadows its own binding

## NEED

Fix the self-shadowing bug in `drop_dead_top_decls` (src/estree.rs, added in
b907552 "estree: eliminate dead top-level declarations (for-loop
shadowing)"). The liveness walk must not treat the leading top-level
declaration being analyzed as a shadowing re-declaration of itself.

Also: commit the pending working-tree state — committed b907552 alone does
NOT compile (`src/cfront.rs:992` constructs `IrProgram` without the
`var_nospace` field; the working tree carries the `var_nospace: vec![]` init
plus the grepMatches WIP). A fresh checkout of the gitlink is currently
unbuildable.

## WHY

The c-sh-go executed-stdout gate regressed 18/31 (all "stdout mismatch",
transpiled output EMPTY): e.g. t02_assign.c (`int x = 42; printf("x=%d\n", x);`)
— the emitted JS is

```js
x = 42;
process.stdout.write(`x=${parseInt(x, 10)||0}\n`);
```

with NO `let x = 0` declaration → `ReferenceError: x is not defined` (ESM
strict) → runner exits 1 → empty stdout. The pre-b907552 binary emitted
`let x = 0; x = 42; ...` and the gate was green (a9430ed).

The same failure hits the core's OWN bash pipeline (`x=42; printf "x=%d\n" "$x"`
through `--shir-in-estree` + estree-runner.mjs fails identically), so this is
not frontend-emission-specific: it is a regression in the shared pass.

Root cause: `stmts_read` (src/estree.rs:4275) flips `sh = true` after ANY
statement that declares the name — INCLUDING the leading declaration itself.
For `let x = 0; x = 42; read x` the walk reads the declaration (init 0, no
read), sets `sh = true`, and every later top-level read of x is then treated
as shadowed → x is "dead" → the declaration is dropped. The flip is only
correct for a re-declaration in a NESTED scope (block / for-init / for-of
left / arrow param), never for the binding under test at top level.

## MINIMAL-CORE-CHANGE

src/estree.rs, the three functions around line 4275:

1. Split `stmts_read` into a top-level entry and a nested variant carrying a
   `top: bool`:

```rust
fn stmts_read(stmts: &[Stmt], name: &str, shadowed: bool) -> bool {
    // top level: the leading declaration under test must not shadow its
    // own binding — reads after `let x = 0` at top level bind to it
    stmts_read_level(stmts, name, shadowed, true)
}
fn stmts_read_level(stmts: &[Stmt], name: &str, shadowed: bool, top: bool) -> bool {
    let mut sh = shadowed;
    for st in stmts {
        if stmt_read(st, name, sh) {
            return true;
        }
        // a `let x` in this block shadows the remainder of it — EXCEPT
        // the top-level declaration being analyzed (only one such decl
        // of a name can exist at top level; nested re-declarations are
        // handled by the recursion below with top=false)
        if stmt_declares(st, name) && !top {
            sh = true;
        }
    }
    false
}
```

2. The two nested recursions in `stmt_read` (the `BlockStatement` and
   `SwitchStatement` arms) call `stmts_read_level(body, name, shadowed, false)`.

Semantics preserved: `let i = 0; for (let i = 1; i <= n; i++) { read i }`
still drops the top-level `let i = 0` (the for's reads are shadowed via the
ForStatement arm's `shadowed || declares`), while `...; echo $i` AFTER the
loop now correctly keeps it (a top-level read after the loop binds to the
top-level decl — this was also broken by the current code despite the commit
message claiming it was handled).
