
## OUTCOME: rejected — the stated build failure does not exist; the worker was parked, not broken

The request's premise is "TRAPPED (build fails repeatedly)". Measured this round, the shared
core builds clean and always did during this incident:

```
$ cargo build --manifest-path otranspilerl/Cargo.toml --bin otranspilerl-cli
    Finished `dev` profile [unoptimized + debuginfo] target(s) in 1m 00s
```
0 errors. There is no compile error to diagnose and no shared-analysis bug to file, so the
escalation is declined rather than answered.

What actually happened, and it is a harness defect in MY scope (setup_backends.sh), now fixed
and committed:

- The `core build FAILED` branch runs a BUILDABILITY PROBE, but invoked `build-lock.sh` with
  no `--timeout`, so it inherited the 1800s backend default against a 900s TOTAL budget. A
  probe queued behind the estree worker's core build could not return before the budget
  expired, so the loop never completed a cycle and could only fall through to `--worker-trapped`.
- `sh2perl/src/zsh_backend.rs` was left in a `DU` (unmerged) index state. No commit can clear
  a `DU` entry without choosing a side, so `git status --porcelain -- src/` was non-empty
  forever — and that is exactly the predicate these workers gate on, so the probe was never
  even reached.

Evidence the park was self-inflicted and is now cleared: 15 consecutive "probe failed" lines
at 60s intervals, then a trap, on a core that compiles in 60s. After the fix the probe returns
rc=0 on the same still-dirty tree and the rust worker logs "core dirty but COMPILES ... retrying
the gate now" — the branch the budget had made unreachable. Regression test:
`harness/test-build-lock-timeout.sh` (verified failing pre-fix, passing post-fix).

NOTE: `harness/build-lock.sh` is bash-only (`[[ ]]`, `$(( ))`) and is invoked WITHOUT an
explicit `bash` at setup_backends.sh:785 and in three other places. It works today only
because those callers are themselves bash scripts. It is not broken, but the four call sites
are one shebang-resolution change away from running it under `/bin/sh` and failing with
"Bad substitution" — which is exactly how it fails when I invoked it from a `sh` shell this
round. Worth an explicit `bash` at each call site; not done this round because no caller is
currently wrong.
