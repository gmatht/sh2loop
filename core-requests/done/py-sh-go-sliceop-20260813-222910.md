# py-sh-go: A1 slice helper has no step field — Python sliceop (extended a[i:j:k] slices) is inexpressible

## NEED
The A1 `param("slice", …)` helper contract must carry an optional **step**
so the py-sh-go frontend can lower Python's extended slice — grammars-v4
Python3 rule `sliceop` (`':' test?`, the optional THIRD part of a
`subscript_`: `test? ':' test? sliceop?`, i.e. `a[1:6:2]` / `a[1:6:]` /
`a[::2]`).

Today the shape is exactly the bash param-slice idiom `${arr[@]:off:len}`:

```json
{ "type": "Call", "func": "param",
  "args": [ {Str "slice"}, {Str name}, {Str start}, {Str len} ] }
```

(emitted by py-sh-go's `subscriptIR` for `a[i:j]` — t66: `param("slice",
"a", "1", "2")`). Proposed: an optional 5th argument, the positive
integer step:

```json
{ "type": "Call", "func": "param",
  "args": [ {Str "slice"}, {Str name}, {Str start}, {Str len}, {Str step} ] }
```

with the 5th arg ABSENT for the existing 4-arg form (all current emits
stay byte-identical). Python `a[i:j:k]` lowers as start=i, len=j-i,
step=k (the frontend already converts Python's end-exclusive `j` to the
shell length `j-i`); the array elements are `i, i+k, i+2k, … < j`.

## WHY
The coverage hook (`rules-gap.sh py-sh-go`) reports `sliceop` as a
Python3 grammar rule no testdata example exercises (verified
2026-08-13: `bash frontends/coverage/rules-gap.sh py-sh-go` lists
`sliceop` among the unexercised rules). The reason no example exists:
the frontend cannot express it — no lowering path. The hand-rolled
parser in frontends/py-sh-go/main.go documents its subscript subset as
`expr | expr:expr | expr: | :expr` (the `[` arm of `parsePrimary`, line
~1283): after the optional `: end` it calls `expectOp("]")` directly, so
a second colon always fails loudly (verified against the built
`./py-sh-go --shir`):

    $ printf 'a = ["a","b","c","d","e","f"]\nprint(" ".join(a[1:6:2]))\n' | ./py-sh-go --shir /dev/stdin --raw
    py-sh-go: parse: expected "]"
    exit=2

This is NOT a documented by-design subset refusal: py-sh-go has no
FRONTEND.md, and the exclusion ledger (frontends/coverage/
refused-py-sh-go.txt) contains no sliceop entry (it ledgered the
match_stmt/`star_named_*`/async/yield/class families; the 2-part slice
is exercised by t37/t66). PARSER_GAPS.md's py-sh-go table categorizes
`sliceop` as category 1 (A1-EXTENSION): "step slices: the shell
param-slice idiom has no step; `a[1:3]` maps (t37/t66), `a[1:3:2]`
can't". Every PART of a stepped slice is already expressible — array
literals (t21/t66), integer literals/arith, `arrayIndex` (t55), the
2-part `param("slice", …)` (t66), `join` (t66) — only the step FIELD on
the slice helper is missing. The bash source language has no stepped
param-slice, so debashc never emits one and the A1 contract (which
mirrors the shell shape) simply lacks the field; the ESTree path can
render it faithfully (JS arrays support arbitrary stepping).

Precedent: identical escalations for the same class of gap —
py-sh-go-comp-if-20260813-215131.md (comprehension filters),
py-sh-go-lambdef-20260813-220859.md (Arrow without params), and
py-sh-go-star-expr-20260813-221910.md (starred expressions): unexercised
grammar rule + parser choke + no refusal-ledger entry + PARSER_GAPS.md
category 1 → A1-EXTENSION request, frontend fix lands after the
contract has the shape.

## MINIMAL-CORE-CHANGE
1. **Contract**: extend the `param("slice", name, start, len)` helper
   with the optional 5th arg `step` (positive-integer string; v1 scope —
   NEGATIVE steps / `a[::-1]` reversal are a follow-up, out of scope
   here). The ingress deserializer (src/shir_json_in.rs, the `Call`
   arm ~line 766) reads args generically, so the shape already ingresses;
   `param` is already PureCpu in src/shir_json.rs `call_purity` (~line
   484) and admitted by the ESTree callee whitelist — no whitelist
   change. All 4-arg emits stay byte-identical.
2. **src/estree.rs**: treat the 5-arg slice like the 4-arg array-valued
   read in the slice-recognizing paths — the array-ref detection (~line
   1287, `op == "slice"` → target is an array ref), the read analysis
   (~line 1348, `op == "slice" && mode == "@"`), `array_len_join`
   (~line 1932), and the native `join(param("slice", …))` lowering
   (~line 3861). Render the step as a filter over the slice window, e.g.
   `arr.slice(start, start+len).filter((_, i) => i % step === 0)`.
3. **harness/sh2-namespace.mjs (runtime)**: `param` case `'slice'` — the
   `${arr[@]:off:len}` array branch (~line 2720) accepts a 5th arg and
   applies `arr.slice(off, off + len).filter((_, i) => i % step === 0)`;
   other slice branches unchanged.
4. **frontends/shir-contract/schema.json**: the workspace-side A1 schema
   gains the optional 5th arg on the `param` slice helper (keeps
   check_schema.py green).

The frontend side (py-sh-go's own fix, lands after the contract has the
shape — same pattern as the star_expr/lambdef requests): `parsePrimary`
`[` arm accepts `test? ':' test? (':' test?)?` (parse the step after the
second colon instead of `expectOp("]")`), and `subscriptIR` emits the
5th arg (`step` from the third part, defaulting to `1` for `a[1:6:]`).
The coverage worker retries the gap automatically once this request
completes (core-pending-py-sh-go.txt re-entry + pruning cycle).

## FAILING-CASE
Minimal Python program (python3 runs it fine):

```python
a = ["a", "b", "c", "d", "e", "f"]
print(" ".join(a[1:6:2]))
```

stdout: `b d f` (indices 1, 3, 5).

Variants that must also work once the shape lands: `a[1:6:]` (empty
step = 1, identical to `a[1:6]`), `a[::2]` (every other element, start
0 / len 6 / step 2).

Current behavior: `./py-sh-go --shir` fails with
`py-sh-go: parse: expected "]"`, exit 2 — so no testdata example can
cover `sliceop`, and the A1 contract is missing the step field
end-to-end (frontend emit → ingress acceptance → ESTree run vs native
python3 stdout).

## OUTCOME: implemented (A1 contract side) — the optional 5th arg step on param("slice", name, start, len[, step]): runtime stepOf + `.filter((_, i) => i % step === 0)` (sh2-namespace.mjs ~2926), estree native lowering a.slice(off, off+len).filter(...), ingress generic (Call args). Verified end-to-end this round: a[1:6:2] → `b d f`, a[::2] → `a c e`, a[1:6:] ≡ a[1:6] → `b c d e f` — all byte-identical to python3. All 4-arg emits unchanged. The frontend emit arm (py-sh-go parsePrimary/subscriptIR) is py-sh-go's own fix per the request.
