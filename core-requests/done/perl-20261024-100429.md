# copy-propagation: a 1–2 char variable name is mistaken for a builtin FLAG

Filed from the perl backend gate (`backend/perl`, worktree
`sh2perl/backends/perl`). A bug in an existing shared analysis, per
`core-requests/README.md` §"Legacy .md requests" — no per-backend workaround
exists, because the pass destroys the information the renderer needs.

## NEED

`copy-propagation` must not fold a variable that a *write builtin* also
writes, when that variable's name is 1–2 characters long. Today it does,
so `unset x` / `read x` are invisible to the single-def scan and a later
read of `x` is replaced by the earlier literal assignment.

## WHY (it is a shared-analysis bug, not a perl gap)

`src/transforms/copy_propagation.rs` `classify_builtin_writes()` — the
argument loop, line ~409:

```rust
        for a in args {
            if let IrExpr::Str(s, _) = a {
                let s = s.trim_start_matches('-');
                if s.is_empty() || (s.chars().all(|c| c.is_ascii_alphabetic()) && s.len() <= 2) {
                    continue; // a flag like -i/-r/-x/-a/-A/-l/-u/-n/-g/-t/-p/-f/-F
                }
                let name = s.split('=').next().unwrap_or(s);
```

The flag test runs on the token *after* the dashes are stripped and never
checks that a dash was ever there. So a bare operand that happens to be
1–2 ASCII letters — `x`, `n`, `ab`, `i` — is discarded as if it were a
flag. For `unset x` the only operand *is* the variable, so the write is
lost and `counts["x"]` stays at 1 (the earlier assignment), which is
exactly the single-def precondition `collect_defs()` folds on.

This is target-independent: the fold happens in the core A1 emitter, so
every backend renders the wrong program. Nothing downstream can recover
it — by the time the renderer sees the shIR, the read is already a
literal and the fact that it used to be `$x` is gone.

## MINIMAL-CORE-CHANGE

Track whether the token actually started with a dash and require that for
the flag test (nothing else changes; over-counting a write is always
sound here — it only refuses a fold):

```rust
         for a in args {
-            if let IrExpr::Str(s, _) = a {
-                let s = s.trim_start_matches('-');
-                if s.is_empty() || (s.chars().all(|c| c.is_ascii_alphabetic()) && s.len() <= 2) {
+            if let IrExpr::Str(raw, _) = a {
+                let is_flag = raw.starts_with('-') || raw.starts_with('+');
+                let s = raw.trim_start_matches(['-', '+']);
+                if s.is_empty()
+                    || (is_flag
+                        && s.chars().all(|c| c.is_ascii_alphabetic())
+                        && s.len() <= 2)
+                {
                     continue; // a flag like -i/-r/-x/-a/-A/-l/-u/-n/-g/-t/-p/-f/-F
                 }
```

Behaviour delta is exactly one class: a *bare* 1–2 letter name is now
counted as a write (correct — it is the operand). Every dashed token
behaves as before (`-i` → skipped, `-r` → skipped), so `declare -i n=42`,
`export -f foo`, `read -r line` keep their current verdicts.

Note `unset x` arrives as `IrStmt::Expr(Call{func:"builtin", args:[Str("unset"), Array([Str("x")])]})`,
which `count_expr_assigns()` already routes to `classify_builtin_writes`
(line ~514) — the routing is fine; only the flag test is wrong.

## FAILING-CASE

Corpus file `frontends/posix-sh-go/testdata/t70_unset.sh` (the perl gate's
only failure: `642/650 corpus render OK, 1 fail (… 1 equiv …)`):

```sh
x=5
unset x
echo "${x:-gone}"
```

bash → `gone`. Perl gate → `5`. The shIR emitted by
`otranspilerl-cli --target shir` already carries the wrong value:

```json
{"stmts":[ … {"expr":{"style":"DoubleQuoted","type":"Str","value":"5"},
   "targets":[{"indices":[],"sigil":null,"var":"x"}],"type":"Assign"},
  { … unset … },
  {"expr":{"args":[{"value":"echo"},
     {"elements":[{"value":"5"}],"type":"Array"}],"func":"builtin"…}}]}
```

Length-dependence confirms the diagnosis (`bash` prints `gone` for all
three; only len ≥ 3 survives the scan):

| probe | shIR echo operand | perl render |
|---|---|---|
| `x=5; unset x; echo "${x:-gone}"` | `"5"` (folded) | `5` |
| `ab=5; unset ab; echo "${ab:-gone}"` | `"5"` (folded) | `5` |
| `foo=5; unset foo; echo "${foo:-gone}"` | `param(":-","foo","gone")` | `gone` |

Second instance, same root cause, NOT in the corpus (latent):
`x=5; read x < in.txt; echo "${x:-gone}"` — bash prints the file's first
line (`hello`), shIR folds the echo operand to `"5"`.

Third, worst shape (also latent): the fold can make a *correct* program
print a stale value after a `read`/`unset` that a conditional guards.

## VERIFIED FIX EVIDENCE

Rebuilding is not needed to prove the pass is the cause — disable it with
the runtime gate (all registered transforms except `copy-propagation`):

```
SH2_TRANSFORMS=<every name but copy-propagation> otranspilerl-cli --target shir t70_unset.sh
  → echo operand is param(":-","x","gone")   (was "5")
perl render + run under an empty scratch CWD → OUTPUT MATCHES bash (`gone`), rc 0
```

Expected gate result after the core fix: `643/650, 0 fail` (the remaining
7 are `bash -n` skips, unchanged).

## OUTCOME: implemented

Landed in `sh2perl/src/transforms/copy_propagation.rs::classify_builtin_writes`: a word is treated as a command-line flag only when it actually carried a leading `-`, so a bare 1-2 letter NAME (`unset x`, `read ab`, `local n`) is recorded as a write and copy-propagation refuses the stale fold. Pinned by unit tests `unset_invalidates_single_def`, `read_invalidates_single_def`, `dashed_flag_is_still_skipped`, `folds_without_unset`.

Verification: `./fail-estree` -> PERL 562/562 passed, ESTREE 561/562. The single estree failure (`grep_p.sh`, "non-sh2 callee: min") reproduces identically with `SH2_TRANSFORMS=none` and the file contains no store-writing builtin, so it is pre-existing/WIP and unrelated. `cargo test --lib`: the 27 failures are identical before and after this hunk (pre-existing WIP); the 4 new tests pass.

Note: the fix landed in the live working tree, which is the tree `setup_backends.sh` and all gates build `otranspilerl-cli` from. The same file carries the in-flight `fold_param_const` WIP (+~640 uncommitted lines) plus 57 other dirty `src/` files, so a scoped commit is not isolable this round.
