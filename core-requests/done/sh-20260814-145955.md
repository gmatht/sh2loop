# sh: `--shir` on invalid-UTF-8 input silently renders the FILE PATH as the script

## NEED

`debashc --shir <file>` must not treat the file's path as shell source when
the file contains non-UTF-8 bytes. Either parse the file lossily
(byte-preserving) or fail cleanly with empty stdout (the A1 ingestible
empty-Program shape) — never emit a program whose content is the filename.

## WHY

The sh backend gate renders every corpus example through
`debashc --shir <f> --raw` → `debashc --shir-in-sh -`. For
`examples/utf8-non-utf8-content.sh` (a 3-line script whose `echo "acc�nt"`
contains a raw ISO-8859-1 byte 0xE9), the core emits a program containing a
single `exec` whose argv[0] is the literal path
`/home/llm/sh2loop/sh2perl/examples/utf8-non-utf8-content.sh`:

```json
{"expr": {"args": [{"style": "DoubleQuoted", "type": "Str",
  "value": "/home/llm/sh2loop/sh2perl/examples/utf8-non-utf8-content.sh"},
  {"elements": [], "type": "Array"}], "func": "exec", "purity": "Spawn",
  "type": "Call"}, "type": "Expr"}
```

That makes the sh render a bare path line: dash fails it with rc=126
(permission denied, executing the file) vs bash rc=0, the rendered text
contains the path (false-positives the sh2.* stub grep via the "sh2loop"
substring), and the file fails the gate — for every backend, not just sh.

Root cause: cli/src/lib.rs's `--shir` file arm uses
`std::fs::read_to_string(input)`; on invalid UTF-8 it returns Err and the
code falls back to `cli_commands::export_shir(input, raw)` — i.e. it
parses the *filename string* as the script. (A copy of the file with the
byte replaced by valid UTF-8 parses fine: 3 exec stmts.)

## MINIMAL-CORE-CHANGE

In cli/src/lib.rs `--shir` (and ideally the `--estree`/`--perl` file arms
with the same fallback): replace

```rust
match fs::read_to_string(input) {
    Ok(content) => cli_commands::export_shir(&content, raw),
    Err(_) => cli_commands::export_shir(input, raw),
}
```

with a bytes read + `String::from_utf8_lossy` (byte-preserving parse —
bash itself is byte-agnostic), or at minimum `Err(_)` → the canonical
empty-Program JSON (`shir_to_shir_json(&ast_to_ir(&[]))`) instead of
`export_shir(input, raw)`. The "file-like input tries a file read first
and falls back to direct string" feature must keep working for genuinely
string inputs (no `.sh`, no spaces — but a *path* whose read fails with
invalid UTF-8 must not be re-parsed as content).

## FAILING-CASE

```sh
printf '#!/bin/sh\necho "Test non-UTF-8:"\necho "acc\xe9nt"\necho "exit: $?"\n' > /tmp/u.sh
debashc --shir /tmp/u.sh --raw   # emits exec of "/tmp/u.sh", not 3 echoes
```

Expected: the same 3-stmt program the valid-UTF-8 copy produces, or empty
stdout (gate skip) — not a program whose argv[0] is the file path.

## OUTCOME: implemented — landed in 0e21666 (fs::read + String::from_utf8_lossy on
the --shir file arm; absent files keep the string-input fallback). Verified this
round: the FAILING-CASE file (/tmp/u.sh, raw 0xE9 byte) emits the 3-stmt program
via --shir --raw and renders 3 echo stmts through --shir-in-sh — never an exec
of the file path.
