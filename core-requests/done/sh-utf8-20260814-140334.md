# sh: invalid-UTF8 source breaks the whole parse (utf8-non-utf8-content red)

## NEED
The parser must tolerate a non-UTF8 byte in the source (an ISO-8859-1
character) instead of degrading to a whole-file fallback.

## WHY
`utf8-non-utf8-content.sh` contains one byte 0xE9 ("accént"). The core
emits a single stmt `exec(Str("<abs path of the file>"))` — the
source-not-inlined fallback — which the sh backend faithfully renders;
running it tries to execute the (non-executable) source file
(rc=126), and the stub gate additionally flags the path's "sh2" bytes.
The gate is RED on this file; it also shows up in the chimera fails.

## MINIMAL-CORE-CHANGE
In the parser/lexer: when a byte is invalid UTF-8, treat it as a
literal character (or lossily decode) rather than aborting the parse —
the file's actual content is plain `echo` lines that parse fine once
the byte is tolerated. (Check where the fallback
`exec(Str(source-path))` is emitted for unparseable input and make it
only fire for genuinely unparseable programs.)

## FAILING-CASE
```sh
#!/bin/sh
# File with ISO-8859-1 byte
echo "Test non-UTF-8:"
echo "acc\xe9nt"

echo "exit: $?"
```
`debashc --shir file.sh --raw` currently emits one exec-of-itself
stmt; bash runs the file and prints the lines.

## ADDENDUM (sh worker, 2026-08-14): precise fallback location + contract caveat

The fallback is NOT in the parser — the parser never sees the file. It is
the CLI read path:

- `cli/src/lib.rs`, the `--shir` arm: `input.contains(".sh")` →
  `fs::read_to_string(input)`; on Err (invalid UTF-8) it calls
  `cli_commands::export_shir(input, raw)` with the **filename string as
  shell source** — that's where `exec(Str("<abs path>"))` comes from
  (the filename parses as a bare command word). Same pattern in the
  `--shir-raw` arm and `--shir-in-estree`/`--shir-in-perl` inputs.
  MINIMAL fix: on read failure, `fs::read(bytes)` + 
  `String::from_utf8_lossy(&bytes)` and parse the lossy content (the
  file is plain `echo` lines; the 0xE9 byte becomes U+FFFD and parses
  fine inside a double-quoted word).

- CONTRACT CAVEAT (why lossy-read alone won't turn the file green):
  bash prints the raw byte 0xE9; the lossy shIR carries U+FFFD; the
  render (a UTF-8 String) prints 0xEF 0xBF 0xBD → the gate's byte-exact
  stdout diff still fails. The A1 JSON contract cannot round-trip a raw
  non-UTF-8 byte. Options for the estree worker to weigh: (a) exclude
  non-UTF-8 source files from the equivalence corpus (the chimera gate
  already excludes original-rc!=0 the same way), or (b) a documented
  byte-escape convention (e.g. Latin-1 range → `\u00xx` + a renderer
  side `printf '\NNN'` lowering) — larger contract change, only worth
  it if non-UTF-8 corpus coverage is wanted.

## OUTCOME: implemented — the lossy-read fix landed in the shared core (0e21666: cli --shir/--shir-raw fs::read + from_utf8_lossy, no more exec-of-the-source-path fallback) and the harness handles the raw byte (estree-runner binary-chunk stdout flush); verified this round: utf8-non-utf8-content.sh PASSES both the perl and estree gates (1/1 each), estree corpus 546/546.
