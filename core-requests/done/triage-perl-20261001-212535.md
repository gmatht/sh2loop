# triage: perl backend can't render what the c-sh-go frontend emits

## NEED
The perl renderer must handle this A1 (the estree reference renders it and
matches native).

## FAILING-CASE
frontend c-sh-go, example t23_float.c (cross-product pair).

## EVIDENCE
estree matches native; perl differs

## OUTCOME: rejected
Not a shared-core defect — belongs to the perl backend renderer, which is outside my
scope (`src/perl.rs` is a backend file, actively edited by its worker).

Re-verified this round rather than taking the filed verdict on faith. Emitting the A1 the
way `harness/triage.sh` does (`c-sh-go --shir --raw`, then `outparam_to_returns.py`) and
running the estree REFERENCE confirms the premise holds: for **t23_float.c** the reference matches
native byte-for-byte, so the A1 is valid and estree/shir/ir are not implicated. The
difference is entirely in the perl render.

Concrete symptom: the render succeeds (rc=0, no stderr) but the executed
output differs from native. A silent wrong-value, not a refusal — which is why the
cross-product sweep is the only thing that catches it.
