# fish-sh-go: A1→ESTree emission is nondeterministic — lifted-var declaration order from HashSet iteration

## NEED

Byte-stable A1→ESTree output. For identical A1 shIR input, `debashc
--shir-in-estree` must emit the same ESTree JSON on every invocation.
Today the top-level lifted-variable declarations (`let x = 0` /
`let x = ""` / `let __fn_f = null;`) appear in a random order that
flips per process.

## WHY

The fish-sh-go gate failed on 2026-08-06T18:04:27 with
`FAIL t40_nested_loop.fish (A1 -> ESTree conversion)` — the only test
whose A1 program lifts TWO loop variables (nested `for`). Root cause is
twofold:

1. **Race (primary, now hardened in harness/):** the shared debashc
   binary was concurrently relinked by the estree worker's `cargo
   build` at 18:04:22, mid-gate-run; the t40 invocation exec'd a
   truncated/invalid binary and exited nonzero. Every other test
   (phase 1 + 101 phase-2 invocations) passed, and the same A1 input
   has passed 1800/1800 invocations since. `harness/frontend-stdout.sh`
   and the fish-sh-go Makefile now retry once after 3s to outlive a
   concurrent relink.
2. **Core defect (this request):** on the same path, the emitted
   declaration order is nondeterministic. `LIFTED_NUMERIC` /
   `LIFTED_STRING` are `static Mutex<Option<HashSet<String>>>`
   (src/shir.rs:22,25) and are iterated directly when emitting the
   program-top declarations (src/shir.rs ~7768, ~7780); `direct_fns`
   from `fn_call_sync_set` (also HashSet-backed, src/shir.rs:7719) is
   iterated the same way (~7808). For t40's A1 (outer For var `i`,
   inner For var `j`), the output alternates ~50/50 between
   `let i = 0; let j = 0;` and `let j = 0; let i = 0;` (verified 70/70
   invocations across two binary builds: 10/20/20/20 splits). Both
   orders execute correctly under the runner today, but the output is
   not byte-reproducible — violating the workspace's byte-identical
   contract — and any future pass that assumes declaration order
   (e.g. the numeric-range ForStatement lowering around the `let i = 0`
   shadowing comment, src/shir.rs:9117) becomes a latent flake.

## MINIMAL-CORE-CHANGE

In src/shir.rs, emit the program-top lifted declarations in a
deterministic order instead of raw HashSet iteration order:

- `LIFTED_NUMERIC` / `LIFTED_STRING`: collect the names into a `Vec`
  and sort before emitting (or switch the statics to `BTreeSet<String>`);
- same treatment for the `direct_fns` loop (line ~7808), which has the
  identical nondeterminism class.

No contract change; no node shape change — only iteration order.
Sorted order is stable across processes and hash seeds.

## FAILING-CASE

`frontends/fish-sh-go/testdata/t40_nested_loop.fish`:

```fish
for i in 1 2
    for j in 1 2
        echo $i$j
    end
end
```

Reproduce:

```sh
cd frontends/fish-sh-go
./fish-sh-go --shir testdata/t40_nested_loop.fish --raw > /tmp/t40.json
for i in $(seq 1 20); do \
  ../../sh2perl/target/debug/debashc --shir-in-estree /tmp/t40.json; echo; \
done | grep -o '"name":"[ij]"' | paste - - | sort | uniq -c
```

Expected today: both `i j` and `j i` declaration orders appear
(roughly 50/50). Expected after fix: only one order, every run.
