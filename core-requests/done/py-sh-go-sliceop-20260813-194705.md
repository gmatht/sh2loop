# py-sh-go: A1 contract has no slice-step shape — Python sliceop is inexpressible

## NEED
The A1 expr vocabulary must express Python's **slice step** (grammars-v4
Python3 rule `sliceop`: `':' test?` — the optional `:step` third part of
a subscript slice, i.e. `a[1:4:2]`, `a[::2]`, `a[1::2]`, `a[1:2:]`), so
the py-sh-go frontend can lower strided slices. The existing slice shape
`param("slice", name, off, len)` (bash `${arr[@]:off:len}`) carries only
offset + length — there is no stride/step field anywhere in the A1
contract (src/ir.rs `"slice"` handling reads args[2]=off, args[3]=len
only; the ESTree renderer's slice rewrites read the same two fields).
Proposed shape: a step-aware slice form, e.g. a `step` argument on
`param("slice", name, off[, len[, step]])` (defaulting to 1 so existing
emits stay byte-identical), or a new whitelisted helper
(e.g. `param("sliceStep", name, start, stop, step)`) that the ESTree
runtime renders as an array-valued strided selection (`Array.from({length:
…}, (_, i) => arr[start + i*step])`-style), following the array-valued
conventions of `arrayItems`/`param("slice")` with mode `@`.

## WHY
The coverage hook (rules-gap.sh) reports `sliceop` as a Python3 grammar
rule no testdata example exercises. The reason no example exists: the
frontend cannot express it — no lowering path. The hand-rolled subscript
parser in frontends/py-sh-go/main.go handles `expr | expr:expr | expr: |
:expr` (SliceStart/SliceEnd → `param("slice", name, start, len)`), but
after the optional end it does `expectOp("]")`, so the second `:` always
fails loudly:

    $ printf 'a = [1, 2, 3, 4]\nprint(a[0:2:1])\n' > /tmp/st.py; ./py-sh-go --shir /tmp/st.py --raw
    py-sh-go: parse: expected "]"
    exit=2
    $ printf 'print(a[::2])\n' | ./py-sh-go --shir /dev/stdin --raw
    py-sh-go: parse: unexpected token ":"
    exit=2
    $ printf 'print(a[1::2])\n' | ./py-sh-go --shir /dev/stdin --raw
    py-sh-go: parse: unexpected token ":"
    exit=2
    $ printf 'print(a[1:4:2])\n' | ./py-sh-go --shir /dev/stdin --raw
    py-sh-go: parse: expected "]"
    exit=2
    $ printf 'print(a[1:2:])\n' | ./py-sh-go --shir /dev/stdin --raw
    py-sh-go: parse: expected "]"
    exit=2

This is NOT a documented by-design subset refusal: py-sh-go has no
FRONTEND.md, and the exclusion ledger (frontends/coverage/
refused-py-sh-go.txt) contains 30 entries, none mentioning
slice/step/stride (nor does bugs-py-sh-go.txt). The plain start:end
slice IS supported and covered (t37_substring, t66_array_slice lower to
`param("slice", …)`), so the step feature is not deliberately excluded
— it is simply unimplemented because there is nowhere to lower it.
Python's slice step semantics (strided element selection) have no bash
counterpart: `${arr[@]:off:len}` selects a contiguous run, and no A1
node/field carries a stride. This follows the lambdef
(py-sh-go-lambdef-20260813-192707) and star_expr
(py-sh-go-star-expr-20260813-193834) precedents: inexpressible because
the A1 contract has no node/field for it, not because the subset
refuses it.

## MINIMAL-CORE-CHANGE
1. src/ir.rs / src/shir.rs: extend the `param("slice", …)` runtime
   contract with an optional trailing `step` arg (absent or 1 ⇒ today's
   contiguous behavior, byte-identical emits), or add a sibling
   whitelisted helper (e.g. `param("sliceStep", name, start, stop,
   step)`) returning an array-valued strided selection in
   array/setArray position (whole-array `@`/`*`/`#`/`!` variants
   unchanged). Purity/emulation tables in src/shir_json.rs + the
   ingress callee gate must accept it (mirror the existing
   `arrayItems`/`listVar`/`split`/`captureWords` conventions).
2. src/estree.rs: render the step form — the runtime currently splices
   array-valued items into `setArray` (`is_scalar_array_item` /
   `[].concat(...)`), so an array-valued strided slice used as a
   setArray/Array element works end-to-end once the runtime returns an
   array for it.
3. src/shir_json_in.rs: accept the new shape in the strict ingress
   deserializer; frontends/shir-contract/schema.json gains it
   (workspace-side, keeps check_schema.py green).
4. Negative step (`a[::-1]`, Python's reverse) can be expressed as
   step = -1 in the same shape; bash has no reverse-slice, so the
   runtime handles it (JS-side reverse/range).

The frontend side (subscript parser: parse the optional second `:` +
step expr into a SliceStep field → emit the step-aware slice) is
py-sh-go's own fix and lands after the contract has the shape; the
coverage worker retries the gap automatically once this request
completes (core-pending-py-sh-go.txt pruning).

## FAILING-CASE
Minimal Python program (python3 runs it fine, prints `['b', 'd']` for
`a[1:4:2]`):

```python
a = ["a", "b", "c", "d"]
print(a[1:4:2])
```

also:

```python
a = [1, 2, 3, 4, 5]
print(a[::2])
print(a[1::2])
print(a[::-1])
```

stdout: `[1, 3, 5]`, `[2, 4]`, `[5, 4, 3, 2, 1]`.

Current behavior: `./py-sh-go --shir` fails with
`py-sh-go: parse: unexpected token ":"` (empty start) or
`py-sh-go: parse: expected "]"` (start+end then `:step`), exit 2 — so
no testdata example can cover `sliceop`, and the A1 contract is missing
the stride shape end-to-end (frontend emit → ingress acceptance →
ESTree run vs native python3 stdout).

## OUTCOME: rejected: superseded by py-sh-go-sliceop-20260813-222910 (identical contract need; the 5-arg step slice shape was implemented under 222910 and re-verified end-to-end this round: `b d f` / `a c e` == python3). Negative-step reversal (a[::-1]) remains the documented v1 follow-up in both requests.
