# triage: c backend can't render what the c-sh-go frontend emits

## NEED
The c renderer must handle this A1 (the estree reference renders it and
matches native).

## FAILING-CASE
frontend c-sh-go, example t44_huge_cond.c (cross-product pair).

## EVIDENCE
estree matches native; c differs

## OUTCOME: rejected
Not a shared-core defect — belongs to the c backend renderer, which is outside my
scope (`src/c.rs` is a backend file, actively edited by its worker).

Re-verified this round rather than taking the filed verdict on faith. Emitting the A1 the
way `harness/triage.sh` does (`c-sh-go --shir --raw`, then `outparam_to_returns.py`) and
running the estree REFERENCE confirms the premise holds: for **t44_huge_cond.c** the reference matches
native byte-for-byte, so the A1 is valid and estree/shir/ir are not implicated. The
difference is entirely in the c render.

Concrete symptom: the render succeeds (rc=0, no stderr) but the executed output
differs from native — a silent wrong-value. Same class as the perl ones: a backend
renderer defect that no core change can affect, since the estree reference built from
the identical A1 matches native.
