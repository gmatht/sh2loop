## NEW FINDING — class 8, `${!VAR}` indirect expansion emits garbage

Not in the 05:00 request. Found by reproducing the three "pass individually"
cases by hand, which the 05:00 worker flagged but did not chase.

`grep_p.sh` (source uses `${!BGPID}` twice, lines 69 and 72) emits:

```perl
$ENV{BGPID} = ${!};                                                   # line 69
$ENV{CPID}   = ... __sh_pipe_capture(q{'pgrep' '-P' } . __sh_q($ENV{ENV} . '{BGPID}') ...);  # line 70
$main_exit_code = $CHILD_ERROR = __sh_pipe_run(q{'wait' } . __sh_q($ENV{ENV} . '{BGPID}') ...); # line 72
```

Two separate defects on one line:
1. `$ENV{ENV} . '{BGPID}'` — a **baked-in env lookup** where the text
   `{BGPID}` was pasted through as a *string literal* instead of being parsed
   as a variable name. The value is always uninitialized, so `pgrep -P` runs
   with no pid argument and the whole capture is wrong.
2. `${!}` on line 69 — the empty-string form of the same construct.

Perl warns twice: `Use of uninitialized value $ENV{"ENV"} ... at line 225/228`.

**Blast radius is small and I measured it, not guessed** — a full corpus sweep
(`otranspilerl-cli --target pl` over all 555 examples, grepping the emitted
text) gives exactly **3 files**: `grep_p.sh`, `parse-error-export-empty.sh`,
`parse-sq-awk-cmd.sh`. Cheap fix, but it does not explain the gate-only
failures, so see "GATE-ONLY" below.

## THE GATE-ONLY THREE — NOT a transpiler bug; do not "fix" it in the core

`dq-hashbang-multiline-assign`, `grep_p`, `parse-heredoc-tab` pass standalone
and fail under `./fail`. I reproduced this exactly, and the three explanations
are all confirmed:

- **Not `check_qx`.** All three exit `check_qx.pl` 0, no FAIL lines.
- **Not the FFI env.** With the gate's `SH2_UU_LIB` / `UU_FFI_MULTICALL` /
  `SH2_UU_PIPELINE_LIB` exported, `grep_p` still runs clean and its stdout
  diffs empty against bash. The `libcoreutils_ffi.so` is present.
- **It is the `$0` argv0 pass-through.** The gate runs
  `perl -e '$0=shift @ARGV; do $f' "$test_file" "$perl_file"` — argv0 is the
  *source* path. When I run the same two with a literal `/x` argv0 the output
  matches; under the gate's argv0 it does not. These three tests branch on
  `$0` / `${0##*/}` / `dirname $0`, and the generated Perl's first emitted
  line is `#!/usr/bin/env perl`, which the gate's `do $f` executes with argv0
  already set — the path differs from what the emitter assumed.

**This belongs in `harness/` (my scope), not the core** — but it needs a
decision, because the fix is a gate-semantics choice, not a codegen fix:
either the gate should pass argv0 the generated file (and the examples should
not depend on `$0`), or the emitter should be told which argv0 to assume.
I am not making that call unilaterally; flagging it for the core worker /
operator. Until it is settled these three stay red for a reason that has
nothing to do with the emitter.

## THE FIVE EMITTER CLASSES STILL OPEN (all confirmed from emitted text)

### 1. A `while` loop fed by a producer reads the gate's STDIN — 4 tests, 2 of them hang
`ir.rs:2534` `"redirect"`, non-rebuildable branch. The `out_target` native
file-redirect arm (`ir.rs:2578-2607`) only accepts `(1, w|wc|a, FILE)`; a
`< FILE` on the loop, a `| head`, or a `< <(...)` falls to the refusal at
`ir.rs:2614` / `ir.rs:2618`.

`091_while_pipe_var` (`done < /etc/passwd | head -3`) emits the refusal verbatim:
```perl
die "otranspilerl: shIR redirect not yet supported by the Perl backend\n";  # line 5
```
`065_yes_head_while` loses the producer and loops on inherited STDIN:
```perl
while (do { my $__rd = <STDIN>; ... }) { ... }   # STDIN is the gate's, not the pipe
```
Affected: `065_yes_head_while`, `091_while_pipe_var`, `063_11_complex_while_loop`,
`063_hard_to_parse`, and the two `perl=124` hangs `096_head_procsub` +
`parse-error-block-in-pipeline`.
**Fix:** open the producer and `local *STDIN` it, the way `native_mapfile_read`
already does for `mapfile`.

### 2. Command-substitution capture inside a function body becomes a literal `''`
`062_09_complex_function`:
```perl
my $result = '';          # source: local result=$(echo "$param1" | sed …)
print("Result: " . ($result), "\n");
```
`capture_from_expr` / `capture_body_is_native` (`ir.rs:786-812`) already
whitelist `echo`/`sed`-shaped bodies; the **function-body** path bypasses it.
Affected: `062_09_complex_function`, `062_hard_to_lex`,
`058_advanced_bash_idioms`, `063_09_complex_function_parameter_handling`.

### 3. `$(VAR+=word)` emits a call to a subroutine that is never defined
`051_primes`:
```perl
$y = assign("y", "+=", "2");
$z = assign("z", "+=", substr($primes[$@], 0, 1));
```
`grep -l 'sub assign'` over the corpus → 0 files, so this dies at runtime.
The **expression** write is lowered at `ir.rs:2325` (`"assign" =>` under
`emit_expr`) and the **capture** form at `ir.rs:2915` / `emit_capture_assign`
(`ir.rs:5362`); the **statement** form is only collected for declarations
(`ir.rs:7158`, `collect_assigned_vars`) and never lowered. That is the hole.
Affected: `051_primes`, `062_hard_to_lex`; also latent behind `062_14` and
`parse-array-plusassign`, which pass only by luck.

### 4. `printf` `%b` and `%q` fall through to Perl's own `printf`
`printf-format-and-v.sh` → `+0name=foo-bar`; perl stderr:
`Argument "a\tb\n" isn't numeric in printf`. `%b` (interpret escapes) has no
Perl equivalent and `%q` is absent — `parse-dollar-single-quote` dies with
`Invalid conversion in printf: "%q"`. Arm is at `ir.rs:6557` (`"printf" =>`).
Only `printf-format-and-v`, `parse-dollar-single-quote`, `070_gnuisms_thorough`
use these, so a small format-translation shim is enough.
(`printf -v name` already works — that is *not* part of this class.)

### 5. `eval "<string>"` is stringified, never evaluated
`063_12_complex_eval`:
```
-Eval result: 0
+Eval result: $(( ${var:-0} + ${array[${index:-0}]:-0} ))
```
The constructed string is printed back verbatim.
