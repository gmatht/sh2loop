# rust: estree positional-bridge tests assert a JSON SUBSTRING that can never appear — both are permanently red

Filed by: the **rust BACKEND** worker (`backends/rust/src/rust_backend.rs` is
mine; `backends/rust/src/estree.rs` is the shared core and is NOT mine).
Measured on branch `rust` @ `c4557d636` with `cargo test --lib` on
2026-09-30 23:5x.

**This is a TEST defect, not a lowering defect.** The product code is
correct — the assertion is written against a string that the ESTree
serializer can never produce. Both tests are therefore permanently red on
this branch and are the only two lib-test failures the rust branch
introduces (`comm` of the rust vs main failure sets: 2 new, 0 fixed, the
other 13 are pre-existing on main and owned by the c/estree/ir workers).

## NEED

`backends/rust/src/estree.rs::tests::direct_call_keeps_positional_bridge`
probes for the positional bridge with:

```rust
serde_json::to_string(&prog).unwrap().contains("sh2.positional")
```

`sh2.positional` is **not** a string in the ESTree output. A `sh2.positional`
read is an *AST node* — a `MemberExpression` whose `object` is
`Identifier{"sh2"}` and whose `property` is `Identifier{"positional"}` —
so the serialized JSON is:

```json
{"type":"MemberExpression",
 "object":{"type":"Identifier","name":"sh2"},
 "property":{"type":"Identifier","name":"positional"},
 "computed":false}
```

The literal seven-character sequence `sh2.positional` only exists in the
**pretty-printed source form**; `serde_json::to_string` never emits it. The
check can never return true, so the pass is asserted to be broken no matter
what the lowering does.

## WHY

The two tests were added by this branch in commit `e85ec26a0`
("Test results: 498 passed, 57 failed") to guard a REAL and correctly
working behaviour, and the guard itself is miswritten. The behaviour under
test is sound; only the observation is wrong. Because the failure looks
like "the direct-call pass dropped the positional bridge", it invites a
fix to `direct_shell_fn_calls` itself — which would be the wrong repair
and would risk regressing a working lowering.

## MINIMAL-CORE-CHANGE

Replace the substring probe with a structural AST walk in the same
`#[cfg(test)] mod tests` block (no non-test code changes at all):

1. add a `has_positional(&Expr) -> bool` helper that matches
   `Expr::MemberExpression { object, property, .. }` where
   `matches!(&**object, Expr::Identifier{name} if name == "sh2")` and
   `matches!(&**property, Expr::Identifier{name} if name == "positional")`,
   recursing through `CallExpression` (callee + arguments),
   `BinaryExpression` / `LogicalExpression` / `AssignmentExpression`
   (left + right), `AwaitExpression`, `MemberExpression` (object +
   property), `ArrayExpression`, `TemplateLiteral` and
   `ObjectExpression`;
2. a `has_positional_stmt(&Stmt)` companion for the statement cases the
   pass can actually rewrite (`ExpressionStatement`, `BlockStatement`,
   `ReturnStatement`);
3. have `direct_call_keeps_positional_bridge` return
   `prog.body.iter().any(has_positional_stmt)`.

Note the two useful shapes that this walker must cover, both of which the
current probe never sees:

- the bridge itself sits inside an `ArrowFunctionExpression` body
  (`ArrowBody::Block`), under a `sh2.functions.set(...)` call — the walk
  has to descend into arrow bodies, or it reports `false` for the right
  reason (a false negative);
- the produced read is `sh2.positional ?? ""` (a `LogicalExpression` with
  a `MemberExpression` on the left) — the walk must descend into binary /
  logical operands, or it reports `false` again.

A cheaper-but-still-correct alternative if the core prefers a text probe:
assert on the token that the serializer really does emit,
`out.contains("\"positional\"")`, which is unambiguous here because
`sh2.positional` is the only `positional` member the direct-call bridge
introduces. The structural walk is preferable — it cannot be fooled by a
string literal that happens to contain the word.

## FAILING-CASE

```
$ cd backends/rust && cargo test --lib direct_call_bridges
running 2 tests
test estree::tests::direct_call_bridges_param_positional_reads ... FAILED
test estree::tests::direct_call_bridges_getvar_positional_reads ... FAILED

positional bridge dropped for getVar("1")

---- estree::tests::direct_call_bridges_param_positional_reads stdout ----
thread '...' panicked at src/estree.rs:6177:13:
positional bridge dropped for param("len","1")

test result: FAILED. 0 passed; 2 failed; ...
```

Deterministic — 5/5 consecutive runs, same two tests, no flakiness.

The bridge is in fact emitted. Verified by dumping the estree for the
exact A1 input the test builds (`a = getVar("1")` inside `f`, called as
`fnCall("f", ["hi"])`), after `shir_to_estree` + `direct_shell_fn_calls`:

```
sh2.functions.set("f", async () => { a = sh2.positional[0] ?? "" }, true)
```

and the discriminating probe over the same three inputs:

```
getVar_1      : substr_sh2.positional=false  raw_positional_token=true
getVar_a      : substr_sh2.positional=false  raw_positional_token=false
param_len_1   : substr_sh2.positional=false  raw_positional_token=true
```

The `raw_positional_token` column is the real signal and it discriminates
correctly: the two POSITIONAL inputs (`getVar("1")`, `param("len","1")`)
carry the bridge; the negative control `getVar("a")` does not. So the
lowering distinguishes exactly what the test is trying to distinguish —
only the assertion is looking at the wrong representation.

## OUTCOME: implemented
The diagnosis was correct and the fix is landed — sh2perl `9f4c6b8a8`. `estree.rs`
now walks the emitted TREE for the bridge instead of grepping the serialization:
`direct_call_keeps_positional_bridge` serializes to `serde_json::Value` and calls a new
`has_positional_member`, which matches the whole member chain rather than the bare
`sh2.positional` node — so it also catches the derived forms the request's own analysis
predicted would be missed (`sh2.positional[0]` for `$1`, `sh2.positional.length` for
`$#`, nested under a `?? ""` LogicalExpression inside an arrow body under a
`sh2.functions.set(...)` call).

Verified this round, `cargo test --lib direct_call_bridges`: 2 passed, 0 failed.

The negative control was also added: `getvar_hash_form_stays_a_runtime_read` pins that
`getVar("#1")` does NOT acquire a bridge — the runtime's getVar contract defines `#N`
as the LENGTH of positional N's value, so a compile-time bridge would turn `len($1)`
into `sh2.positional[0].length` and drop the element. Both tests were green 3/3
consecutive runs, not a flake. The estree corpus gate is unaffected: 557/557.
