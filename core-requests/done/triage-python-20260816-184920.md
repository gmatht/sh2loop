# triage: python backend can't render what the zsh-sh-go frontend emits

## NEED
The python renderer must handle this A1 (the estree reference renders it and
matches native).

## FAILING-CASE
frontend zsh-sh-go, example t90_herestring.zsh (cross-product pair).

## EVIDENCE
estree matches native; python differs

## OUTCOME: implemented

The python renderer dropped fd-0 HERESTRING redirects entirely: for
`cat <<<"$v world"` it emitted `__sh_exec(["cat"])` with no stdin, so `cat`
read the script's own stdin and printed nothing (the estree reference prints
`hello world`). A herestring value is computed in PYTHON (its target is an
Interpolate of shell variables), so it cannot ride the heredoc body — bash
would re-expand its contents. `python_backend`'s Redirect arm now runs the
command through the stdin-carrying seam (`__sh_bash_in(...)` with
`<value> + "\n"`), with the sibling `> file` case writing the captured bytes
to the file instead of stdout.

Verified: `harness/triage.sh zsh-sh-go t90_herestring.zsh python` → PASS
(matches the estree oracle `hello world`). NOTE: `zsh` is not installed on
this box, so the pair's oracle is the estree reference (triage falls back to
it when native output is empty); the fix is renderer-side and zsh-agnostic.
