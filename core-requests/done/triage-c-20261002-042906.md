# triage: c backend can't render what the bat-sh-go frontend emits

## NEED
The c renderer must handle this A1 (the estree reference renders it and
matches native).

## FAILING-CASE
frontend bat-sh-go, example t53_renpattern.bat (cross-product pair).

## EVIDENCE
estree matches native; c differs

## OUTCOME: rejected: two independent out-of-core causes, and the "estree matches native" premise is false for the goto family

Re-diagnosed with the correct A1 input path. NOTE for any future round: A1 goes to the
CLI on **stdin** (`otranspilerl-cli - --target <t>`), NOT as a file path. Feeding the
`.a1.json` as a positional filename makes the CLI parse the *filename* as shell source and
emit a bogus `process.exit(2)`; that artifact is what the prior five rounds of this family
were reading as "C renders an empty stub". Re-measured properly:

**1. The goto family — estree is NOT a working reference (premise is false).**
`t06_goto`, `t10_mixed`, `t23_labels` all contain `Goto`/`Label` nodes in the A1
(`{"name":"skip","type":"Goto"}`, verified structurally). Rendering them to estree gives
`sh2.unsupported` call counts of **1 / 1 / 2**, so `harness/estree_gate.pl` **FAILS** on all
three ("sh2.unsupported call present"). C renders t06 as before/after — i.e. C drops the
goto, estree marks it unsupported — but the claim "estree matches native" does not hold.
(Counting note: the emitter writes this as two JSON tokens, `object:"sh2"` +
`property:"unsupported"`, so a plain `grep -c sh2.unsupported` reports 0 and is a false
negative; it must be counted as a CallExpression shape, as the gate does.)

This is a real **word-level lowering gap in the shared emitter** (`Goto`/`Label` unlowered) —
but it is *shared*, not c-specific: estree fails identically, so it is not "c can't render
what estree renders", and closing it moves the goto family for BOTH backends. It belongs to
the emitter as a genuine core task, not to the c renderer.

**2. t53/t45 — C's render is correct; the C cell cannot compile.**
`t53` renders `rc=0`, no `TODO sh2.*`, empty stderr, and a complete faithful program (the
`ren *.cxx *.cpp` loop via `basename` + `mv`, both `cat`s, the `del`). But it emits
`#include <uu_run.h>` and calls `_sh_uu_capture`/`_sh_uu_run`, which resolve against
`libcoreutils_ffi.so`. That artifact is **never built**: `backends/c/runtime/lib/` does not
exist, and `runtime/build_uu_ffi.sh` (the only builder) has not been run. Compiling by hand:
`fatal error: uu_run.h`, and with `uu_run.c` linked, `undefined reference to 'uu_run'`.
So the cell diverges at **compile/link time**, never at the core's render step.

Out of core scope for a renderer change: mechanism 1 needs an emitter feature (shared, and
it would help estree too), mechanism 2 needs the uu-ffi runtime built in the C cell.
