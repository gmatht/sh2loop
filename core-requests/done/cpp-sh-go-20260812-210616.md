# cpp-sh-go: A1 ForInit panics the ESTree renderer in --shir-in-estree (strip_cfor unwired) — same root cause as c-sh-go-20260812-205941

## NEED

`debashc --shir-in-estree` (the cpp-sh-go gate's ingress-acceptance oracle,
Makefile `test-cpp`) must accept the A1 `ForInit` node that the C-family
frontends emit for C-style `for` loops. The lowering pass already exists and
is unit-tested — `src/shir_passes/strip.rs` (`strip_cfor`, added in submodule
commit f5d761f) — but it is never invoked: `src/shir_passes/mod.rs` does not
declare `pub mod strip;` (the file is not even compiled into the crate), and
the A1-ingress paths in `cli/src/lib.rs` call only `restructure_goto_only` +
`process_subst`. Wire the existing pass in:

1. `src/shir_passes/mod.rs` (after `pub mod restructure;`, line 51):
   ```rust
   pub mod strip;
   pub use strip::strip_cfor;
   ```
2. `cli/src/lib.rs` — `debashl::shir_passes::strip_cfor(&mut prog);`
   immediately after `restructure_goto_only(&mut prog);` in:
   - `--shir-in-estree` (line 932)  ← the failing oracle
   - `--shir-in-perl` (line 962)
   - `--shir-in-sh` (line 986)
3. `src/wasi_api.rs` — `otranspilerl_render` (line 250) and the
   `src_lang == "shir"` branch of `otranspilerl_transpile_impl` (line 223):
   call `crate::shir_passes::strip_cfor(&mut prog)` after `shir_json_to_ir`
   and before `render_ir`.

strip.rs's own header states the intended wiring: "A renderer that encounters
an UNSTRIPPED ForInit refuses (REFUSE > GUESS) — the pipeline runs this pass
before every renderer, so reaching one means a pipeline forgot the strip."
The backends' REFUSE messages ("strip_cfor should have lowered it") confirm
the pass is expected in the pipeline.

## WHY

The cpp-sh-go gate fails on the first loop-bearing example, `t05_arith_loop.cc`:

```
OK t04_comment.cc (valid A1 shIR — the core deserializer accepts it)
FAIL t05_arith_loop.cc (emit is not valid A1 shIR — the gap the worker fixes; probes 101/101, post-rebuild 101)
```

The emit is contract-valid — the deserializer accepts it, and the A1
`ForInit` node + `strip_cfor` were added together (workspace commit 2d577e6
"A1: ForInit (C-style for) + first-class Continue/Break, with the strip_cfor
pass"; `frontends/shir-contract/schema.json` carries `ForInit`). The failure
is a core pipeline gap: `--shir-in-estree` deserializes, then
`shir_to_estree_json` panics at `stmt_to_estree` (src/shir.rs:13915,
`other => unreachable!("Perl-only IR statement reached the ESTree renderer:
ForInit {...}")`) → exit 101 → "emit is not valid A1 shIR". (The same panic
is the c-sh-go gate's `t06_for.c` failure; c-sh-go's request
c-sh-go-20260812-205941 documents the identical fix.)

Evidence this is a wiring regression, not a new feature:
- `sh2perl/target/debashc` (built 12:31, before the estree worker's WIP
  churn) contains compiled `strip_cfor` symbols and ACCEPTS both
  `t05_arith_loop.cc` and `t06_for.c` emits (exit 0).
- The current `target/debug/debashc` (rebuilt 20:59) does not (panic).
- The exact wiring is preserved in the estree worker's own stash
  `stash@{0}` "estree-worker-broken-wip": `debashl::shir_passes::strip_cfor(&mut prog);`
  after `restructure_goto_only` in `--shir-in-estree` / `--shir-in-glsl` /
  `--shir-in-perl` / `--shir-in-sh`.
- The current debug binary accepts the manually-stripped shape
  (`Block([init…, While(cond, body+step)])`) with exit 0 — the pass is the
  complete fix, nothing else is broken in the renderer.

## MINIMAL-CORE-CHANGE

The three edits above — expose the existing pass and call it in the four
A1-ingress render paths. No new logic: `strip_cfor` already implements the
continue step-splice semantics (step re-inserted before every top-level
`continue`, recursing into If/Block but not nested loops; see
`forinit_lowers_to_while_with_step_and_continue_splice` unit test in
strip.rs:154).

## FAILING-CASE

Repro (no frontend rebuild needed):

    cd /home/llm/sh2loop/frontends/cpp-sh-go
    ./cpp-sh-go --shir testdata_cpp/t05_arith_loop.cc --raw > /tmp/t05.json
    ../../sh2perl/target/debug/debashc --shir-in-estree /tmp/t05.json

→ panics: `internal error: entered unreachable code: Perl-only IR statement
reached the ESTree renderer: ForInit { init: [Assign { … i = Str("1") }],
cond: Call { func: "test", args: [Str("$i -le 4")] }, step: [Assign { … i =
Arith i+1 }], body: [Assign { … sum = Arith sum+i }] }`

Minimal source:

```cpp
#include <cstdio>
int main() {
    int sum = 0;
    for (int i = 1; i <= 4; i++) {
        sum += i;
    }
    printf("sum=%d\n", sum);
    return 0;
}
```

Validation after the fix: `--shir-in-estree` must exit 0 on the emit, then
`make test` in `frontends/cpp-sh-go` (refusals + ingress + executed-stdout
vs native g++ → `sum=10`) and in `frontends/c-sh-go` (C-invariant,
`t06_for.c` → `f0\nf1\nf2\n`) must go green.

## OUTCOME: implemented: the pass is wired in all requested sites — src/shir_passes/mod.rs `pub mod strip;` + `pub use strip::strip_cfor;` and wasi_api.rs (otranspilerl_transpile_impl shir branch + otranspilerl_render) are committed (submodule bb5249d); cli/src/lib.rs calls strip_cfor in --shir-in-estree/--shir-in-perl/--shir-in-sh (committed 955b318).
