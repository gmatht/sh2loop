# sh: `>|` (RedirectOutClobber) loses its clobber flag — rendered as plain `>` under set -C

## NEED

The A1 shIR redirect contract must carry the `>|` clobber distinction. The
parser currently lowers `>|` to plain `RedirectOperator::Output` (mode
"w"), so no backend can render it faithfully — under `set -C` (noclobber)
a rendered plain `>` fails while bash's `>|` succeeds.

## WHY

The sh backend gate fails `examples/parse-redirect-clobber.sh`:

```sh
#!/bin/sh
set -C
tmpf=$(mktemp /tmp/clobber_test.XXXXXX)
: >| "$tmpf"
printf 'clobber file exists=%s\n' "$([ -f "$tmpf" ] && echo yes || echo no)"
rm -f "$tmpf"
```

The emitted shIR redirect spec is `{"fd": 1, "interpolate": true, "mode":
"w", "target": {"func": "getVar", ...}}` — the clobber flag is gone. The sh
renderer emits `: >"$tmpf"`, which under `set -C` fails (rc=2, no output)
vs bash rc=0 printing `clobber file exists=yes`. The C/perl/go backends
hit the identical wall: the contract cannot express the flag.

Root cause: src/parser/redirects.rs:64
`Some(Token::RedirectOutClobber) => RedirectOperator::Output, // Use Output as fallback`
— a deliberate fallback that drops the token. `RedirectOperator` itself
(and the estree node model) may already distinguish the two; only the
shIR lowering and the JSON serialization lose it.

## MINIMAL-CORE-CHANGE

1. In the shIR lowering (src/shir.rs, the `redirect_to_ir`-style fn that
   builds `IrRedirect`): map `RedirectOperator::ClobberOutput` (or a new
   distinct operator for `>|`) to a distinct mode string, e.g. `"wc"`
   (documented alongside the existing `"r" | "w" | "a" | "r+"` set in
   src/ir.rs `IrRedirect.mode`). If `RedirectOperator` has no
   ClobberOutput variant, add one in the parser and map the token in
   src/parser/redirects.rs:64 instead of falling back to Output.
2. shir_json.rs serialization already emits `"mode": r.mode` — no change
   needed beyond the new mode string flowing through.
3. shir_json_in.rs: accept the new mode string on ingress (the
   `req_str(o, "mode", ...)` read is generic — verify no enum check
   rejects it).

## FAILING-CASE

```sh
set -C
tmpf=$(mktemp /tmp/clobber_test.XXXXXX)
: >| "$tmpf"          # must truncate/create even though noclobber is on
echo "exists=$([ -f "$tmpf" ] && echo yes || echo no)"
rm -f "$tmpf"
```

`debashc --shir` on this must emit a redirect with mode `"wc"` (or a
`clobber: true` field on the spec), so backends can render `>|`. With the
current mode `"w"`, bash prints `exists=yes` (rc 0) while every rendered
translation fails under `set -C`.

## OUTCOME: implemented — landed in 0e21666 (parser RedirectOperator::ClobberOutput
+ mode "wc" on the A1 redirect spec; harness runner treats wc as w). Verified this
round: the FAILING-CASE script emits "mode":"wc" through --shir --raw and the
shir_json round-trip preserves it (clobber_redirect_keeps_wc_mode test).
