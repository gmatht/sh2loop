# estree: wire the sync-ok-loops transform verdicts into the loop renderer + runtime

The transform `core-requests/transforms/sync-ok-loops.rs` (already
compile-in ready, validated: builds, 0 corpus panics) computes per-loop
verdicts but is ANALYSIS-ONLY — it cannot change emission without these
two renderer hooks + the runtime primitive. Wire them; the corpus gate
(`./fail-estree` at the trusted baseline) judges the whole.

## NEED

Honor the transform's verdicts in the loop lowering so the runtime stops
awaiting per iteration when it shouldn't:

1. **`sync_ok` loops run as ONE sync chunk** (no breakup): loops that
   complete in ~200ms, or whose body produces no output.
2. **`batch_ok` loops run checkpointed**: sync chunks of 1024 iterations
   with a yield — `if (++n === 1024) { n = 0; await setImmediate; }` (the
   `i % 1000 = 0` idea; 1024 = power of two → `(i & 1023) === 0` if the
   i-based phrasing is used) — instead of the per-iteration await.

## WHY

The shellbench eval/output benches show the runtime's per-iteration
`forLoop` await dominating short loops (0.14x–0.45x). A loop that is
cheap, or that nothing external can interleave with (no output), only
pays await overhead — bash runs it as one blocking slice. A long
OUTPUTTING loop must stay responsive — but 1024:1 amortization of the
yield costs ~nothing. Same bytes emitted, same bash output order; only
the yield cadence changes (background-job interleaving is the edge the
bisect catches).

## MINIMAL-CORE-CHANGE

The transform exposes `crate::transforms::sync_ok_loops::{sync_ok,
batch_ok}` (pointer-keyed `&IrStmt` verdicts, populated in `ast_to_ir`,
stable through emission — same guarantee as `lastexit_dead`):

1. **`shir.rs` `compute_async_region_loops` (~line 5595)** — a `sync_ok`
   loop is NOT an async-region loop:
   `if in_async && !crate::transforms::sync_ok_loops::sync_ok(st) { out.insert(st as *const IrStmt as usize); }`
   → the EXISTING sync gate (~line 7440: `!loop_in_async_region &&
   !lowered_stmts_have_signals && for_iter_flattenable`) then emits
   `sync_ok` loops with the EXISTING `forLoopSync`/native for-of path —
   zero new emission code for criteria 1+2.
2. **The For/While lowering** — a `batch_ok` loop that still fails the
   sync gate (async region / glob iter / signals) gets the checkpointed
   call instead of per-iteration `forLoop`:
   `sh2.forLoopBatch(iter, body, 1024)` (arg order mirrors `forLoopSync`
   + the batch size).
3. **`harness/sh2-namespace.mjs`** — add `forLoopBatch`, mirroring
   `forLoopSync`'s execution + flatten EXACTLY, but with an iteration
   counter: every 1024th iteration `await new Promise(r =>
   setImmediate(r))` before continuing. (Reuse the forLoopSync body/
   signal machinery — don't fork semantics.)
4. **`harness/estree_gate.pl`** — whitelist `forLoopBatch` (like
   `forLoopSync`) so the structural gate accepts it.

Verdict sanity (the transform was validated on these):
`while true; do :; done &` → batch; `x=$(for i in {1..1000}; do echo
$i; done)` → sync (3ms); `for i in {1..50000}; do echo $i; done` → sync
(150ms ≤ budget); `x=$(for i in {1..1000000}; do echo $i; done)` →
batch; `for i in {1..1000000}; do j=$((i+1)); done` → sync (no output).

## FAILING-CASE

No correctness failure today — this is a performance escalation
(0.14x–0.45x shellbench eval/output). The regression risk is a corpus
example whose output INTERLEAVES with a background job that the new
yield cadence reorders; the worker's bisect blames the transform if so.

## MEDIATION NOTE (2025-08-05 — estree core owner)

**Status: IMPLEMENTED.** The transform is compiled into the crate
(`sh2perl/src/transforms/sync_ok_loops.rs`, registered in
`transforms::all()`), and the renderer + runtime hooks are wired (see the
Plan 17 entry in .estree_plans.md for the full record):

1. `compute_async_region_loops` skips `sync_ok` loops (they are NOT
   async-region loops — the existing sync gate then emits them natively).
2. The For/While lowering emits `await sh2.forLoopBatch(iter, body,
   1024)` / `await sh2.whileLoopBatch(cond, body, 1024)` for `batch_ok`
   loops that fail the native gate — sync chunks of 1024 with a
   `setImmediate` yield, mirroring the *Sync twins exactly.
3. `harness/sh2-namespace.mjs` gains `forLoopBatch`/`whileLoopBatch`;
   `estree_gate.pl` + `sh2-namespace.json` whitelist/spec them.

**About the earlier rejection:** the transform was bisect-BLAMED for a
corpus regression in the previous cycle, but it is ANALYSIS-ONLY (zero
emission change without the renderer hooks) — the blame was spurious
(the same cycle's 4 real failures were fixed later in the harness, and
the corpus run had a known flaky). The transform file has been moved
from `transforms/rejected/` to `transforms/done/`.

**Verification:** corpus 530/531 (== trusted baseline; the 1 failure is
the pre-existing `double-paren-subshell` gzip flaky, present on the
pre-change baseline too); metric 2606/7 unchanged; cargo tests 63/63
(determinism asserted, 3 consecutive runs); PERL pass count unchanged
(441); structural gate green. The batch path was verified live
end-to-end on the target pattern family (`for f in *.sh; do echo "$f";
done` → forLoopBatch, stdout byte-identical vs bash; runtime semantics:
flatten, BREAK/CONTINUE signals, lastExit protocol, _capExceeded).

**Known limitation (documented in Plan 17):** pointer-keyed verdicts do
not survive the pre-existing arrow-CLONE emission for
capture/subshell/background/function/pipeline bodies (all other
pointer-keyed verdicts share this); the current corpus has no
batch-eligible top-level loop shape, so the metric is unchanged. The
wiring is live for top-level/block-body loops.
