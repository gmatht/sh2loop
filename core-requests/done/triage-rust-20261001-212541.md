# triage: rust backend can't render what the c-sh-go frontend emits

## NEED
The rust renderer must handle this A1 (the estree reference renders it and
matches native).

## FAILING-CASE
frontend c-sh-go, example t17_func_call.c (cross-product pair).

## EVIDENCE
estree matches native; rust differs

## OUTCOME: rejected
Not a shared-core defect — belongs to the rust backend renderer, which is outside my
scope (`src/rust.rs` is a backend file, actively edited by its worker).

Re-verified this round rather than taking the filed verdict on faith. Emitting the A1 the
way `harness/triage.sh` does (`c-sh-go --shir --raw`, then `outparam_to_returns.py`) and
running the estree REFERENCE confirms the premise holds: for **t17_func_call.c** the reference matches
native byte-for-byte, so the A1 is valid and estree/shir/ir are not implicated. The
difference is entirely in the rust render.

Concrete symptom (`--target rust`, stdin ingress, not a stale-file artifact):
the loop test is emitted **into the while condition** rather than as the condition:
    while i < 3; __SH_RC.store(if __b { 0 } else { 1 }, Ordering::SeqCst) {
which is a hard syntax error, so the file never compiles:

    error: expected `{`, found `;`
      --> t05_rust.rs:250:16
       |
    250 |     while i < 3; __SH_RC.store(...) {
       |     ----- -----^ expected `{`

Emitted from `src/rust_backend.rs` (the `__sh_while_ran` gensym sites, lines ~7484 and
~10450). This is the same family the earlier rust triage round already filed with
t36/t37/t61/t93 — one bug, many examples — so it wants ONE fix in the while renderer,
not ten.
