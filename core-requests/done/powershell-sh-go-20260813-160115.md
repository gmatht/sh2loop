# powershell-sh-go: the A1 comparison expression (BinOp Eq/Ne/Lt/Gt/Le/Ge) is Perl-only in the ESTree renderer — comparison_operator is inexpressible

## NEED

`expr_to_estree` in src/shir.rs must render the six value-comparison
`IrExpr::BinOp` ops — `Eq`, `Ne`, `Lt`, `Gt`, `Le`, `Ge` — as native JS
binary expressions, instead of falling into the terminal
`other => unreachable!("Perl-only IR expression reached the ESTree
renderer: {other:?}")` (src/shir.rs:29350). The exact operator table
already exists in src/js_backend.rs:169-197 (`Eq` → `==`, `Ne` → `!=`,
`Lt` → `<`, `Gt` → `>`, `Le` → `<=`, `Ge` → `>=`; parens around the
binary). `And`/`Or`/`Not` already have status-semantics arms in
`expr_to_estree` — they are a different concern (command exit-status
protocol) and are NOT what's missing; the missing set is the six
value-comparison ops.

No contract/schema change is needed: `"BinOp"` is already serialized
(shir_json.rs:305-308) and deserialized (shir_json_in.rs:755) by the A1
contract, and the Perl backend already renders it — only the ESTree
renderer lacks the arms.

## WHY

The coverage hook reports `comparison_operator`
(wharflab/tree-sitter-powershell grammar rule; the `-eq -ne -lt -le -gt
-ge -like -match -contains …` family) as a parser node no testdata
example exercises. The reason no example exists: the frontend cannot
express the construct end-to-end, and the blocker is the shared core.

This is NOT a by-design subset refusal. PLAN_POWERSHELL_F.md's v1
mapping table explicitly plans `-eq -ne -lt -le -gt -ge` →
`== != < <= > >=` ("the test grammar"), §5 plans `t10_cmp.ps1`
(-eq/-ne/-lt/-and/-or), and the pinned-refusal list excludes only the
pattern/collection operators (`-like -match -contains`, plus the
case-sensitive `-c…` and explicit `-i…` variants). The frontend's
`lowerExpr` default-refuses today only because the rung is unlanded
(REFUSE > GUESS), not excluded.

The frontend could express it if the ESTree side had the node —
lower.go needs only `parenthesized_expression` and
`comparison_expression` cases in `lowerExpr` (walk the two
`unary_expression` operands, map the `comparison_operator` text
`-eq/-ne/-lt/-le/-gt/-ge` → `Eq/Ne/Lt/Gt/Le/Ge`, refuse the by-design
pattern operators), emitting the A1 `BinOp`. But the gate cannot
consume that emit today:

1. Ingress acceptance (`make test` runs `debashc --shir-in-estree` on
   every emit) PANICS on any program whose IR contains the comparison
   BinOp — exit 101, so the gate fails:
   `internal error: entered unreachable code: Perl-only IR expression
   reached the ESTree renderer: BinOp { lhs: Int(1), op: Eq, rhs:
   Int(2) }` (src/shir.rs:29350, `--shir-in-estree` on a valid-A1 emit).
2. The executed-stdout oracle (estree-runner) therefore cannot run a
   comparison program at all.

No workaround exists inside the current contract: `Arith` `Bin "=="`
renders but prints `0`/`1` (bash `$((1 == 2))` semantics); the runtime
`test` Call returns a JS boolean that stringifies `true`/`false`; the
`Bool` node renders `true`/`false`. Live pwsh 7.6.4 prints
`False`/`True` (`Write-Output (1 -eq 2)` → `False`; verified against
/snap/powershell/current/opt/powershell/pwsh) — so the eventual t10_cmp
pin needs the value-comparison node rendered; the pwsh `True`/`False`
text convention is then a frontend-side lowering decision (Ternary wrap
over the rendered cond — the frontend's job once the cond renders).

Note: in BARE argument position (`Write-Output 1 -eq 2`) the grammar
parses `-eq` as `command_parameter`, not `comparison_operator` — the
construct is reachable only in expression position
(`Write-Output (1 -eq 2)` → `parenthesized_expression` →
`comparison_expression` → `comparison_operator`), so the frontend
rung needs the `parenthesized_expression` case too.

## MINIMAL-CORE-CHANGE

In src/shir.rs `expr_to_estree`, add one arm for the six
value-comparison BinOps, mirroring src/js_backend.rs:169-197:

```rust
IrExpr::BinOp { op: BinOpKind::Eq | BinOpKind::Ne | BinOpKind::Lt
             | BinOpKind::Gt | BinOpKind::Le | BinOpKind::Ge,
                lhs, rhs } => {
    let l = expr_to_estree(lhs);
    let r = expr_to_estree(rhs);
    let js_op = match op { /* Eq=>"==", Ne=>"!=", Lt=>"<", Gt=>">", Le=>"<=", Ge=>">=" */ };
    Expr::BinaryExpression { operator: js_op, left: Box::new(l), right: Box::new(r), .. }
}
```

- No runtime helper, no contract/schema change (`BinOp` round-trips
  through shir_json.rs / shir_json_in.rs already), no Perl-backend
  change (it renders BinOp today).
- The bash corpus never emits a value-comparison BinOp into an
  ESTree-reachable position (bash conditions go through the `test`
  text channel; `$((…))` goes through `Arith`), so `./fail-estree`
  must stay at the trusted baseline — verify it, plus
  `cargo test --lib`.

## FAILING-CASE

Minimal PowerShell program (the construct the plan maps; parses clean
in the vendored grammar — `comparison_expression` with
`comparison_operator` `-eq`):

```powershell
Write-Output (1 -eq 2)
```

- Live pwsh 7.6.4 reference stdout: `False`.
- Frontend today (unlanded rung, not by design):
  `./powershell-sh-go --shir` → `REFUSE: expression
  "parenthesized_expression" near "(1 -eq 2)"` (exit 1).
- The A1 the frontend will emit once the rung lands — valid per the
  contract today (the deserializer accepts it):

```json
{"type":"BinOp","op":"Eq","lhs":{"type":"Int","value":1},"rhs":{"type":"Int","value":2}}
```

- Core today, on that A1 (or on the equivalent `debashc`-shaped
  program): `debashc --shir-in-estree` panics —

```
thread 'main' panicked at src/shir.rs:29350:18:
internal error: entered unreachable code: Perl-only IR expression
reached the ESTree renderer: BinOp { lhs: Int(1), op: Eq, rhs: Int(2) }
```

— exit 101, so the gate's ingress loop fails any comparison emit and
the stdout oracle cannot run it. With the renderer arms landed, the
frontend worker lands the pinned testdata example
(t10_cmp per PLAN_POWERSHELL_F §5) and the coverage node goes green.

## OUTCOME: implemented — expr_to_estree now renders the six value-comparison BinOps (Eq/Ne/Lt/Gt/Le/Ge → ==/!=/</>/<=/>=, the js_backend.rs operator table) as native JS BinaryExpression, replacing the `unreachable!` panic. No contract change (BinOp already round-trips); `--shir-in-estree` on the request's exact A1 (`{"type":"BinOp","op":"Eq","lhs":Int(1),"rhs":Int(2)}`) renders `{"type":"BinaryExpression","operator":"==",...}` and executes. The bash corpus never emits value-comparison BinOps into ESTree-reachable positions — verified: ./fail-estree 521/521 (estree_failed 0), ./fail 320/201, cargo test --lib 253/0. The frontend-side rung (lowerExpr `parenthesized_expression`/`comparison_expression` → BinOp, t10_cmp.ps1, the pwsh True/False text convention as a Ternary wrap) is the powershell worker's job.
