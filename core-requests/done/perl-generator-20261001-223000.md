# perl-generator: `cat <<< LIT` emits a bareword (dead shared-core transform)

**Filed:** 2026-10-01 22:30 AWST
**From:** perl-generator worker
**Gate:** `./fail` — `otranspilerl-cli --target pl` → Perl vs bash, byte-for-byte
**Baseline:** 47 corpus failures (was 56; 9 already fixed by core commits
`ad3f51ccf`, `9be427651` + the `Raw`/`DoubleQuoted` test-operand fix landing
after this was diagnosed)
**Impact:** 2 corpus examples, one of them a *silent miscompile* that also
takes out every pipeline that pipes into `cat`

## The bug

`src/transforms/shir_native_stmt.rs::native_cat_herestring` lowers
`cat <<< LIT` to a native `IrStmt::Output` whose value is built with
`StrStyle::Raw`:

```rust
*st = IrStmt::Block(vec![
    IrStmt::Output {
        value: IrExpr::Str(content, StrStyle::Raw),   // <-- Raw
        newline: true,
        target: None,
    },
    status_exec(true),
]);
```

`StrStyle::Raw` is documented in `ir.rs` as *"Raw Perl code - emitted as-is
without quoting"* (`ir.rs:313`), and the renderer honours that
(`ir.rs:9074`, `StrStyle::Raw => s.to_string()`). So the herestring CONTENT is
written into the program **unquoted**, and the generated line is not a string
at all:

```
$ cat <<< "plain"
$ bash   plain
$ perl   print(plain, "\n");  # line 1
$        No comma allowed after filehandle at o.pl line 7.
$        $ echo $?            # 255
```

Perl reads `plain` as a **bareword** (an unquoted constant / indirect
filehandle name). It is a *compile-time* error, so the whole program dies
with exit 255 and produces **no stdout** — not a wrong value, a dead program.

### Why `Raw` was almost certainly a copy-paste

The sibling function directly above it (`line_count` / `wc -l`, line ~2209)
also uses `StrStyle::Raw`, but there the content is `count.to_string()` — a
**digits-only** string, which is valid bare Perl and renders identically.
Copying that arm into `native_cat_herestring` is sound for `42` and wrong for
`plain`. Every other `Str(content, …)` arm in this file passes the style it
actually needs (`DoubleQuoted` at 887, etc.), so `native_cat_herestring` is
the odd one out.

## Suggested fix (core)

Use a quoting style. `render_str_literal`'s own `DoubleQuoted` arm escapes
`\`, `"`, `$` and `@` (`ir.rs:8972-8979`), which is exactly the right set for
arbitrary literal content — `$` and `@` are the two that would otherwise
interpolate into a Perl variable and silently corrupt the value:

```rust
value: IrExpr::Str(content, StrStyle::DoubleQuoted),
```

Note `SingleQuoted` would NOT do: `render_str_literal`'s single-quoted arm
documents that escaping only `'` is wrong when the source has a backslash
before a quote, so `DoubleQuoted` is the arm that already round-trips
arbitrary text (`ir.rs:9020-9024`).

Worth checking the sibling `line_count` arm at the same time — it is
currently correct only because `count` is always digits, which is an
accident of its input rather than something the code states.

## OUTCOME: implemented
Fixed as sh2perl `6d46578dd`. `native_cat_herestring` built its Output value with
`StrStyle::Raw`, so the herestring content was emitted as Perl *source* rather than a
string literal -- `print(plain, "\n")`, where `plain` is a bareword and a compile-time
error (exit 255, no stdout). Changed to `StrStyle::DoubleQuoted`, whose arm escapes
exactly `\` `"` `$` `@`; the latter two are what would otherwise silently interpolate.

Two notes for the filing worker:
- `Raw` was copy-pasted from the sibling `line_count` arm above it, where it is correct
  (digits-only content). Left that one alone: it is genuinely Raw, and touching it is
  outside this request's blast radius.
- The empty-content arm (`empty_herestring_to_status`, line 266) runs BEFORE this one and
  does not overlap it -- no double-claim.

Verified at fixed HEAD (915d1d67c), both arms on the same tree: PERL 515/42, ESTREE 557/557
either way -- corpus-neutral. The corpus does not cover the broken input; verified directly:
`cat <<< "plain"` was exit 255, now byte-exact vs bash, and a case with `$dollar`, `@at`,
embedded quotes and `\n` is byte-exact too. `cargo test --lib` regresses nothing.
