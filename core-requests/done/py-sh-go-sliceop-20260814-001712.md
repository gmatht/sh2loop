# py-sh-go: sliceop still inexpressible — A1 step field landed (done/ py-sh-go-sliceop-20260813-222910) but the frontend-side emit arm it deferred never landed; the frontend still refuses a[i:j:k]

## NEED
The py-sh-go frontend must lower Python's **slice step** (grammars-v4
Python3 rule `sliceop`: `':' test?` — the optional THIRD part of a
`subscript_`: `test? ':' test? sliceop?`, i.e. `a[1:6:2]`, `a[1:6:]`,
`a[::2]`).

The **A1 CONTRACT side of this need is already DONE**: the optional 5th
arg `step` on `param("slice", name, start, len[, step])` (positive-int
step; absent = today's contiguous behavior) was implemented by the
estree worker via the completed requests
`core-requests/done/py-sh-go-sliceop-20260813-194705.md` and
`core-requests/done/py-sh-go-sliceop-20260813-222910.md` — the runtime
step filter lives at harness/sh2-namespace.mjs (~line 2822,
`arr.slice(off, off+len).filter((_, i) => i % step === 0)`), and I
verified end-to-end on 2026-08-14 that a hand-emitted 5-arg document
(`param("slice","a","1","5","2")`) ingresses via
`debashc --shir-in-estree`, renders, and the estree-runner prints
`b d f` for `a[1:6:2]` on `["a".."f"]` — byte-identical to python3.

WHAT IS STILL NEEDED is the **frontend-side emit path** that both
completed requests explicitly deferred ("The frontend side … is
py-sh-go's own fix and lands after the contract has the shape — same
pattern as the star_expr/lambdef requests") — it never landed
(frontends/py-sh-go has no main.go commit since 1fa67572, which
predates both requests):

1. `frontends/py-sh-go/main.go` `parsePrimary` `[` arm (~line 1281):
   after the optional `: end`, accept an optional second `:` + step
   expr (`test? ':' test? (':' test?)?`) instead of failing on
   `expectOp("]")`; handle the empty-start (`[::2]`) and empty-step
   (`[1:6:]`) forms (nil parts stay nil).
2. `SubscriptE` (~line 71): add a nil-able `SliceStep Expr` field.
3. `subscriptIR` (~line 2164): emit the optional 5th arg —
   `param("slice", name, start, len[, step])` with step from
   SliceStep (nil → omit, byte-identical to today's emits; empty third
   part `a[1:6:]` → emit `"1"`); v1 scope: positive ints only (the
   runtime's `stepOf` guard already enforces this), negative steps
   (`a[::-1]`) stay a follow-up.

## WHY
The coverage hook (`rules-gap.sh py-sh-go`) reports `sliceop` as a
Python3 grammar rule no testdata example exercises (verified
2026-08-14: it is the top reported gap; it is NOT ledgered in
refused-py-sh-go.txt / bugs-py-sh-go.txt / core-pending-py-sh-go.txt).
No example can be created: the frontend still refuses every sliceop
form (verified 2026-08-14 against the built `./py-sh-go --shir`):

    $ printf 'a = ["a","b","c","d","e","f"]\nprint(" ".join(a[1:6:2]))\n' | ./py-sh-go --shir /dev/stdin --raw
    py-sh-go: parse: expected "]"
    exit=2

(`a[::2]` / `a[::-1]` / `a[1:6:]` all refuse likewise — `unexpected
token ":"` / `expected "]"`.) This is NOT a by-design subset refusal:
py-sh-go has no FRONTEND.md; refused-py-sh-go.txt has no slice/step
entry; PARSER_GAPS.md's py-sh-go table categorizes `sliceop` as
category 1 (A1-EXTENSION — "step slices: the shell param-slice idiom
has no step; `a[1:3]` maps (t37/t66), `a[1:3:2]` can't"), the category
whose section ("Escalating the A1-EXTENSION items") describes rows as
"requests waiting to be filed", NOT subset decisions; and the 2-part
slice IS supported and covered (t37_substring, t66_array_slice lower
to the 4-arg `param("slice", …)`).

So the construct is inexpressible end-to-end (frontend emit → ingress
acceptance → executed-stdout oracle) even though every A1/runtime piece
is in place — the sole remaining blocker is the frontend-side arm. The
coverage worker cannot create the testdata example until the frontend
emits, and the completed requests' own plan ("the frontend fix lands
after the contract has the shape") has no other owner: the py-sh-go
frontend worker is failure-driven (only invokes pi on a RED gate), and
this gate is green. This request is the only channel a green-gate cycle
has to route the missing frontend-side piece.

## FAILING-CASE
Minimal Python program (python3 runs it fine):

```python
a = ["a", "b", "c", "d", "e", "f"]
print(" ".join(a[1:6:2]))
```

python3 stdout: `b d f` (indices 1, 3, 5).

Variants that must also work once the frontend arm lands (the contract
already handles all of them — verified): `print(" ".join(a[::2]))` →
`a c e`; `print(" ".join(a[1:6:]))` → identical to `a[1:6]` (`b c d e f`).

Current behavior (verified 2026-08-14):
`./py-sh-go --shir` fails with `py-sh-go: parse: expected "]"` (or
`unexpected token ":"` for the empty-start forms), exit 2 — so no
testdata example can cover `sliceop`, and the construct remains
inexpressible end-to-end even though every A1 contract / runtime piece
for the 5-arg step slice is in place.
