# triage: python backend can't render what the c-sh-go frontend emits

## NEED
The python renderer must handle this A1 (the estree reference renders it and
matches native).

## FAILING-CASE
frontend c-sh-go, example t10_string_pointer.c (cross-product pair).

## EVIDENCE
estree matches native; python differs

## OUTCOME: implemented

Two python-renderer defects (`sh2perl/src/python_backend.rs`), both reproduced
from this pair's A1:

1. `param("slice", s, off, "")` — an EMPTY length means "to the end of the
   string". `expr_as_num` folded it to 0, so the renderer emitted `s[1:1+0]`
   (an empty slice) and the C frontend's `char *t = s + 1` printed nothing.
   Empty length now renders `s[off:]`.
2. `__sh_env()` skipped every global whose name starts with `__`, which also
   matches the C frontend's hoisted temps `___tN` (THREE underscores). The
   `bash -c` seam then read `$___t1` as unset and `printf '%c'` emitted a NUL
   byte. The filter now keeps `___`-prefixed names (python's own dunders are
   exactly `__x__`) in both the module-global and the function-local form.

Verified: `harness/triage.sh c-sh-go t10_string_pointer.c python` → PASS
(byte-identical to the estree oracle: `hello` / `h` / `ello` / `o`).
`cargo test --lib python_backend` 7/7.
