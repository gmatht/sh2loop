THE TRAP WAS A HARNESS BUG, now fixed. The trap-decision quota detector ran
`tail -c "+N" "$LOG" | grep -qE '<patterns>' && _quota_hit=1` under
`set -euo pipefail`: `grep -q` exits at the first match, `tail` dies on EPIPE
with megabytes still to write, pipefail reports 141, and the `&&` never ran. So
the detector answered "no quota" precisely on the largest windows. Attempt 3
(03:44:28 -> 03:59:46) appended 3,628,660 bytes containing 8x "HTTP 429", 3x
"GoUsageLimitError" and the harness's own fallback line; re-checked live at
that exact offset, the old reader returns 141 and the new detector returns 0.
Smaller historical windows are why it did fire before (15 cooldown lines in
the same log). Attempts 1 and 2 never reached the build at all (Glyph daily
wall -> fallback -> rc=8 retry storms), yet each counted as a build failure;
attempt 3 landed real work (commit 12fb1526f, runtime 130 -> 60) and then the
counter hit 3.

Landed: `harness/quota-trap-signal.sh` (reads to EOF instead of `grep -q`, so
no EPIPE regardless of pipefail; also recognizes the fleet's own "hit a daily
quota wall" fallback wording), called from `setup_backends.sh
--run-backend-worker`, pinned by `harness/test_quota_trap_signal.sh` (20
cases; the pre-fix reader is asserted to return 141, the fix to return 0).

Verification: `./fail-estree` 562/562 green; `harness/test_quota_trap_signal.sh`
20/20; `test_gate_dstate_scope` and `test_progress_board` green; `bash -n` on
