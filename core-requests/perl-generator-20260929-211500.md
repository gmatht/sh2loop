# perl-generator: the 58 corpus failures are ALL inside `ir.rs::shir_to_perl` (shared core) — the Perl generator is not in the worker's owned surface

Filed by the `perl-generator` worker (the `sh2perlgenerator.service` loop).
Gate: `./fail` (otranspilerl-cli --target pl → Perl → run vs bash, byte-for-byte
stdout + exit code + side effects). Baseline reproduced this run: **58 failures,
trusted baseline 0.**

## WHY THIS IS AN ESCALATION AND NOT A FIX

My assignment scoped me to `sh2perl/src/perl_generator_fixed.rs` and `harness/`.
Neither can hold these fixes:

1. **`sh2perl/src/perl_generator_fixed.rs` does not exist as a generator.** It
   is a 3-byte file (two newlines) and it is **not** declared in
   `sh2perl/src/lib.rs` — it is not compiled at all.

   ```
   $ xxd sh2perl/src/perl_generator_fixed.rs
   00000000: 0a0a 0a                                  ...
   ```

2. **The renderer on the gate path is `ir::shir_to_perl` in `sh2perl/src/ir.rs`.**
   The CLI dispatch is `otranspilerl/src/lib.rs:750`:

   ```rust
   "perl" => debashl::ir::shir_to_perl(&prog),
   ```

   `ir.rs` is explicitly listed in my task's shared-core exclusion set, along
   with `shir.rs`, `estree.rs` and `parser/`.

3. **`sh2perl/src/perl_backend.rs` is a second, independent renderer, NOT on
   the gate path.** Despite its docstring ("branch `backend/perl`",
   "`shir_to_perl(&IrProgram) -> String`"), `ir::shir_to_perl` never calls it
   (`grep -n "perl_backend::" sh2perl/src/ir.rs` → no hits). It is a
   parallel implementation of the same public signature.

So there is currently **no file I am permitted to edit that changes the Perl
output of `./fail`.** Every defect below is in `ir.rs`.

### Recommended structural fix (for whoever owns this)

`perl_backend.rs` (3,241 lines, explicitly "worktree-local", compiles, never
reaches the gate) and `ir.rs::shir_to_perl` are two implementations of one
function. Either should be deleted and the other moved to the worker-owned
location, with `lib.rs`'s `"perl" =>` arm repointed at it. That is a core
change, and it is what would make this class of failure fixable by the
backend worker at all.

## THE DEFECTS

Each entry is verified end-to-end: `./otranspilerl/target/debug/otranspilerl-cli
--target pl <example>` → the emitted Perl → run under `perl -M5.010` and
diffed against `bash <example>`. Diagnostic helper: `harness/pg-diff.sh`
(single example, byte diff) and `harness/pg-batch.sh` (batch) — both added by
this worker under `harness/`, which is in scope.

---

### A. `done … < FILE` never reached — every pipeline/loop with a redirect emits NOTHING (11 examples)

`IrStmt::Redirect`'s redirect-rebuild path bails out with
`die "otranspilerl: shIR construct not yet supported by the Perl backend (redirect)\n";`
when the inner is a **pipeline** rather than a single command. A `die` at
top level aborts the whole program, so *every line printed before it is lost
too* — the failure is "missing output", not "wrong output".

Minimal repro — `examples/091_while_pipe_var.sh` is 7 lines:

```bash
count=0
while read -r line; do
    count=$(( count + 1 ))
    echo "$count: $line"
done < /etc/passwd | head -3
```

emits:

```perl
$count = "0";  # line 4
die "otranspilerl: shIR redirect not yet supported by the Perl backend\n";  # line 5
__sh_uu_run('head', '-3'); $main_exit_code = $CHILD_ERROR = $__sh_uu_rc;
```

→ `perl_bytes=0` vs `bash_bytes=125`. The `stmts_to_shell_cmd(inner)` arm
(`ir.rs:2161`) already builds a correct `bash -c` string for a command
redirect; it just is not reached for a multi-statement inner, and the `_`
fallback arm (`ir.rs:2310`) only handles `w|wc|a|r+` on a *non-pipeline* inner.

**Fix shape:** in the `None` branch, when the inner contains a pipeline/loop,
materialize the pipeline to a temp file and `open` it on STDIN (the shape
`cat_heredoc_body`/`native_mapfile_read` already use), instead of `die`.

Affects: `091_while_pipe_var`, `096_head_procsub`, `070_gnuisms_thorough`,
`063_11_complex_while_loop`, `063_hard_to_parse`, `parse-eval-multiline`,
`parse-dollar-paren-pipe`, `parse-redirect-in-case-pattern`, `heredoc-unclosed`,
`qx-var-builtin-cd`, `sync-direct-call-await`.

### B. Tilde expansion is dropped in `[ ]` operands (1 example)

`flat_operand` (`ir.rs:8042`) special-cases `${…}` but its `t == "~"` /
`starts_with("~/")` arms are **below the `return`**, and are never reached for
`[ … ]` tokens, so the literal is emitted:

```perl
$CHILD_ERROR = ((($__nocasematch) ? lc('~') eq lc($ENV{HOME}) : '~' eq $ENV{HOME})) ? 0 : 1;
```

`examples/043_home.sh` (`[ ~ = "$HOME" ] && echo 1 || echo -`) then prints
`-\n-\n-\n` instead of `1\n-\n3\n`. The correct arms already exist 20 lines
below in the same function — they are simply not consulted on this path.

### C. `eval` is assigned, not executed (1 example)

`examples/063_12_complex_eval.sh`:
```bash
eval "result=\$(( \${var:-0} + \${array[\${index:-0}]:-0} ))"
echo "Eval result: $result"
```
emits `$result = "\$(( \${var:-0} + … ))";` — a string assignment. The `eval`
builtin is treated as a plain assignment, so the Perl program prints the
unexpanded source text. bash prints `Eval result: 0` (bash performs the
arithmetic during `eval`; unset vars are 0, so the result is `0`).

### D. `local -a args=("$@")` never populates `@args` (1 example)

`examples/063_09_complex_function_parameter_handling.sh` emits:

```perl
sub complex_function {
    local @ARGV = @_;
    my $__argc = @ARGV;
    …
    while (($i < scalar(@args))) {     # @args is never declared or assigned
```

`@args` is referenced but nothing ever binds it, so the loop never runs and
`echo "Processed ${#options[@]} options"` prints 0 instead of 4.

### E. `$!` after a script with no background job must be empty (1 example)

`ir.rs:1364` declares `our $__sh2_last_bg = 0;` and `ir.rs:3783` maps `"!"` to
`$__sh2_last_bg`. bash: `$!` is **unset** (expands to the empty string) when no
background job has been started; `examples/dollar-bang.sh` prints
`background: ` (trailing space). The generator prints `background: 0`. The
initializer must be `''`, not `0`.

## PROGRESS: core owner verified the escalation (the diagnosis is correct: the gate
renderer really is ir::shir_to_perl, and perl_generator_fixed.rs really is a 3-byte
undeclared file) and traced defect A to its exact root cause. NOT completed — a

WHAT I ESTABLISHED about defect A (the 11-example class). The `die` is real and it
aborts the whole program, so output printed BEFORE the redirect is lost too —
reproduced verbatim on 091_while_pipe_var: perl_bytes=0 vs bash 125, exit 255.
But the fix is NOT the temp-file shape the report proposes. The standalone fd-0
read case already works (092 emits a correct `local *STDIN; open(STDIN,...)`
native loop). Only the `redirect(whileLoop, specs) | pipeline` shape dies. Three
gaps, all in ir.rs, all required:

1. stmts_to_shell_cmd has no `whileLoop` arm. The loop arrives as a Call wrapping
   two Arrows (cond, body), NOT as IrStmt::While — so adding a statement-level
   While arm (as I first tried) is a no-op. The arm belongs in expr_to_cmd.
2. The body carries an Assign (`count=$((count+1))`), which the rebuild cannot
   express, so it returns None and the redirect falls through to the die.
3. Arithmetic RHS must rebuild as bash `$(( … ))`. Routing it through the
   existing bash_word_for emits the PERL text `int(($count + 1))`, which a
   `bash -c` string prints literally — the loop then ran and printed
   `int((0 + 1)): root:x:0:0:...` instead of `1: root:x:0:0:...`. A new
   bash_arith_ast_for walking ArithAst::{Num,Var,Ident,Index,Bin} is required,
   and it must REFUSE ops whose bash text differs from the source symbol
   (notably Pow: `**` is `^` in bash arithmetic) rather than guess.

With all three, the repro emits the correct 3 lines and exits 0. The changes are
small and belong to whoever finishes the ir.rs pass; re-apply on top of the
current tree (my working copy was overwritten by the concurrent writer mid-round
and I reverted rather than leave a half-merge). Remaining after A: defects C-F
(eval, local -a, $!, primes/return, assoc arrays) are each separate and untouched.
The report's structural recommendation (delete one of the two Perl renderers)
remains valid and is a core change, but it is far larger than one round.
