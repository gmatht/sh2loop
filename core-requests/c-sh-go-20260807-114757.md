# c-sh-go: grow IrType::Float (and double) in the A1 type layer

## NEED
A first-class float/double type in the A1 contract's type annotations.
The typed-node-ir growth (core-requests/done/typed-node-ir-20260806.md)
added IrType::Int(width), Ptr, Array, Struct — but no float. Add
`IrType::Float(u8)` with width 32/64 (double = Float(64)), mirroring the
existing `IrType::Int(width)` pattern, serialized beside var_types /
var_const / var_lifetimes on IrProgram.

## WHY
c-sh-go (C source -> A1 shIR) must parse `double x = 1.5;` and
`float f = 2.5f;` to cover the language ladder (gap 4 of the roadmap:
structs/unions/typedef, float/double, sizeof). Today the frontend
REFUSES float programs outright (the type layer has no float, so the
emitter has no honest representation), so float code can't be
transpiled at all. The type annotation is the enabling first step: once
a var can be typed Float, the frontend can emit float assignments and
the estree.rs renderer decides the lowering (JS Number/parseFloat arith
vs the Int/Str arith nodes) without the frontend guessing a
string-typed representation.

## MINIMAL-CORE-CHANGE
Additive only — existing Int/Str/Any emissions stay byte-identical:
- src/shir.rs: extend the IrType enum with `Float(u8)` (bit width,
  32/64) — same shape as Int(width).
- shir_json.rs: serialize Float(w) (e.g. {"kind":"Float","width":64}),
  alongside Int, in var_types (and any other type-annotation site).
- shir_json_in.rs: accept the "Float" kind in the round-trip
  deserializer (keep rejecting unknown kinds as it does today).
- contract_version stays 1 (additive field, same pattern as the
  earlier annotation siblings).
- Out of scope here (the estree worker's call): the arith node's
  integer-only semantics — float-typed vars may need a parseFloat arith
  lowering in estree.rs; the type annotation is the prerequisite.

## FAILING-CASE
frontends/c-sh-go/testdata/t23_float.c (added with the roadmap ladder):

```c
#include <stdio.h>
int main(void) {
    double x = 1.5;
    double y = x * 2.0;
    printf("%.1f\n", y);
    return 0;
}
```

Currently: `./c-sh-go --shir t23_float.c --raw` refuses
(`lex: unexpected "."` on the `1.5` literal) -> exit 1. Expected once
the type layer lands: the frontend parses float literals, marks x/y as
Float(64), and the transpiled run prints `3.0` like gcc.
