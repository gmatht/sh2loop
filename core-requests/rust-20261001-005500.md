# c: power-of-2 strength reduction rewrites `% 2^k` to an unsigned mask with NO non-negativity proof — it is unsound for negative operands

Filed by: the **rust BACKEND** worker, while auditing `cargo test --lib` output that
the rust gate's own report attributes to rust. **None of the 13 failures are rust
tests** (0 `rust_backend::`), so this is not a rust concern and is escalated rather
than fixed. Measured on `main-worktree` @ `9f4c6b8a8`, 2026-10-01 00:5x.

This is a **PRODUCT defect, not a test defect.** The five `refuses_*` C tests are
correct and are catching a real soundness hole.

## NEED

`src/c_backend.rs:11288-11300`, the integer `/` and `%` strength reduction:

```rust
} else if *op == "/" || *op == "%" {
    // Strength-reduce power-of-2 divisors: % 2^k -> & (2^k-1),
    // / 2^k -> >> k. Eliminates ~30-cycle div (1-cycle and/shift).
    if let crate::ir::ArithAst::Num(d) = rhs.as_ref() {
        if *d > 0 && (*d & (*d - 1)) == 0 {
            if *op == "%" {
                let mask = *d - 1;
                return format!("((unsigned long long)({l}) & {mask}ull)");
            } else {
                let shift = (*d as u64).trailing_zeros();
                return format!("((unsigned long long)({l}) >> {shift}u)");
            }
        }
```

The guard is **`d > 0 && d is a power of two` and nothing else.** It never asks
whether the dividend is non-negative, and it does not ask whether the unsigned
shift is even the right transform.

**`x % 2^k == x & (2^k - 1)` holds ONLY for `x >= 0`.** For a negative `x` in
two's complement, the sign bits are set, so `x & (2^k-1)` yields the correct
non-negative residue — but a comparison against the mask (`& 1ull) == 1`)
inverts relative to the signed modulo. `src/c_backend.rs:3843` (`ver_nested_mods`)
has the same shape of hole and gates only on `d > 0`.

## WHY

The emitted C is not a faster equivalent of the bash — it computes a **different
predicate**. `let_compare_modmask_refuses_nonzero_test` (c_backend.rs:42561)
asserts exactly this, and its own comment states the invariant the code violates:

> `((v % 2 == 1))` is NOT a bitmask shape (negative odd v gives -1, but v&1 is 1 —
> the test differs): native `%`, no mask.

Its render, with `v` a plain signed `long long`:

```c
while (((((unsigned long long)(v) & 1ull) == 1))) {
    v++;
}
```

**FAILING-CASE, executed (not argued):** for `v = -3`,

| expression | value |
|---|---|
| `v % 2 == 1` | `0` (false) |
| `(unsigned long long)(v) & 1ull == 1` | `1` (true) |

The loop that bash runs **zero** times, the translation runs **once** — and then
loops on `-3, -2, -1, 0, …` with different behaviour at every step. Any corpus
example reaching a negative-capable `% 2^k` or `/ 2^k` compiles, runs, and returns
a wrong answer with no diagnostic. `tests/coreutils` is unaffected: its `%` cases
use non-negative operands, which is why this has never been caught downstream.

## MINIMAL-CORE-CHANGE

Gate the rewrite on a **non-negativity proof for the dividend**, and treat the
unsigned `>>` for `/` the same way (floor division of a negative is not a shift).
The gate must **refuse** — emit the native signed `%` / `/` — whenever the proof is
absent. A miss costs one division; a wrong answer costs correctness.

The two sibling tests already specify the intended contract, so the proof obligation
is pre-existing and simply unimplemented:

```rust
// c_backend.rs:42658 — "Bare `w % 8` with w unknown: no proof → signed (miss, safe)."
fn unsigned_mod_refuses_unranged() { … assert!(!out.contains("unsigned long long")) }

// c_backend.rs:42641 — refuses a negative-capable dividend
fn unsigned_mod_refuses_negative_capable() { … }
```

Range facts are already available in this file (`VerCtx`, `ver_state_empty`,
`ver_threshold`, the `var_types` verdicts per AGENTS.md "the sh2.* boundary") — the
rewrite needs to consult the same source the refusing tests expect it to consult.
