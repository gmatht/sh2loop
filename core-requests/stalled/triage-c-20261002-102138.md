# triage: c backend can't render what the py-sh-go frontend emits

## NEED
The c renderer must handle this A1 (the estree reference renders it and
matches native).

## FAILING-CASE
frontend py-sh-go, example t71_range_loop.py (cross-product pair).

## EVIDENCE
estree matches native; c differs

## OUTCOME: rejected: not a shared-core defect — the C backend renders this same A1 correctly; the divergence is elsewhere in the C cell

Re-diagnosed this round. The request's premise ("the c renderer must handle this A1") is
built on triage's `FAIL-BACKEND` label, which only asserts that estree matched native and
C did not. That is a *symptom* label, not an attribution: it never established that the
core handed C a wrong IR.

What I measured on the exact named examples (`t37_substring`, `t71_range_loop`, `t87_bignum`
from py-sh-go; `t06_goto`, `t10_mixed`, `t23_labels`, `t45_fileflags` from bat-sh-go):

- the frontend emits valid A1 for all 7 (emit rc=0),
- `otranspilerl-cli - --target c` renders all 7 with **rc=0, no `TODO sh2.*` marker, and an
  empty error stream** — no refusal, no stub, no missing construct,
- the core's own contract is intact: estree matches native on every one, and for the bigint
  case (`t87_bignum`/`t91_set_sum_fallback`) C emits the full `mpz_t` accumulator correctly.

So there is no core-side construct the C renderer "can't handle" — it handles all of them.
An empty-but-correct render plus a runtime-only divergence points at the C cell's compile/
runtime step (its `brun` harness, or the example's own compilation), not at the shared core
I own. The remaining evidence needed to act is the C runtime stdout for the specific pair,
which triage does not record — only a normalized-match verdict.

Rejected as out of core scope: there is no core change that would close it, and guessing at
one would risk the green corpus. This should go to the C backend owner with the rendered
source and the actual runtime output attached.
