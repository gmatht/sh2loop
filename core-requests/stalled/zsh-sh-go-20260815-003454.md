# zsh-sh-go: RE-OPEN — A1 still has no correct lowering for the translated string `$"..."` (ts node `translated_string`); the done/ request is unimplemented

Re-activates `core-requests/done/zsh-sh-go-20260814-200005.md` (the
`translated_string` node), which sits in `done/` but is UNIMPLEMENTED:
verified 2026-08-15 against the current source and
`target/debug/debashc` (HEAD b5ae282) — `parse_string_interpolation`
(src/parser/words.rs:3400) still strips outer quotes only when the
token text starts with `"`, so the `DollarDoubleQuotedString` token
(`$"..."`, lexer regex `\$"([^"\\]|\\.)*"`) keeps its raw `$"` prefix
and trailing `"` as ONE literal part. The estree poller does not
re-read `done/`, so the gap would otherwise go silent. Companion:
`core-requests/zsh-sh-go-20260814-200005.md` (the original request;
same fix, one function).

## NEED

The shared core must lower `$"..."` (the bash/zsh translated string,
lexer token `DollarDoubleQuotedString`) into an A1 shape that (a)
round-trips shir_json.rs / shir_json_in.rs, (b) the zsh frontend can
emit byte-identically (it ALREADY emits the target shape — see WHY),
and (c) the estree runner evaluates to the value native zsh 5.9
produces.

Root cause, pinpointed (unchanged since the original request):
`parse_string_interpolation` (src/parser/words.rs:3400) strips the
outer quotes only when the token text starts with `"`:

    let content = if string_content.starts_with('"') && string_content.ends_with('"') {
        &string_content[1..string_content.len() - 1]
    } else { &string_content };

The `DollarDoubleQuotedString` token text is `$"hello"` — it starts
with `$`, so NOTHING is stripped and the raw `$"hello"` (quotes and
dollar included) becomes one Literal part:
`Interpolate[lit "$\"hello\""]`. The `DollarSingleQuotedString` sibling
has a dedicated correct path (`parse_ansic_quoted_string`); the DQ
variant has no equivalent.

## WHY

The zsh-sh-go coverage sweep (tree-sitter node-type truth) still
reports the tree-sitter-zsh `translated_string` node (`$` + `string`,
grammar rule `translated_string`: `"$"` followed by a double-quoted
`string`) as uncovered by testdata, and NO testdata example can pass
`make test`: the byte-equality phase (phase 1) DIFFs in every context,
because the core's A1 output for `$"` cannot be byte-matched. Re-verified
2026-08-15 with the current binaries:

    echo $"hello"            # and: x=world; echo $"$x"  /  echo $"a $x b"
      native zsh 5.9          -> "$hello"   (literal $ + DQ content;
                                              this zsh build has no
                                              gettext translation)
      frontend emit (today)   -> Str "$hello" / Interpolate[lit "$",
                                  getVar(x)] / Interpolate[lit "$",
                                  lit "a ", getVar(x), lit " b"]
                                  -> estree prints "$hello"/"$world"/
                                  "$a world b"   (stdout-CORRECT; verified
                                  end-to-end through --shir-in-estree +
                                  harness/estree-runner.mjs)
      core emit (today)       -> Interpolate[lit "$\"hello\""] /
                                  Interpolate[lit "$\"", getVar(x),
                                  lit "\""] -> estree prints
                                  $"hello" / $"world" (quotes leaked;
                                  wrong for bash too — bash prints
                                  "hello" for $"hello")

The executed-stdout oracle is therefore ALREADY satisfiable with the
frontend's EXISTING lowering — the frontend does not refuse the
construct (FRONTEND.md lists no exclusion) and needs NO change — but
phase 1 fails, and the array-subscript waiver
(harness/zsh-subscript.ere) deliberately does not match `$"` (it is
the 0-based-subscript normalization class; a `$"` waiver would bless
the core's quote-leaking lowering, which is a parser bug, not a
runtime limitation — the project forbids blessing those). So the
construct stays inexpressible until the core fix lands.

No bash-corpus regression risk (from the original request, re-checked):
`grep '\$"'` over sh2perl/examples/ hits only `$` before a CLOSING
quote inside DQ strings (`echo "the price is $"`, `grep "\.txt$"`),
never the `$"`-opens-a-string construct — so changing the
`DollarDoubleQuotedString` lowering cannot affect `./fail` or the
ESTree corpus.

## MINIMAL-CORE-CHANGE

In `parse_string_interpolation` (src/parser/words.rs), handle the
`DollarDoubleQuotedString` spelling: when the token text starts with
`$"`, strip the `$"` prefix AND the closing `"` before
`unescape_interpolation_content` / `scan_interpolation_parts`, and
represent the construct so the estree runner can tell the languages
apart. Two candidate shapes (concrete arg layout open to the estree
worker; must round-trip shir_json.rs / shir_json_in.rs):

- (a) minimal, gate-unblocking: emit the content parts prefixed by a
  literal `$` part — `Interpolate[lit "$", <content parts>]`,
  collapsing to `Str "$hello"` for plain content. This byte-matches
  the zsh frontend's CURRENT emit (`Str "$hello"`,
  `Interpolate[lit "$", getVar(x)]`,
  `Interpolate[lit "$", lit "a ", getVar(x), lit " b"]` — verified
  today) with NO frontend change, and the runner already prints
  `$hello` for it (zsh-correct). Cost: the core's bash semantics for
  `$"..."` become `$hello` rather than bash's `hello` (zero corpus
  impact today, as above).
- (b) semantically clean for bash: a dedicated node/field carrying the
  translated content (e.g. a `translate(...)` func or `LocaleString`
  node with the interpolated content as its value), dispatched
  per-language in harness/sh2-namespace.mjs like the existing
  `_setLang("zsh")` split no-op: bash mode → content (`hello`), zsh
  mode → `$` + content (`$hello`). Requires the zsh frontend to follow
  the new shape (its byte-equality oracle tracks the core).

Either way the FAILING-CASE below must print `$hello` / `$world` via
`--shir-in-estree` + harness/estree-runner.mjs, and the zsh frontend's
emit must equal the core's byte-for-byte. Once the fix lands, the
zsh-sh-go worker adds `testdata/t94_translated_string.zsh` and the
byte-equality phase passes without any waiver.
