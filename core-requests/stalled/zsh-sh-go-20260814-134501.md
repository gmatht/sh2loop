# zsh-sh-go: i53-escalated Arith Assign RHS never BigInt-wrapped → ESTree path throws (t48_accum, t85_cstyle_for)

## NEED

The shared core must render an i53-escalated / `--true64` `ArithAst::Assign`
(`((s += n))`, cstyle-for init `((i = 0))`, step `((j += 2))`) with a
BigInt-clean RHS. Today the emitted JS mixes BigInt and Number and throws,
so the executed-stdout gate fails on both zsh tests.

Root cause: the render-time wrap guard `arith_mentions_true64`
(src/shir.rs:92-98 — already fixed in the estree worker's in-flight diff)
decides "wrap needed" when the Assign **target** is an Int64 var, but the
wrapper itself `wrap_true64_arith_ast` (src/shir.rs:118) still checks only
the RHS. The guard and the wrapper disagree, so for
`Assign{var: <escalated>, rhs: <non-escalated leaf>}` the guard fires, the
wrapper no-ops, and the RHS keeps its Number literal / Number-homed Ident:

- `((i = 0))` → `i = BigInt.asIntN(64, i = 0)` → TypeError: Cannot convert 0 to a BigInt
- `((s += n))` → `s = BigInt.asIntN(64, s += n)` → TypeError: Cannot mix BigInt and other types
- `((j += 2))` → `j = BigInt.asIntN(64, j += 2)` → TypeError: Cannot mix BigInt and other types

## WHY

The zsh-sh-go gate fails the executed-stdout phase on t48_accum.zsh and
t85_cstyle_for.zsh (81/83). Byte-equality with the core's own A1 emit
passes — the frontend is byte-identical; the failure is purely in the
shared A1→ESTree path, and the core's own bash frontend reproduces it
from plain bash source (`s=0; for n in 1 2 3; do ((s += n)); done; echo $s`
and `for ((i=0; i<3; i++)); do echo $i; done` fail identically), so this
is a shared-core defect, not a zsh emission gap.

The i53 escalation (SH2_ASSUME_I53, default ON) homes range-proven
numeric vars as BigInt. In t48, `s` escalates (accumulator; every write
proven-int) while loop var `n` stays Number (fed strings) — hence the
mixed `s += n`. In t85, the cstyle-for `ForInit` shape makes `i`/`j`/
`sum` escalate (analyze_var_ranges gives the init/step-written vars the
unknown range), so `i = 0` / `j += 2` mix a BigInt target with Number
leaves.

## MINIMAL-CORE-CHANGE

In `src/shir.rs`, inside `wrap_true64_arith_ast`'s nested `mentions` fn
(currently at shir.rs:118), replace

```rust
ArithAst::Assign { rhs, .. } => mentions(rhs),
```

with

```rust
ArithAst::Assign { var, rhs, .. } => {
    mentions(rhs) || true64_int_var(var) || slot_var_index(var).is_some()
}
```

i.e. mirror the Assign arm the worker already landed in the guard
`arith_mentions_true64` (shir.rs:92-98, with its comment "the TARGET
matters too: `((x = 5))` on an Int64 x must wrap the RHS literal
(BigInt("5"))"). The wrapper's `wrap` fn already handles the RHS
(`ArithAst::Assign { rhs, .. } => wrap(rhs)`) — `Num` → `Cast(Int64, Num)`
(emits exact `BigInt("N")`, no asIntN for literals) and non-slot
`Ident`/`Var` → `Cast(Int64, x)` (emits `BigInt(x)`); slot leaves stay
raw. `wrap_true64_arith` (the pre-pass, shir.rs:180) then wraps the tree
once; at render, `arith_to_estree_wrapped`'s `!arith_has_cast(a)` skips
the re-wrap, so no redundant nesting.

No other file changes. Regression risk nil: the arm only fires when the
assignment TARGET is an escalated/slot var, which previously produced
CRASHING JS (no green corpus test can exercise it); verified on the
patched build — 7 bash-corpus samples emit byte-identical ESTree JSON,
and `--true64` changes only the intended `i = 2` → `i = BigInt("2")`
wrap (the pre-existing 092_for_arith_func --true64 step-bug
`String(BigInt(i) + 1)` is untouched).

## FAILING-CASE

Both zsh corpus files fail via `debashc --shir-in-estree <a1>` +
`node harness/estree-runner.mjs`:

```
frontends/zsh-sh-go/testdata/t48_accum.zsh:
s=0
for n in 1 2 3; do
    ((s += n))
done
echo $s          # zsh prints 6; ESTree path: TypeError at `s += n`

frontends/zsh-sh-go/testdata/t85_cstyle_for.zsh:
for ((i=0; i<3; i++)); do
    echo "i=$i"
done
sum=0
for ((j=1; j<=5; j+=2)); do
    sum=$((sum + j))
done
echo "sum=$sum"  # zsh prints i=0..2, sum=9; ESTree path: TypeError at `i = 0`
```

Minimal bash repro (core's own frontend, no zsh needed):

```bash
s=0
for n in 1 2 3; do
    ((s += n))
done
echo $s
```

`debashc --shir-in-estree` on the A1 of this emits
`s = BigInt.asIntN(64, s += n)` where `n` is `Number`-homed (loop var:
`n = Number(n)`); expected after the fix:
`s = BigInt.asIntN(64, s += BigInt(n))` → prints 6. Verified: the patched
core emits exactly that and the zsh gate goes 83/83.

Estree corpus at baseline; PERL count unchanged.
