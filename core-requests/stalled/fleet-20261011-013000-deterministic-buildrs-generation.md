# fleet: make build.rs handler generation deterministic (spurious core dirt)

## NEED
Sort the handler-name lists before emitting `mod.rs` + dispatch chains in
`sh2perl/build.rs` Parts 3–5 (render / render_ext_expr / render_ext_estree
handlers), the way Parts 1–2 already sort (`leaves.sort()`,
`out.sort_by(name)`). Exact patch shape: collect `(hname, tag)` pairs into a
Vec, `sort_by(hname)`, then emit `hmods`/`hchain` from the sorted order.

## WHY
`fs::read_dir` order is filesystem-arbitrary, and these three blocks append
`pub(crate) mod …` lines in that order with no sort. Any directory change (a
new handler file, a fresh checkout on another filesystem) rewrites the
committed `mod.rs` files with zero human intent. Every backend worker treats
that as estree-worker WIP and waits/traps on it — measured 2026-10-10: this
one dirt class trapped every backend worker fleet-wide, plus the remote go
worker (whose tree nothing else had touched), burning the whole fleet's day
into trap cycles. Dispatch order is semantics-free (match arms keyed by
unique tag; module declaration order is irrelevant), so sorting changes no
behavior — it only makes regeneration idempotent.

## MINIMAL-CORE-CHANGE
In `build.rs` Parts 3, 4, 5: gather names first, sort, emit. Three small
restructures, no new files, no API change. Verify by building twice and
diffing the three `handlers/mod.rs` files (must be byte-identical), plus
`cargo build` + `cargo test --lib` green.

## FAILING-CASE
`git status --porcelain -- src/` shows `M src/render_ext*/handlers/mod.rs`
with pure-reorder diffs after any build that follows a directory change
(e.g. adding `gpu_op.rs` rehashed the listing everywhere). Backend logs show
`core mid-edit … waiting` → `core still dirty+unbuildable … trapping` on
trees whose only dirt is this reorder noise.

## NOTE (operator, 2026-10-10)
The fleet is unblocked meanwhile by a harness-side filter
(`setup_backends.sh` dirty-check ignores `// @generated by build.rs` files;
new handler `.rs` files still trip the wait). This request is the permanent
cure. Do NOT hand-edit the generated mod.rs files into a canonical order —
the next build would rewrite them again.

## OUTCOME: implemented

Parts 3–5 of `sh2perl/build.rs` now collect the `read_dir` entry names into a
`Vec<String>`, `sort()` them, and emit `hmods`/`hchain`, `expr_hmods`/
`expr_hchain` and `s_hmods`/`s_hchain` from the sorted order (Parts 1–2
already sorted). Verified by building twice with `touch build.rs`: the three
generated `handlers/mod.rs` files are byte-identical across rebuilds
(`md5sum -c`). The first regeneration canonicalised one pre-existing reorder
(`gpu_op` had been appended at the end of
`src/render_ext_estree/handlers/mod.rs`) — exactly the dirt class reported.
`cargo build --lib` green; `cargo test --lib` unchanged (the same 14
pre-existing `c_backend`/`fish_backend` failures before and after the change);
`./fail-estree` 562/562 and `./fail` 562/562.
