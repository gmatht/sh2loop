# posix-sh-go: shell `continue` never lowers to the A1 `Continue` node — no frontend can cover it

## NEED

The shared core's shell frontend must lower the `continue` builtin to the
A1 `IrStmt::Continue` node (statement position) so `debashc --shir FILE
--raw` can actually emit `"type": "Continue"`. Today the shell frontend
path **never** constructs `IrStmt::Continue` (verified: `stmt_for_command`
at src/shir.rs:5282 lowers `Command::Continue(_)` to
`IrStmt::Expr(call("continue", vec![]))`, and the expression path
`command_to_ir` at src/shir.rs:6049 does the same; the only
`IrStmt::Continue` constructions in the tree are `shir_passes/strip.rs`
— the C-style ForInit→while pass, unreachable from POSIX sh input, which
has no C-style `for` — and the deserializer `shir_json_in.rs:414`), so
no `--shir` output for any POSIX program contains a Continue node and the
A1-node coverage proxy (`frontends/coverage/coverage-gap.sh`) reports
`A1 node Continue` for every shell frontend at once (posix-sh-go,
zsh-sh-go, fish-sh-go, bat-sh-go, powershell-sh-go, ...).

The node itself is complete end-to-end — no contract change needed:
- schema: `frontends/shir-contract/schema.json` stmts.Continue
  (`{"type":"Continue"}`, type required, no other fields)
- serializer: `src/shir_json.rs:158` —
  `IrStmt::Continue => json!({ "type": "Continue", "runs": stmt_provably_runs(s) })`
- deserializer: `src/shir_json_in.rs:414` — `"Continue" => IrStmt::Continue`
- estree renderer: `src/shir.rs:13188` — renders to
  `sh2.continue()` (runtime call), byte-identical to the legacy
  `Expr(Call "continue")` arm at src/shir.rs:13194 — the estree output
  is unchanged either way

## WHY

posix-sh-go gate is GREEN but `frontends/coverage/coverage-gap.sh
posix-sh-go` reports `A1 node Continue` uncovered. The existing example
`testdata/t81_continue.sh` (gate green) emits only
`Expr`/`Call`/`Str`/`Array`/`Arith` — byte-equal to the core, gate green,
and the gap detector **still** reports Continue, because the example
cannot contain a Continue node: the frontend is byte-locked to
`debashc --shir --raw`, which never emits one. Probing every form:

```
continue            -> Expr(Call "continue")    # t81, byte-equal
continue 2          -> Expr(Call "continue")    # level DROPPED by the current lowering
```

This is NOT a by-design subset refusal: the posix-sh-go frontend parses
the `continue` keyword fine (t81_continue.sh passes the gate — the
keyword is expressed, just as a builtin call). What is inexpressible is
the **Continue emission shape**, which only the shared core's lowering
can provide. Same situation as the pending `A1 node Declare` request
(`core-requests/posix-sh-go-20260813-001245.md`): the node is complete
end-to-end, but the shell lowering never emits it. Escalating per the
core-requests channel (the estree worker is the single owner of
src/shir.rs).

## MINIMAL-CORE-CHANGE

Scope: `src/shir.rs` only — the `Command::Continue(_)` arm of
`stmt_for_command` (src/shir.rs:5282).

When the statement is a bare `continue` (no level argument), emit the
first-class node instead of the builtin call:

```rust
Command::Continue(None) => IrStmt::Continue,
Command::Continue(Some(_)) => IrStmt::Expr(call("continue", vec![])),
```

Concrete mapping:
- `continue` → `{"type":"Continue","runs":…}`
- `continue 2` → stays `Expr(Call "continue")` — the A1 Continue node has
  no level field, so a leveled continue would LOSE semantics; keep the
  legacy call shape for it (same "keep unchanged" discipline as the
  Declare request's flag forms)

Keep unchanged:
- the expression-context arm `command_to_ir` (src/shir.rs:6049) —
  `continue` inside `&&`/`||`/`!` chains is an operand, not a statement,
  and must stay `call("continue", …)`
- the estree side needs no change: the first-class arm (shir.rs:13188)
  and the legacy-call arm (shir.rs:13194) both render `sh2.continue()` —
  byte-identical estree output, so no corpus regression
- serializer/deserializer/schema already exist

Corpus constraint (the estree worker mediates): this changes `--shir`
output for every shell file containing a bare `continue` (t81-style).
Executed-stdout semantics are preserved (both shapes run the same
runtime `sh2.continue()`), and the estree corpus output is byte-identical
as noted. Frontend byte-equality gates (posix-sh-go and the other shell
frontends) will show `DIFF` until each frontend mirrors the new shape in
the same window — the established pattern from
`core-requests/done/posix-sh-go-20260806-174619.md`; the posix-sh-go
mirror is `lowering.go`'s continue arm (currently always the builtin
call, mirroring the core).

## FAILING-CASE

Minimal posix-sh-go (shell) snippet — the coverage example this request
unblocks (currently uncreatable):

```sh
i=0
while [ "$i" -lt 3 ]; do
    i=$((i + 1))
    if [ "$i" -eq 2 ]; then
        continue
    fi
    echo "$i"
done
```

Today `debashc --shir failing.sh --raw` emits — and the posix-sh-go
frontend must byte-match — no Continue anywhere: the `continue` lowers to
`{"type":"Expr","expr":{"type":"Call","func":"continue","args":[],…}}`.
After the change the A1 must contain (the estree renderer already
consumes this shape):

```json
{"type":"Continue","runs":…}
```

Repro of the gap itself (no core change needed to see it):
`bash frontends/coverage/coverage-gap.sh posix-sh-go` →
`A1 node Continue`, with `frontends/posix-sh-go/testdata/t81_continue.sh`
present and the gate green — the example cannot cover the node until this
request lands.
