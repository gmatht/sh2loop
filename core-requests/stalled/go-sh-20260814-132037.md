# go-sh: ESTree renderer cannot execute the A1 `Index` expr node (round-trip gap)

## NEED

The shared core must render the contract's expr `Index` node
(`{"type":"Index","var":<str>,"key":<expr>}` — the A1 representation of an
array element read) in the ESTree backend, so a frontend that emits it can
pass `debashc --shir-in-estree` end-to-end instead of panicking.

This is the SAME fix as the pending `core-requests/py-sh-go-20260814-125405.md`
request (identical root cause: `expr_to_estree` in src/shir.rs has no arm
for `IrExpr::Index` and falls into the
`other => unreachable!("Perl-only IR expression reached the ESTree
renderer: {other:?}")` fallback, currently at shir.rs:32251). The two
requests are not in conflict — one renderer arm satisfies both.

## WHY

go-sh's gate is GREEN (86/86 executed-stdout matches), but the coverage
proxy (frontends/coverage/coverage-gap.sh — the A1-node inventory over the
testdata emits) reports "A1 node Index" as an uncovered construct. Go
indexed reads ARE a core subset feature (t21_array, t55_array_elem,
t77_fixed_array exercise them; the gate passes), but the emitter
(go-sh.go, `exprToWord` case "index") hardwires every array read to

```json
{"type":"Call","func":"param","purity":"PureCpu",
 "args":[{"type":"Str","value":"","style":"DoubleQuoted"},
         {"type":"Str","value":"a[1]","style":"DoubleQuoted"}]}
```

— the raw `name[idx]` string, interpreted at runtime by `sh2.getVar`'s
subscript regex (harness/sh2-namespace.mjs). Map reads lower to
`Call{func:"assocGet"}` and indexed writes to an Assign target var named
`"a[1]"`. None of these produce the contract's rich `Index` node, so the
construct stays uncovered no matter which testdata example is written.

The frontend cannot switch to emitting `Index`: the A1 deserializer
ACCEPTS the node (ingress passes), but `debashc --shir-in-estree` then
crashes:

```
thread 'main' panicked at src/shir.rs:32251:18:
internal error: entered unreachable code: Perl-only IR expression reached
the ESTree renderer: Index { var: "a", key: Int(1) }
```

(exit 101 → the gate's ingress phase reports "emit is not valid A1
shIR"). So the construct is inexpressible end-to-end not because the
subset refuses it (array reads are a core subset feature) and not because
the contract lacks the node (schema.json defines `Index` in both the
expr and arith vocabularies; shir_json_in.rs:881/1161 deserialize it) —
but because the gate's execution backend cannot render it. The estree
worker's fix unlocks the go-sh worker's follow-up: extend the go-sh
emitter to emit `Index` for `a[i]` reads and add the testdata example
that covers it.

## MINIMAL-CORE-CHANGE

In `src/shir.rs`, `expr_to_estree` (the match ending at the fallback
`other => unreachable!("Perl-only IR expression...")`, shir.rs:32251),
add one arm BEFORE that fallback, mirroring the existing
`func == "arrayIndex"` Call arm (shir.rs:30536) and the already-rendered
`ArithAst::Index` arm (shir.rs:9282, `Number(sh2.arrayIndex(var, key))||0`):

```rust
// A1 `Index` expr node (array element read — the contract's rich form
// of the `arrayIndex` call; the arith variant renders below at
// `ArithAst::Index`, and the go/rust/zig/perl backends already render
// IrExpr::Index). The key is a full expr (Str/Int/...).
IrExpr::Index { var, key } => {
    let key_e = expr_to_estree(key);
    sh2_call("arrayIndex", vec![str_lit(var), key_e]),
}
```

No other file changes: shir_json_in.rs (lines 881, 1161) and
shir_json.rs (lines 381, 467) already round-trip both Index variants.
Regression risk is nil: the arm only fires on the contract's Index node,
which no current corpus emit produces (the core's bash frontend parses
`$arr[i]` to `arrayIndex` Call; go-sh today emits the `param` form above).

## FAILING-CASE

Minimal valid A1 program (the deserializer accepts it; the ESTree
renderer panics). Reproduce: `debashc --shir-in-estree /tmp/go-index.json`:

```json
{"type":"Program","contract_version":1,"imports":[],"requires":[],
 "subs":[],"var_types":[],
 "stmts":[
  {"type":"Assign","targets":[{"var":"a","sigil":null,"indices":[]}],
   "expr":{"type":"Call","func":"setArray","purity":"Emulable",
     "args":[{"type":"Str","value":"a","style":"DoubleQuoted"},
             {"type":"Array","elements":[
               {"type":"Str","value":"x","style":"DoubleQuoted"},
               {"type":"Str","value":"y","style":"DoubleQuoted"},
               {"type":"Str","value":"z","style":"DoubleQuoted"}]}]}},
  {"type":"Expr","expr":{"type":"Call","func":"exec","purity":"Emulable",
    "args":[{"type":"Str","value":"echo","style":"DoubleQuoted"},
            {"type":"Array","elements":[
              {"type":"Interpolate","parts":[
                {"kind":"expr","expr":{"type":"Index","var":"a",
                  "key":{"type":"Int","value":1}}}]}]}]}}
 ]}
```

Expected after the fix: the Index read renders as
`sh2.arrayIndex("a", 1)` and the emitted JS prints `y` (the same read
expressed as `{"type":"Call","func":"arrayIndex",...}` already runs green
today). The Go source the go-sh frontend would lower to this shape once
the renderer exists:

```go
// t86_index: array element read via the A1 Index node
a := []string{"x", "y", "z"}
fmt.Println(a[1])
```
