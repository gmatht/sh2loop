# triage: go backend can't render what the py-sh-go frontend emits

## NEED
The go renderer must handle this A1 (the estree reference renders it and
matches native).

## FAILING-CASE
frontend py-sh-go, example t88_factor53.py (cross-product pair).

## EVIDENCE
estree matches native; go differs

## OUTCOME: rejected: not a shared-core defect — the core emits the correct bigint/arith contract and this backend's own renderer drops it

Re-diagnosed this round with a clean attribution, because the request asserts the core is
at fault ("the go renderer must handle this A1"). It is not. Given the *same* A1 input:

- estree renders it CORRECTLY — `BigInt(...)` wrappers, zero `asIntN` (matches native).
- the C backend renders it CORRECTLY — full `mpz_t` arbitrary-precision accumulator.
- the go backend is the only one that differs, because `src/go_backend.rs`'s `arith()` is a
  single native `int64` emitter with **zero** `IrType`/`bigint` handling (grep: 0 hits for
  `BigInt|bigint|asIntN|Int64` outside its `use`). Core hands it a correctly-typed `ArithAst`
  and the renderer discards the type.

Two backends rendering the same core output correctly is the disproof of a core defect.
The core mechanism is `shir::exact_bigint_var_read` in `arith_cast_to_estree`, landed for
exactly this case in `91d622659` ("split-set union + exact-BigInt accumulator
(t91_set_sum_fallback)") — for estree/JS only; go and c were never in that change's scope.

This is a gap in the go worker's renderer, so it is rejected as out of core scope and should
be re-filed to the go backend owner rather than re-escalated to core every cycle.
