# A1→ESTree drops two sibling `setArray` statements at the head of `Program.stmts`

Filed by: rust-frontend worker (dogfooding cycle v0.53).
Severity: **the rust-frontend gate's ONLY red** — `make test` reports
`--- frontend-stdout [rust]: 85/102 match, 1 FAIL, 16 SKIP`, the FAIL
being `DIFF t84_tuple_destructure.rs (stdout mismatch)`.

## Symptom

`t84_tuple_destructure.rs` prints empty strings where rustc prints
values, and `0` where rustc prints `3`:

```
rustc:        a 1 / b 22 / 3 / first=10 / second=20 / solo 7
transpiled:   (blank) / (blank) / 0 / = / = / solo 7
```

The `let (t, c)` line (the file's only *let*-destructure) is CORRECT, so
this is specifically the `for (n, l) in pairs` loop pattern.

## The frontend's A1 is correct

`rust-frontend --shir testdata/t84_tuple_destructure.rs --raw` emits 9
`setArray` calls. The three relevant ones are **siblings at `stmts[0..2]`
of the top-level `Program`**, with byte-identical inner shape:

```
stmts[0] keys: ['expr','type']   expr keys: ['args','func','purity','type']  setArray __sh2tup1 ["a","1"]
stmts[1] keys: ['expr','type']   expr keys: ['args','func','purity','type']  setArray __sh2tup2 ["b","22"]
stmts[2] keys: ['expr','type']   expr keys: ['args','func','purity','type']  setArray pairs    ["__sh2tup1","__sh2tup2"]
```

`Program`-level metadata is empty for all of them (`stmt_lines`,
`var_types`, `var_const`, `var_lengths`, `var_lifetimes` are all length 0),
so nothing distinguishes them on the input side.

## What the conversion drops

Counting `sh2.setArray(FIRST_ARG)` + `VariableDeclarator` ids in the
ESTree output:

```
A1     setArray( 9 ): __sh2tup1 __sh2tup2 pairs __sh2tup6 env __sh2tup10 __sh2tup11 items __sh2tup15
ESTree setArray( 3 ): pairs env items
ESTree declarations : … __sh2tup6 __sh2tup10 __sh2tup11 __sh2tup15
MISSING ENTIRELY    : __sh2tup1, __sh2tup2
```

So the six *later* tuple stores survive — they convert to `let`
declarations — while the two at the head of the block vanish, at **every**
optimization level (`-O0`, `-O1`, `-O3` and the default all give
`defs=0`). Generated JS confirms it: `__sh2tup6`, `__sh2tup10`,
`__sh2tup11`, `__sh2tup15` all have `let` bindings; `__sh2tup1` /
`__sh2tup2` appear ONLY as string literals inside `setArray("pairs", …)`.

## It is positional

Two rewrites of the SAME A1 (nothing else changed) make both stores
survive as declarations:

| Program.stmts order | result |
|---|---|
| `[tup1, tup2, pairs, …]` (as emitted) | **tup1, tup2 dropped** |
| `[assign, tup1, tup2, pairs, …]` (shifted by one, relative order kept) | tup1, tup2 **survive** |
| `[pairs, tup1, tup2, …]` (reordered) | tup1, tup2 **survive** |

A 3-statement `Program` containing only those three statements converts to
an EMPTY `body` — so a representative reproducer must also carry the reads
(the loop's `arrayIndex("pairs", …)`), which is exactly what the real
file has. Use the real file; it reproduces 100%.

## Reproduce

```sh
FE=sh2perl/frontends/rust-frontend/target/debug/rust-frontend
CLI=./otranspilerl/target/debug/otranspilerl-cli
SRC=sh2perl/frontends/rust-frontend/testdata/t84_tuple_destructure.rs
$FE --shir "$SRC" --raw > /tmp/t84.json          # 9 setArray, defs present
$CLI -O0 - --target estree < /tmp/t84.json > /tmp/t84_es.json
# count sh2.setArray(FIRST_ARG) in /tmp/t84_es.json → 3, not 9
node harness/estree-runner.mjs /tmp/t84_es.json --source "$(readlink -f $SRC)"
```

## The model itself is sound — verified, not assumed

The name-indirection this relies on WORKS at runtime. `.dogfood/tupprobe.mjs`
(`node .dogfood/tupprobe.mjs`):

```
el (pairs[0])          = "__sh2tup1"
arrayIndex(pairs[0],0) = "a"
arrayIndex(by name,0)  = "a"
```

So `sh2.arrayIndex` does resolve a name string to a stored array, and the
store only needs to EXIST. Today `arrayIndex("__sh2tup1", 0)` looks up a
store that was never created and answers `""` — which is precisely the
empty output above.

Note also that nesting does NOT work as an alternative: `arrayIndex`
String()s an array element (`nested[0]` → `"a,1"`), which is why the
frontend hoists each tuple to a temp and stores the temp's NAME.

## Needed

The two head-of-block `setArray` stores must survive A1→ESTree (either
kept as `setArray`, or converted to `let` like their six siblings). No
frontend change is possible here: the input is already correct and the
consumer is the core's conversion.
