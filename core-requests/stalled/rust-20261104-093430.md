# estree backend: a never-written, non-reserved name's read folds to `""` and drops the env fallback

**Filed by:** rust-frontend (2026-11-04), while landing the
`env::var(k).as_deref() == Ok("0")` lowering (FRONTEND.md v0.62).

## Symptom

`std::env::var("K")` lowers to `getVar("K")` (documented in the frontend's
t67_env_var as "getVar falls back to process.env, and the native oracle
runs with the SAME process environment, so the branch agrees whether the
key is set or unset"). That is true only when `K` is on
`is_reserved_var`'s denylist. For any other key the emitted program reads
`""` even when the key IS set:

```
$ PIN_X=0 ./native                      $ PIN_X=0 node estree-runner ...
USER-set                                USER-set
PIN-set                                 PIN-unset        <-- divergence
```
(`env::var("USER").is_ok()` agrees; `env::var("PIN_X").is_ok()` does not.)

Not a compile-time env snapshot: transpiling with `PIN_X=0` in the CLI's
own environment still emits the fold.

## Minimal repro (no hand-written A1 needed)

```rust
fn main() {
    let u = std::env::var("USER");
    if u.is_ok() { println!("USER-set"); } else { println!("USER-unset"); }
    let p = std::env::var("PIN_X");
    if p.is_ok() { println!("PIN-set"); } else { println!("PIN-unset"); }
}
```
```
rustc -O -o /tmp/e repro.rs && /tmp/e                        # native
rust-frontend --shir repro.rs --raw \
  | otranspilerl-cli -O0 - --target estree > /tmp/e.json
PIN_X=1 node harness/estree-runner.mjs /tmp/e.json --source repro.rs
```

## Diagnosis

The A1 is the same shape for both keys — one `Assign` whose expr is
`{"func":"getVar","args":[Str "USER"|"PIN_X"]}` — so the difference is on
the core side, and it tracks `is_reserved_var` exactly:

- **reserved** (`HOME`, `PATH`, `USER`, `SHELL`, …): the emit is the
  documented store read with the fallback,
  `sh2.vars.HOME ?? process.env.HOME ?? ""`.
- **everything else**: the assignment becomes the literal
  `sh2.vars.u = ""`.

So the lift/native-binding path in `src/estree.rs` treats "never written in
this program" as "empty", which is sound for a shell variable and unsound
for a name the caller's environment may set. `shir.rs` already has the
right primitive — `store_var_read_no_fold(name)` — and its `param` path
uses it for exactly this reason ("a never-written name may still be SET in
the caller's environment"). The lift path does not.

## Suggested direction

When the lifted initializer is a `getVar(<literal name>)` for a name the
program never writes, emit `store_var_read_no_fold(name)` rather than the
folded `""`; or veto the lift for that assign. The reserved list stays as
the desync guard for names the RUNTIME itself reads — it is not a
sufficient definition of "may be set in the environment".

## Why it matters

Every frontend that emits `env::var`/`Getenv` as a store read silently
answers "unset" for its own flag variables — `SH2_DEBUG`, `NO_COLOR`,
`CARGO_*`, anything not in the reserved list — so an operator who sets the
flag sees no change and no diagnostic. The frontend cannot compensate
without emitting a fake write to the name, which would break `$K` reads in
the same program. Frontend gate impact: 0 today (the gate cannot export a
variable for one example), which is why this was found by hand.
