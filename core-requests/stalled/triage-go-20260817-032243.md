# triage: go backend can't render what the c-sh-go frontend emits

## NEED
The go renderer must handle this A1 (the estree reference renders it and
matches native).

## FAILING-CASE
frontend c-sh-go, example t67_heap_dyn.c (cross-product pair).

## EVIDENCE
estree matches native; go differs

## OUTCOME: rejected: not shared-core — re-measured today, still FAIL-BACKEND, but the A1 is correct

Re-ran `harness/triage.sh c-sh-go t67_heap_dyn.c go`: still FAIL-BACKEND (estree matches
native, go differs). Diagnosis: the c-sh-go A1 is valid and complete — it carries
`setVar("a", memAlloc("12"))`, `memStore(a, $i, "int", Arith)`, `memLoad(a, $i, "int")` and
`memFree(a)`, and the estree reference executes it correctly through the sh2 runtime. The
shared core is not at fault.

The defect is in the go renderer: `sh2perl/src/go_backend.rs` has no arm for any of
memAlloc/memStore/memLoad/memFree (`grep -c memAlloc src/go_backend.rs` = 0), so it emits
`// TODO(unsupported): memAlloc` etc. and the program prints nothing instead of 7/14/21.
Fix point is the go emitter (add the four mem arms), which is go-backend-owned, not core.
No core change can close it without changing the IR contract.
