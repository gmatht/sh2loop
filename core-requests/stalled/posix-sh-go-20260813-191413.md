# posix-sh-go: const_fold_arith folds loop-carried variables from the stale pre-loop pool (while-loop increments collapse to a constant → infinite loop in generated JS)

## NEED

The ESTree-path arith fold `shir::const_fold_arith` (uncommitted WIP in
`src/shir.rs`, core request estree-20260813-182434-const-fold-arith) must
not fold reads of a variable whose value can change at runtime. The const
pool is currently seeded from ANY unconditional top-level `Assign` whose
RHS folds to an integer, and the pool then persists into while/for/if
bodies, so `Var` reads inside a loop body resolve to the PRE-LOOP value.
The documented soundness rule "only `analyze_var_const` `Const` verdicts
seed" is NOT implemented: the `consts` set is consulted only for the
early-return gate, never at the seed site.

## WHY

posix-sh-go gate (byte-equality + executed-stdout) went GREEN at
18:55 and RED at 19:03: debashc was rebuilt at 19:03 with this
uncommitted fold. Byte-equality still passes 88/88 (the fold runs on the
`shir_to_estree` clone), but the executed-stdout phase now fails
deterministically:

```
DIFF t02_control.sh (stdout mismatch)
     4,6c4,2784256
     < i=3
     < hello alice
     < hello bob
     ---
     > i=2
```

The transpiled side loops forever printing `i=2` (20s timeout, ~2.8M
lines). Generated JS for the loop body:

```js
while (i <= 3) {
  process.stdout.write(String(`i=${i}`) + "\n");
  i = 2;            // BUG: should be `i = i + 1`
}
```

Root cause trace (`t02_control.sh`):

1. A1 (byte-identical between posix-sh-go and the core frontend):
   top-level `Assign i = 1`, then
   `While(cond=test "$i" -le 3, body=[echo "i=$i", Assign i = Arith(Bin(+, Var(i), Num(1)))])`.
2. `const_fold_arith` seeds the pool `i → 1` from the top-level
   `i = 1` (no `consts` check — `i` is a Var verdict: it has TWO write
   sites), then walks the while body with the SAME pool
   (`fold_stmts(body, pool, false)`), so `fold_arith` resolves
   `Var(i)` from the pool and rewrites `Arith(i + 1)` → `Num(2)`.
   The body assignment becomes `i = 2` → infinite loop.

Same unsoundness also clobbers conditionals, e.g. `x=5; if c; then
x=7; fi; echo $((x+1))` folds to `6` even though `x` may be `7`.

## MINIMAL-CORE-CHANGE

In `src/shir.rs`, `const_fold_arith`, in `fold_stmts`'s
`IrStmt::Assign` arm, gate the pool seed on the Const verdict — the
`consts` set is already computed:

```rust
IrStmt::Assign { targets, expr } => {
    fold_expr(expr, pool);
    if seed
        && targets.len() == 1
        && targets[0].indices.is_empty()
        && !targets[0].var.contains('[')
        && consts.contains(&targets[0].var)   // <-- add this
    {
        if let Some(v) = const_value(expr) {
            if in_range(v) {
                pool.insert(targets[0].var.clone(), v);
            }
        }
    }
}
```

A `Const` verdict is a single static write site in the whole program, so
a pooled name can never be rewritten by a loop/conditional body — reads
anywhere (including inside loops) then fold soundly. This alone fixes
the failing case (`i` is a Var verdict → never pooled → `i + 1` stays
runtime) and also fixes the conditional-clobber unsoundness. A stronger
alternative (defense-in-depth): additionally invalidate/snapshot the
pool around `While`/`DoWhile`/`For`/`If` bodies for names written
anywhere in that body.

## FAILING-CASE

`frontends/posix-sh-go/testdata/t02_control.sh` (POSIX sh):

```sh
#!/bin/sh
count=3
if [ "$count" -gt 2 ]; then
  echo "big"
elif [ "$count" -gt 1 ]; then
  echo "mid"
else
  echo "small"
fi
i=1
while [ "$i" -le 3 ]; do
  echo "i=$i"
  i=$((i+1))
done
for name in alice bob; do
  echo "hello $name"
done
```

Expected stdout: `big`, `i=1`, `i=2`, `i=3`, `hello alice`,
`hello bob`. Actual (transpiled): `big`, `i=1`, `i=2`, then `i=2`
forever (timeout).


The A1 is byte-identical to the core frontend's (`debashc --shir
testdata/t02_control.sh --raw`); the defect is entirely in the
