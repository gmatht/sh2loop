# py-sh-go: A1 contract still has no lambda node — Python lambdef remains inexpressible

## NEED
The A1 expr vocabulary must provide a **function-literal expression node
with parameters** so the py-sh-go frontend can lower Python `lambda`
(grammars-v4 Python3 rule `lambdef`: `'lambda' [varargslist] ':' test`,
and its sibling `lambdef_nocond`) and the ESTree backend can render it as
a JS `ArrowFunctionExpression` with params. The existing `Arrow` expr is
a zero-parameter closure:

```json
{ "type": "Arrow", "body": [<stmt>...] }        // no "params" field
```

Proposed shape (extend `Arrow` with an optional `params` field, keeping
the existing no-params shape byte-compatible; serde_json
BTreeMap-sorted keys, mirroring the `Function` stmt node's params
style):

```json
{ "type": "Arrow", "params": ["x"], "body": [<stmt>...] }
```

with `params` absent/`[]` for the existing pipeline-stage closures.

## WHY
The coverage hook (rules-gap.sh) reports `lambdef` as a Python3 grammar
rule no testdata example exercises. No example can exist: the frontend
cannot express it. `lambda` is not handled anywhere in
frontends/py-sh-go/main.go (hand-rolled recursive-descent parser +
lowerer): the lexer tokenizes it as a plain identifier, `parsePrimary`
turns it into `NameE{Name: "lambda"}`, and the following parameter name
then fails loudly:

    $ printf 'f = lambda x: x + 1\nprint(f(3))\n' | ./py-sh-go --shir /dev/stdin --raw
    py-sh-go: parse: unexpected token "x"
    exit=2

(a control `def`/`return` program emits valid A1, exit 0 — the parser
is healthy; only the lambda arm is missing).

This is NOT a by-design subset refusal: py-sh-go has no FRONTEND.md,
`lambdef` is in no exclusion ledger (frontends/coverage/
refused-py-sh-go.txt / bugs-py-sh-go.txt — grep finds no entry), and
PARSER_GAPS.md's py-sh-go table notes the A1 has only `Arrow` "lambda
body" while py-sh-go's function model never implemented closures.
Previous triage: core-requests/done/py-sh-go-lambdef-20260813-192707.md
made this exact request, but the node never landed (no core commit;
src/ir.rs:391 still reads `Arrow(Vec<IrStmt>)`, shir_json.rs:367 still
serializes `{"type":"Arrow","body":...}` with no params, shir_json_in.rs
deserializes only `body`), and the request was archived, which pruned
the core-pending-py-sh-go.txt ledger — so rules-gap.sh re-surfaced
`lambdef`. (go-sh-commclause-20260813-204112.md, still pending, cites
the lambdef/sliceop/star-expr precedents for the same verdict:
inexpressible because the A1 contract has no node/field, not because
the subset refuses it.)

A lambda is an anonymous function VALUE: `f = lambda x: x+1;
print(f(3))` binds a closure to a name and calls it. The A1 expr
vocabulary (schema.json "exprs": Int, Str, Var, Index, BinOp, Call,
MethodCall, Ternary, DefinedOr, Interpolate, Capture, Regex, Range,
RawExpr, Arrow, Array, Arith, Bool, Json, Ident, Object) has no node
that carries params+body as an expression: `Arrow` is a thunk used only
for ESTree-path pipeline stages, `Function` is a named statement-level
definition (shell fn), and no combination of the existing nodes can
reproduce parameterized-closure call semantics — so the executed-stdout
oracle (native python3 vs the transpiled ESTree run) can never pass for
a lambda example. The frontend could express it if shIR had node X: its
expr parser needs only a `lambda` case (params + body suite →
Arrow-with-params) and a function-valued Call form.

## MINIMAL-CORE-CHANGE
1. src/ir.rs / src/shir.rs: add `params: Vec<String>` to
   `IrExpr::Arrow` (or add a sibling `IrExpr::Lambda { params, body }`;
   extending Arrow keeps the ESTree renderer's existing
   `ArrowFunctionExpression { params, body }` mapping — estree.rs
   already models params on the JS side and src/shir.rs:2781 already
   reads them in the ESTree→shIR direction). No change to existing node
   shapes, so current emits stay byte-identical.
2. src/shir_json.rs / src/shir_json_in.rs: serialize/deserialize the
   `params` field (omit or `[]` when empty so existing pipeline-stage
   emits stay byte-identical; strict ingress in shir_json_in.rs needs
   the new optional field), so the A1-ingress oracle
   (`debashc --shir-in-estree`) accepts frontend emits.
3. src/shir.rs (stmt_to_estree/expr_to_estree): render the params into
   the JS `ArrowFunctionExpression` params array; body stmts lower as
   today (Arrow body is already a stmt list; the ESTree runtime must
   bind params into the var store at call time — a
   `(...params) => { sh2.setVar(p, ...); <body> }` convention).
4. frontends/shir-contract/schema.json: add `params` to the "exprs"
   Arrow entry (workspace-side, keeps check_schema.py green).

The frontend side (exprParser `lambda` case → emit Arrow-with-params,
plus a Call form for function-valued names) is py-sh-go's own fix and
lands after the contract has the node; the coverage worker retries the
gap automatically once this request completes (core-pending-py-sh-go.txt
re-entry + pruning cycle).

## FAILING-CASE
Minimal Python program (python3 runs it fine, prints "4"):

```python
f = lambda x: x + 1
print(f(3))
```

Current behavior: `./py-sh-go --shir` fails with
`py-sh-go: parse: unexpected token "x"` (exit 2), so no testdata
example can cover `lambdef` and the A1 node is missing end-to-end
(frontend emit → ingress acceptance → ESTree run vs native python3
stdout).
