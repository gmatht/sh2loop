## WHY (item 1 is shared core, and is NOT a rust problem)

`t109_bool_func.go` is a Go program with a `bool`-returning user function used
in a condition:

```go
func isYes(s string) bool { return s == "y" }
...
if isYes("y") { fmt.Println("yes") }
if !isYes("n") { fmt.Println("not-n") }
fmt.Println(isYes("y"))
```

`go run` (the oracle) → `yes / not-n / true`, rc 0.

The A1 is **correct**. `go-sh --shir --raw t109_bool_func.go` contains, for the
inlined body's test:

```json
{"lhs":{"type":"Call","func":"getVar","purity":"Emulable",
        "args":[{"type":"Str","value":"s","style":"DoubleQuoted"}]},
 "op":"Eq","rhs":{"type":"Str","value":"y"},"type":"BinOp"}
```

i.e. the predicate parameter `s` is read as `getVar("s")` — the same
convention every other transform uses (`src/transforms/dead_store_elim.rs:549`,
`copy_propagation.rs:696`, `f32_narrow.rs:759`, `shir_native_stmt.rs:1072`).

**The same A1 renders correctly to Rust and wrong to ESTree.** The emitted
ESTree replaces the parameter read with an empty literal:

```json
{"type":"IfStatement",
 "test":{"type":"BinaryExpression","operator":"==",
         "left":{"type":"Literal","value":"","raw":null},
         "right":{"type":"Literal","value":"y","raw":null}},
 ...}
```

so `s` reads empty, `isYes("y")` is false, and the program prints
`not-n / false` instead of `yes / not-n / true`.

Proof, both renderers on the identical A1 (`$S` = scratch):

```
$ go-sh --shir t109_bool_func.go --raw > t109.a1          # the A1, once

$ shir_render --target=rust  - < t109.a1 > m.rs && rustc -C opt-level=1 -o b m.rs && ./b
yes
not-n
true                                   # == the oracle            CORRECT

$ shir_render --target estree - < t109.a1 > e.json
      && node harness/estree-runner.mjs /dev/stdin --source t109_bool_func.go < e.json
not-n
false                                  # != the oracle            WRONG
```

Reproduced **3/3** on both `backends/rust/target/debug/shir_render` (clean,
committed, `bbdb49cb3`) and the main checkout's `otranspilerl-cli` — so this is a
**committed** defect, not estree-worker WIP and not a load flake. (The previous
session's `backends/rust/docs/backend-rust-gate-diagnosis.md` called this case a
"flake"; it is deterministic, and it is the one thing that holds the js column
red.)

  `debug_param_positional` tests calling `direct_shell_fn_calls` — so this is

## ITEM 2 — NOT CORE: `fail-go` scores a skip as a rust failure

`fail-go` runs the rust leg only when the **js runtime** exited 0
(`fail-go:179`):

```sh
if [ $jrc -eq 0 ] && [ -n "$a1" ]; then
```

`jrc` is *node's* exit code, so any program whose correct exit code is nonzero
never gets a rust verdict. `t99_external_unit.go` is exactly that: with no args
it prints `alive` and `os.Exit(2)`; js passes with `MORC=2, jrc=2`. The rust leg
is then skipped, `R="n/a"` (`fail-go:202`), and `fail-go:264` counts that skip
as a rust failure while `fail-go:265` refuses to print it — the tally reads
`123/124` with no failure shown.

The rust target is correct for t99; it is simply never measured. Measured by
hand on that A1: `stdout=alive`, `rc=2` — equal to the oracle.

Minimal patch (2 lines, `fail-go` owner):

```sh
# fail-go:179 — the rust target must not depend on the js program's exit code
-    if [ $jrc -eq 0 ] && [ -n "$a1" ]; then
+    if [ -n "$a1" ]; then

# fail-go:264 — `n/a` is a skip, not a failure (line 265 already agrees)
-  if [ "$RUST" = 1 ]; then [ "$Rv" = PASS ] && rs_pass=$((rs_pass+1)) || rs_fail=$((rs_fail+1)); fi
+  if [ "$RUST" = 1 ]; then case "$Rv" in PASS) rs_pass=$((rs_pass+1));; n/a) skip_rust=$((skip_rust+1));; *) rs_fail=$((rs_fail+1));; esac; fi
```

## RESOLVED 2026-09-30 19:40 — and the reason this report could not find it

Both rows above are green now: `./fail-go --rust` reports **124/124 js pass,
124/124 rust pass**, stable over two runs. The cause was one layer below
anything this report checked, and it is worth recording because it explains
why every "VERIFIED STATE" row here was measured against the wrong code.

**The shared core did not compile.** `src/perl_generator_fixed.rs:519` called
`fix_eval_stmts`, which commit `62b79b39a` added the *call* for but never
defined — it is in no commit in this repo's history:

    error[E0425]: cannot find function `fix_eval_stmts` in this scope

So `cargo build` against the core failed, `ensure_oracle` in `fail-go` could
not rebuild `otranspilerl-cli`, and the binary on disk was whatever was last
linked — 16:12 today, roughly two hours before this report was written. Every
green row above is a real measurement of that stale binary, which is why the
worktree was GREEN and the gate RED with nothing in between to explain it.

Two further consequences, both now fixed in e3de0a9dd:

  * the A1 named-parameter fix (22083e1c4) was already correct and could not
    take effect for the same reason — t109's `js` column went green only
    after a successful relink.
  * `quote_cmdsub_tails` returned an empty string whenever its needle was
    absent, i.e. for essentially every program, so the Perl path emitted 0-byte
    files that still exited 0. The corpus now generates 553 files, 0 empty.

**The `getVar` fold this report names was not the t109 bug.** The estree
rendering of `isYes` was losing the parameter (`() =>` instead of `(s) =>`),
which 22083e1c4 fixes; with the binary rebuilt, t109 passes on both columns
without any further estree change.

**Do not "fix" this in the rust backend.** Still true, and now with a
mechanism rather than an inference.

**One gate bug this report is right about, now fixed** (workspace 4ae764dd):
`fail-go:264` counted `n/a` as a rust failure while `:265` declined to print
it, so the summary read 123/124 while listing no failing row. The rust leg was
also gated on the *js* leg's exit code, which scored t99's correct `os.Exit(2)`
as `n/a`. Both are corrected; the rust column is 124/124.

**Also worth recording** (workspace 9c2f3b81): `fail-go`'s oracle had never
worked. `wrap_go`'s guard was `grep -q 'func main('`, and on this box `grep`
is a shell function wrapping ripgrep, which rejects the unescaped `(` as an
invalid regex. Every one of the 124 corpus files was therefore wrapped a
second time and the oracle build failed for all of them — the `oracle_rc` this
report quotes as evidence was measuring a syntax error, not the program.
